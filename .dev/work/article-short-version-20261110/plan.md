# 首次阅读短稿计划

任务：article-short-version-20261110。正式文稿任务，无代码/展示验证档，无 Test。用户要求现有长稿作为总纲参考，另写简化稿或给出写法建议；按明确文稿意图交付一篇可比较的独立短稿，保留既有总纲。

## 目标与范围

新增 `articles/agent-delivery-system-short.md`，面向用过 AI 编程、遇到“完成却不能用”的首次阅读者，约 1600～2200 个汉字。只讲一个中心问题：为什么 Agent 的完成声明不能直接等同交付，如何改善这条链路。文中简要联系开明项目，不写产品手册。不改总纲、产品行为、技术契约、代码、权限、环境、交付检查或项目规则，不对外发布。

本目录保存 Plan、作者报告、独立 Review 和结算；`docs/technicalnew/validation.md` 追加本轮文稿检查入口与未执行边界。

## 验收

1. 有独立标题与具体开头，读者无需读总纲即可理解；全篇一个假设案例（订单导出）串起问题与措施，清楚是假设，不能伪装成真实事故或产品战绩。
2. 内容只保留三个断点及回应：需求依据/验收未被准确使用；测试陷入同一假设；交付后缺少证据和项目记忆。每点有因果和具体做法，而非概念罗列。
3. 保留用户此前强调的模块文档、索引、按需加载，但压缩到能解释清楚的几段：按业务能力组织，读本模块和必要共享接口/规则，可补读；不把所有内容塞给所有 Agent，也不为缩短上下文删掉必要约束。
4. 测试讲清预期来自确认需求、独立检查实际结果、坏结果应被检查识别，不能仅凭全绿；独立不靠换角色名或读作者自评，需正式依据与实际成果。无需展开术语“负向控制”、测试体系和返工状态。
5. 完成标准先明确，检查与当前交付一致，未覆盖如实记录，知识写回项目；简述工程原则，不保证绝对正确，不将程序事实门写成自动判断全部业务。
6. 删除首次阅读不必要的 Task 字段/状态、七角色、验证档、Pi/MCP/DSL、Git 判定、恢复栈、SDK、研究与验证流水细节；不逐章缩写总纲。原则以原正式依据为准，不新增对外产品承诺。
7. 公众号短段落，最多三个正文分节，不用密集列表/大表/架构图；结尾回到读者如何判断交付，项目介绍约一段。长度目标服务阅读，不为数字删掉逻辑。
