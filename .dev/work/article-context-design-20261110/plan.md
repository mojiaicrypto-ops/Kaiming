任务：article-context-design-20261110。正式文稿修改，不改代码、产品/技术规则、验收、模块边界、交付检查或环境。无代码/展示验证档，无 Test 阶段。前一篇交付已提交为 73f6161；本次为用户明确追加的文稿目标，直接授权范围内修改。

## 目标与范围

在 `articles/agent-delivery-system.md` 的核心论证中补足需求文档组织、按模块拆分、索引、按需加载和独立开发，衔接已有任务/验证/结算主线。保存本任务 Plan、独立 Review 和结算，在 `docs/technicalnew/validation.md` 追加文稿验证记录。不对外发布，不调整既有项目契约。

## 验收

1. 文档组织作为开发前的理解条件进入主线，不能只在结算章节补一句“按需读取”。说明长上下文不等于有效理解，避免宣称所有模型存在固定长度阈值或本项目已证实性能提升。
2. 拆分按长期业务能力/技术职责内聚，不按文件页数、前后端角色或聊天轮次机械切；模块和实现切片不是同一概念。小项目无需预建空目录。
3. 说明结构化 Markdown 的作用：稳定标题可引用，职责/正常异常/验收/实现状态/未知可定位；产品与技术职责分开、共享规则一份权威定义。格式服务语义，不承诺格式本身使模型正确。
4. 索引给路径、职责、何时读取；模块地图连接规格、实现、接口；不用复制正文形成第二份事实。可用简洁阅读路径表达“项目入口→模块地图→目标模块规格/接口→本次 Plan→相关代码与测试”。
5. 沿用假设订单导出案例说明 developer 加载目标模块及必要依赖/共享权限契约、相关实现和测试，排除无关模块与设计聊天；可补读，依据不足先补设计，不为压缩 token 丢弃必要约束。
6. 先有规格和共享接口，再形成可独立验收、写入集中、依赖清楚、Review 可覆盖的切片；独立上下文开展开发，必要时按明确写入范围协作，最终组合仍要联调与验收，不新增未支持的并行 Task/自动检索承诺。
7. 开头或结尾适当呼应理解环节，新增内容与原文连贯，保留假测试、自证循环等核心，不整篇泛化为文档教程。
