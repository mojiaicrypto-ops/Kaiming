## 1. AC-054 事件重放抖动 `[1,2,3,4,4]`：**测试侧**

### 1.1 诊断

`apps/daemon/test/protocol.integration.test.ts` 的 AC-054 用例在 resume 后把**整条连接**的 `event.cursor` 序列断言为 `[1,2,3,missed]`。产品侧的保证是**按订阅流**的：

1. `apps/daemon/src/protocol.ts` 的 `subscribe()` 在**同范围**重订阅时同步删除旧订阅（`subscriptions.delete` + `events.remove`），注释即写明「One live subscription per (kind, id)」；
2. 但旧流在删除之前，其 50 ms 轮询可能已经把新事件发出——这是**被替换流自己的 cursor 前进**，不是重放；
3. `packages/client/src/subscriptions.ts` 的游标水位按订阅维护（`cursor <= watermark` 计为 duplicate 并丢弃），事件帧本身不携带 `subscriptionId`，批次由 `batch_end {subscriptionId, scannedThrough}` 封闭（`protocol.md` §2）。

因此重复只可能是**跨流**的，而旧断言把两条流当成一条流求和。

### 1.2 复现（旧断言在负载下真的会输）

用 `git show HEAD:…` 取回修复前的用例，放入一次性副本 `apps/daemon/test/zz-ac054-oldassert.integration.test.ts`（跑完即删），在 64 个忙循环的合成负载下重复：

```text
run 5/40 exit=1 load=161.14 86.35 77.56
AssertionError: expected [ 1, 2, 3, 4, 4 ] to deeply equal [ 1, 2, 3, 4 ]
    1008|     expect(afterResume).toEqual([1, 2, 3, missed]);
```

低负载（28–88）时同一旧断言 5/5 通过——抖动是概率性的，与登记完全一致。另用一次性探针（`zz-` 前缀，已删除）对同一 resume 序列做 120 次分类采样，在 load 38 下得到：

```text
AC054-REPRO duplicates=7 crossStream=7 sameStream=0
```

**同流重复为 0**，全部重复都发生在两条不同订阅之间，坐实「测试侧跨流误读」。

### 1.3 修法与验证

- 等待真实条件：resume 流的 `batch_end {subscriptionId: resumedId, scannedThrough >= missed}`（有界 5 s，`waitFor` 轮询帧，不是 sleep）；`resumedId !== subscriptionId`。
- 按 `batch_end` 归属游标（新增 `cursorsByBatch`，每个批次由其 `batch_end` 封闭，发送端在同一次同步扫描内发完事件再发 `batch_end`，不会交错）。
- 断言：resume 流**恰好**重放 `[missed]`；**每条流**的游标不重复；连接整体游标集合 = `{1,2,3,missed}`、前三个 = `[1,2,3]`、最后一个 = `missed`。断言未放宽：单流唯一性比旧断言更强。
- 负载复验：**10/10 通过**，load 141–172（含旧断言失败的 161 档）。

## 2. Docker 容器读 `broker.integration.test.ts:505`：**测试侧**

### 2.1 诊断

失败行是容器 **bash** 调用的 `expect(identity.ok).toBe(true)`。`Broker.invoke` 在 `mode === 'container'` 时，第 5 步对**每一次调用**执行 `this.docker(this.execImage)`，默认实现 `probeDockerAvailability` 用 `docker version`，超时 **15 s**（`packages/core/src/broker.ts`）。探针超时即 `PROVIDER_UNAVAILABLE` 拒绝，**在容器执行之前**返回；同一次用例里更早的容器 read 已经成功，说明容器执行路径本身没问题。

### 2.2 复现（注入真实条件：探针慢于 15 s 预算）

用一个只延迟 `docker version` 的 PATH 外壳（`/tmp` 内，未入库），让第 3 次 `docker version`（= bash 调用前的探针）睡 16 s：

```text
FAIL broker.integration.test.ts:505:27
AssertionError: expected false to be true
Tests  1 failed | 7 skipped (8)     （时长 24.83s，与 16s 延迟 + 15s 探针超时吻合）
# 直接量测产品探针：
elapsedMs 15004 {"available":false,"reason":"spawnSync docker ETIMEDOUT"}
```

自然负载侧：在 4 个满载容器 + 32/48/64 忙循环（load 60→239）下，修复前单用例 6/6 通过、整文件 4/4 通过——本机合成负载下 `docker version` 峰值仅 1.85 s（40 次采样 0 失败），未自然复现；登记条件（Docker Desktop VM 长期 300% CPU）正是同一机制在更高压力下的表现。这是**诚实边界**：机制被证明，自然负载下的翻转未在本次复现。

### 2.3 修法与验证

- 在模块加载时用产品自己的 `probeDockerAvailability` **测一次**，对超时（`ETIMEDOUT`）做**有界等待**（60 s 上限、1 s 间隔、每次都是真实探针；守护进程确实下线时快速失败，不空等）。
- 把这一次**真实量测**通过 Broker 的 `docker` 注入口交给 harness，容器执行仍然是真的 `docker run`（read + `id -u` = `10001` 全部断言保留）。
- 拒绝路径的确定性覆盖不变：`broker.test.ts` W7R3-04（注入探针）+ `apps/cli` doctor。
- 同一慢探针外壳下的 A/B：修复前 `:505` 失败（探针调用计数 3），修复后通过且 `docker version` 调用计数 = 1（只余那一次真实量测）。
- 负载复验：**6/6 通过**，load 170–228，单用例 11.7–20.4 s（真实容器执行，未跳过）。

## 3. AC-046 并行兄弟失败（整机负例，新增）

文件：`packages/core/test/join.integration.test.ts`（`describe('join: parallel sibling failure on the real stack (AC-046)')`）。

- 真实 `Orchestrator.dispatch` 派发 Chief Run；再由真实 `professionalSpec` 派发**两个并行子 Run**（`join=all`）。

- 断言：`RunLifecycle.end` 在活着的 `join=all` 子 Run 存在时拒绝父 Run 置 `completed`；父保持 `waiting_children`；`JoinCoordinator.onChildSettled` 返回 `blocked` 且 `failedRequired=[required]`，**兄弟的 `stage_result` 完整保留**（summary/`readLedgerSeq`/`readLedgerHash` + 库中 1 行）；`protocol.md` §7 的 `chief_action_required` **恰一次**并携带全部子 Run（重复计算不重复落事件，N-06）；父仍处于 `waiting_children` 时经真实 `ProjectMailbox` 提交**新 Chief 指令**并被受理，join 状态回到 `waiting`，失败子 Run 与兄弟结果均未被改写。
