# 开明产品需求文档

日期：2026-10-04。本套文档定义第一版已确认的产品行为；设计要求不声明功能已经实现。

## 1. 我们要做什么

**开明是一个持续推进软件项目的 AI 工作台。用户与主管 Agent 自由讨论，把确定要做的事情保存为需求，交给 Agent 协作完成，经过独立检查后取得成果，并把项目知识更新到可以继续工作的状态。**

用户主要面对一个主管。主管既是讨论伙伴，也是其他 Agent 的组织者：可以直接回答、调查项目、澄清需求、提出建议，也可以组织设计、开发、审核、测试和结算。设计 Agent 同时负责产品分析与必要技术设计；角色用于明确责任和隔离上下文，不照搬人类团队岗位。用户决定目标与取舍，主管在已授权范围内自主组织工作。

产品要交付三个相互关联的结果：

1. **事情做完**：得到实际代码或文档成果，知道哪些检查执行过、哪里还有问题。
2. **项目记住**：需求、产品与技术知识、代码和测试入口随工作更新，不只留下一段聊天总结。
3. **下次接得上**：离开工作台后工作仍可推进；重新打开或换一个会话，能找到进展、成果和下一步。

## 2. 谁使用，在什么情况下使用

第一版面向个人开发者，以及能够明确项目目标、参与方案取舍和验收的软件项目负责人。用户可以把专业工作交给 Agent，但仍需对产品方向、范围变化和重要风险作决定。

产品形态为用户自管、单用户的浏览器工作台，可在自己的工作电脑或服务器持续运行。用户管理的是该运行环境中可访问的项目目录；远程访问时，浏览器所在电脑的文件不会自动成为项目文件。首次使用需要启动工作台、取得访问凭证、配置可用模型，再打开项目。安装、启动、取得凭证和进入工作台的说明属于首版交付材料。

典型使用场景：

- 接手已有项目，希望 AI 先理解当前能力，再讨论下一步。
- 有一个想法，先自由讨论，暂时不决定开发。
- 保存尚待规划的需求提案，让 AI 设计后形成实施需求；也可直接保存已有充分依据的实施需求。
- 提交开发或正式文档任务，让 Agent 组织实施、检查和交付。
- 查看正在进行的工作，参与必要决定，离开后回来继续。
- 开始新会话，希望从项目知识接续，不再重复解释整个项目。
- 正在用 Codex、Claude Code 等编码 Agent 干活，希望把其中一项工作交给工作台：说清目标、看进度、答问题、取回成果。

每个开明实例只有一个全局 Server，统一管理该实例的多个 Project 和 Session。第一版支持多项目、多主管会话；一个主管 Session 同时只推进一项未结束的 Task，其他话题在新的主管 Session 中处理。团队账号、多用户同时协作、托管商业服务不属于本版范围。

## 3. 产品由哪些业务模块组成

| 业务模块 | 用户要完成的事情 | 得到的结果 | 详细需求 |
|---|---|---|---|
| 项目工作区 | 接入、切换项目，找到会话和已有工作，配置模型，查看项目文件 | 可以持续推进的项目空间 | [项目工作区](modules/project-workspace.md) |
| 主管对话 | 自由讨论、调查项目、澄清目标、获取建议、协调工作、作出决定 | 讨论结果、候选需求和明确指令 | [主管对话](modules/chief-conversation.md) |
| 需求管理 | 保存提案、查看设计产出的实施需求、选择实现并追溯结果 | 可追溯的用户意图与明确交付目标 | [需求管理](modules/requirements.md) |
| 任务交付 | 给出正式任务，查看计划和进展，检查实际成果，暂停或继续 | 经过适用独立验证并完成结算的成果 | [任务交付](modules/delivery.md) |
| 项目知识 | 了解已有能力、设计与实现情况，维护按模块组织的知识，在新会话中继续 | 可导航、可按需读取的项目记忆 | [项目知识](modules/project-knowledge.md) |
| 外部 Agent 接入 | 用 Codex、Claude Code、Grok 等编码 Agent 把工作交给工作台，看进度、答问题、取回成果 | 与浏览器同一条会话、同一套交付规则的第二个入口 | [外部 Agent 接入](modules/external-agents.md) |

项目工作区承载其余四项能力；浏览器与外部 Agent 是两个入口、同一份工作。主管对话是主要协作入口；需求管理连接提案、实施需求和交付结果；任务交付组织设计与实现工作；项目知识保存内聚产品能力、技术依据及实际状态。任务结束时，成果通过结算回到需求和项目知识。

这些模块围绕同一个项目配合，用户能够从需求找到任务，从任务找到成果与报告，从成果找到相关知识和文件。

## 4. 从意图到交付的完整主线

需求提案是尚待规划的意图；实施需求是范围明确、可验收的改变；模块是长期知识边界；Task 是一次设计工作或一个实现流程；Session 是专业 Agent 的工作上下文。设计工作可产出多条实施需求，模块与需求不按文件数量一一对应。

```text
自由讨论／需求提案
  → 设计工作：产品分析 + 必要技术设计
  → 独立审阅、结算，保存内聚模块与实施需求
  → 选择实施需求，进入实现 Task 流程
  → Plan → 开发 → Review → Test → 结算
  → 需求完成，项目知识更新
```

主管依据已有事实判断缺口，已有设计充分时可以直接实施，不机械重走设计；只委托设计时交付后结束，不自动开发。用户决定目标、范围和重要取舍，AI 决定具体分析、文档拆分、专业协作和上下文，工具保存真实结果，独立验证约束完成结论。

以“做一个支付网关”为例：

1. 用户讨论业务目标，明确保存后形成轻量提案，不要求立刻提供完整接口与验收。
2. 用户委托设计。主管组织统一设计角色，按需调查现状、确认行为，形成支付接入、交易、退款、对账等内聚模块，并补齐必要技术契约；模块数量由项目决定。
3. 设计形成创建订单、支付通知处理、退款处理等实施需求，每条有范围、验收、依赖和文档依据。独立审阅覆盖原目标、模块内聚与可实施性；确认并结算后归档提案，实施需求仍未完成。
4. 用户选择一条实施需求。主管制定总体 Plan，组织专业 Session 完成开发、Review、Test 和结算，回填相应模块与需求的实际事实。
5. 后续继续其他实施需求；新会话按项目索引读取已有设计和成果，不依赖设计聊天。Plan 若发现边界不清则停止实现并返回设计，不凭空创造规则。

已有项目中的较小改变也沿同一关系推进。下面说明具备充分依据时的直接实现路径。

## 5. 一个直接实现的使用例子

以“给已有项目增加密码重置功能”为例：

1. 用户打开项目，看到已有会话、需求和未完成工作。开始主管协作后，按需调查现状；首次正式保存或实施前，展示要建立的知识入口，用户确认后保存。
2. 用户与主管讨论密码重置。主管按需阅读账号模块、当前实现和相关约束，区分已有事实与新建议。此时仍是讨论。
3. 用户说“把这个保存为需求”。已有行为与验收充分时，主管保存实施需求并关联账号模块；仍有待规划意图则保存提案，再按授权组织设计。保存不启动开发。
4. 用户说“实现这个需求”。主管核对已形成的产品与技术依据，必要时先设计；充分后建立负责该实施需求完整交付的 Task，制定并固定保存一份总体 Plan，再按当前步骤组织一个或多个专业 Session。用户可以看到正在做什么、阶段成果和需要自己决定的问题。
5. 开发完成后，由独立 Agent 审核和测试实际成果。发现属于当前目标的问题，主管组织修复并重新检查；改变目标或范围的事项由用户决定。
6. 检查通过后进行结算：更新账号模块的实际实现与验证情况、代码和测试入口，写需求完成摘要、保存交付报告和遗留问题，保存本次成果。
7. 用户得到完成报告：实际改变、验证结果、未覆盖部分、项目知识和证据位置、保存情况、剩余问题。只有完成要求满足，任务才显示完成。
8. 用户以后打开新会话，主管可以从项目知识了解密码重置已经做到哪里。用户继续提出下一项工作，无需重讲上次开发过程。

上述过程中，主管在阶段切换前显式更新任务结果与阶段，程序不自动推进业务阶段。委派同步推进当前任务；专业 Session 需要用户确认、选择或输入时沿用 Pi 原生语义，经主管协作通道呈现，由宿主关联答复并恢复原调用；不新增业务确认类型或要求主管管理交互生命周期。需要模型判断时通过实际执行结果取得答复，继续原 Session 和等待。关闭浏览器不等于暂停任务；回来后看到同一项工作的真实进展、待处理请求和已有成果。

另有两条常用路径：用户可以一直自由讨论而不创建需求；也可以直接要求实施一个明确目标，由主管补齐必要的需求与计划后继续，不要求用户先保存再重复启动。

所有使用路径见 [完整用户流程](journeys.md)。

## 6. 用户实际能看到和操作什么

具体排版由产品界面设计决定，下列能力必须可达：

- **项目入口**：打开、切换项目；查看项目概况、会话、需求、进行中工作和需要处理的事项。
- **主管对话**：发送文字，阅读回复、专业结果与工作说明，对需要决定的事项作答。
- **需求列表与详情**：区分待规划提案与实施需求，查看来源、设计结果、目标、验收和依据，选择设计或实施，查看成果摘要和历史关联。
- **任务进展与详情**：查看目标、计划、当前阶段、参与角色、检查结果、阻断和下一步；暂停、继续或取消。
- **项目资料**：浏览项目目录和文本文件，打开相关知识、需求、计划、报告、证据和源码入口。
- **模型设置**：配置默认模型，按专业角色或项目调整，检查实际可用性。
- **外部接入可见**：外部 Agent 委派的工作出现在同一条固定主管会话里，用户在浏览器能看到它的 Task、阶段、成员、待答问题与报告，也能取消；名称由用户决定，不影响归属。

用户必须能够区分“正在讨论”“指令已收到”“需求已保存”“任务正在实施”“正在等待决定”“成果已经完成”。聊天回复结束不代表交付任务完成。

界面以主管对话为主入口：正在推进的任务、计划步骤、参与角色和待决定事项在同一屏可见，其余资料视图用于查看依据和成果。具体布局、视觉与组件契约见技术设计的前端设计契约，不在产品需求中规定。

## 7. 第一版必须完整交付什么

| 范围 | 第一版完成要求 |
|---|---|
| 接入与使用 | 有使用说明，可以进入工作台、配置模型、打开项目并开始协作 |
| 项目与会话 | 一个全局 Server 管理多项目与会话；每个主管 Session 同时只推进一项未结束 Task，新话题使用新主管 Session；已有会话可继续 |
| 讨论与决定 | 允许自由讨论；明确保存和明确实施才产生对应业务结果；专业交互沿用 Pi 原生语义，经主管协作通道呈现，宿主关联答复并恢复原请求；已有授权不重复询问 |
| 需求 | 轻量提案与实施需求各有一份项目文件；设计转化来源可追溯，列表真实反映状态，能规划、实施、取消和归档 |
| 正式交付 | 设计工作、标准代码、轻量修改与正式文档维护均能按适用要求完成；设计不自动进入开发 |
| 独立检查 | 实际审核与测试结果可查看，发现问题可返工，不能由开发自称通过 |
| 结算与知识 | 更新受影响知识、完成摘要、入口和归档，新会话能够据此继续 |
| 持续与接续 | 用户离开后继续工作；重启恢复 Task、Session 历史和已有成果，核实后续办；不恢复工具栈、不自动重放未知操作 |
| 失败反馈 | 配置缺失、等待决定、保存失败、检查失败、执行情况未知均有明确原因和下一步 |
| 外部 Agent 接入 | 提供标准 MCP 服务（本地 stdio 与常驻端点）；每个项目一条固定会话、上下文连续；可委派、查进度、等进展、答问题、补充、取消、读报告与 Plan，并能列出项目与需求；不新增策略层、不改变浏览器工作流与既有检查规则 |

本版不要求用户设计工作流、逐步维护每个 Agent 的状态或编写上下文装配表。产品应内置基础协作规则，让主管自主计划和组织；用户查看依据与结果，在需要时作出决定。

本版不扩展团队管理、需求排期系统、自动定时任务、生产发布自动化或通用项目管理套件。讨论中提出的额外需求先作为建议，不能自动扩大本次交付。

## 8. 判断产品是否完成

需要实际走通：打开项目 → 自由讨论 → 保存提案 → 设计与独立审阅 → 保存实施需求和文档、归档提案 → 启动实现流程 → 修复审核发现 → 独立验证 → 结算并保存成果 → 新会话从知识继续。还要验证复用已有设计与 Plan 返回设计的路径，实际完成一次轻量修改、一次正式文档交付，以及暂停、断线和接续场景；并用一个真实编码 Agent（如 Codex 或 Claude Code）通过外部接入委派一项工作，走完 [J-11](journeys.md) 的进度、答复、取消与接续。

需求规范、模块化知识和结算是完成条件的一部分。代码存在、模型说完成、单个 Agent 结束，都不足以证明产品交付完成。验收场景见 [产品验收](acceptance.md)。

## 9. 如何阅读和使用本套文档

首次了解产品，读本页即可建立整体图景，再读 [用户流程](journeys.md)。设计某项能力时，只展开相应模块及其引用；核对实现结果时，使用 [产品验收](acceptance.md)。

模块文档定义具体用户行为、可见结果、异常和边界；总体流程只负责串联。技术方案与实施计划应依据获批准的产品需求另行编写。

本套文档是当前正式产品需求。

Task 只分只读与修改：只读调查的 Plan/报告保存在工作台；正式需求设计和代码/知识修改采用修改 Task。主管等待当前步骤的全部子 Session，超时取得状态后决定下一步。业务含义由主管与独立 Agent 判断，程序核对身份、状态、必要报告、版本与真实保存。完整交付责任见 [任务交付](modules/delivery.md)。
