# 任务交付

## 用户目标与模块边界

用户把一个明确的软件项目工作交给 Agent，能看到推进过程，最后取得真实成果、验证结果和可以继续使用的项目记录。

Task 是主管组织完成一次正式工作的过程，目标可以是保存专业分析结果、交付设计依据，也可以是实现一条实施需求；这些工作有不同成果和完成条件，不把项目从最初设想到全部实现塞进一个长期 Task。主管自行讨论、只给方案、保存提案不强制建立任务；调用专业 Session 时必须绑定 Task，只读调查采用只读 Task，不因此启动开发。本模块负责从明确目标到完成；[需求管理](requirements.md) 保存改变，[项目知识](project-knowledge.md) 保存项目当前事实。

## D-01 创建工作与明确交付目标

用户启动已有需求，或直接要求开发、修改、正式整理项目文档时，主管明确目标、范围、交付物和验收，建立一项持续保存的工作记录。

设计工作围绕本次设计目标建立 Task，可以形成多个模块和实施需求；实现流程围绕一个实施需求建立 Task，专业分工和开发、Review、Test 各步骤不是新的用户任务。产品与技术设计由统一设计角色承担，是否需要分多个设计 Session 由主管按上下文和职责边界决定。一个主管 Session 同时只推进一项未结束 Task，包括等待、暂停和结算中的任务；其他话题或交付目标在新的主管 Session 中处理。当前任务完成、实际取消或安全交接给另一主管 Session 后，原主管 Session 可以承接下一项工作。标准开发缺少充分依据时，先判断能否补存明确实施需求，或是否需要独立设计工作；按有效授权完成必要准备后继续，不能拿宽泛目标直接开发。轻量修改可以直接按明确目标工作。

Task 只分只读和修改，由主管按目标选择。只读用于调查、讨论辅助，只保存工作台里的 Plan 和报告，不修改项目；修改用于正式需求/设计文档、项目知识和代码改变。审核角色可以在修改 Task 内保持只读，角色与 Task 类型不是一回事。标准、轻量、设计等是完成责任不同的工作场景，不再是 Task 类型。

用户能找到任务与来源需求、主管会话的关联。重复提交相同启动操作返回已有工作，不重复实施；不同目标可以形成不同任务，不能仅凭文字相似就合并。

## D-02 修改前有计划，授权范围可理解

代码或正式文档修改前，主管为整个 Task 制定一份与规模相称的总体 Plan，包含目标、范围、依据、主要步骤与角色、检查方式、风险和需要用户决定的事项。修改 Task 的总体 Plan 固定保存在 `.dev/work/<taskId>/plan.md`，只读 Task 的简短安排保存在工作台，由任务详情打开；简单修改可以用一段话。后续修订维护同一份总体 Plan，并保留必要的修订与决定记录。

默认情况下，明确实施指令已经授权目标范围内总体 Plan：展示后可继续，不反复批准相同步骤。项目可以选择逐计划确认，确认对象是主管制定的总体 Plan；选择后必须遵守，不能用默认政策覆盖。展示完整 Plan 后通过与其他事项相同的 Pi 原生确认、选择或输入取得答复，不定义专属 Plan 确认类型。

子 Session 可以自主制定内部计划，也可以直接完成简单工作，不要求另存计划文件或逐份审批。内部安排在总体 Plan 与已有授权范围内推进；它不能自行改变目标、范围、验收或绕过需要用户决定的政策。

改变产品目标、范围、验收、项目规则，或进行破坏性数据操作、对外发布等重要动作，先提供具体影响供用户决定。仅分析或给方案的请求没有修改授权。已确认决定与计划修订保留，方便核对后来为何变化。

## D-03 主管组织专业协作

主管自主选择适合的角色、任务拆分、依赖和返工安排，不要求用户手动派发每个 Agent。主管按当前步骤创建或绑定一个或多个专业 Session，再运行相应工作；角色按实际需要使用，不要求每次全部运行。

| 责任 | 应完成的工作 | 用户能查看的结果 |
|---|---|---|
| 设计 | 产品分析、模块内聚与需求拆分、必要技术架构与契约设计 | 产品文档、实施需求、适用技术依据、未知与决定 |
| 前端/后端工程 | 对应实现、调查与范围内修复，内置单元测试与 TDD 自查 | 实际变更、实施说明、执行过的检查 |
| 审核 | 独立检查成果、需求和影响 | 审核结论、问题、证据和修复核对 |
| 测试 | 独立执行端到端集成/E2E 验收与适用回归 | 实际步骤、观察、结果、未覆盖事项 |
| 结算 | 将已验证成果沉淀为项目事实 | 知识更新、摘要、归档、遗留问题 |

每项专业工作有明确目标、适用规则、依据路径、依赖和期待成果。专业 Agent 可以自主调查、补读相关资料和质疑假设。主管了解全局并协调，不能代替开发者自证独立审核或测试通过。

委派工具等待当前 Task 当前步骤的全部专业 Session，底层异步调度；不等待主管本身或历史步骤的 Session。一份报告到达后仍有其他成员运行、排队或等待用户，就继续等待。所有成员结束后汇总报告和异常给主管；等待超时先返回全部成员状态和已有结果，不取消子工作，主管决定继续等或核实后补做剩余工作。普通用户确认、选择与输入沿用 Pi 原生交互，经主管协作通道呈现，宿主直接关联答复并恢复发起请求的工具；父委派保持等待，不需要主管模型返回后才能呈现。确需主管调整工作时，专业 Agent 提交本轮阻断结果并停稳；待当前步骤全部结束或超时返回后，主管处理原因并接续原专业 Session，不重复创建工作。多个专业 Session 可以在当前步骤并行工作，各自的结果和未解决请求必须分别保留。
主管的等待只存在于它自己的回合内。回合已经结束（等待超时、技术中止或模型失败）而成员随后提交结果时，宿主为主管补一次回合，把该步骤的结果与状态交给它；同一已停稳步骤只补一次，主管仍在运行或 Task 已不在运行状态时不补。补回合只让主管继续决定，不推进阶段、不判定完成。

设计成果与实现成果都由独立审阅 Session 检查。审阅、测试不读取作者或主管聊天中的自评，依据目标、正式需求、计划、实际成果和真实证据判断。可以使用相同模型，用户能看到实际配置；工作独立性必须保留。

同一份工作成果不同时交给多个 Agent 相互覆盖。主管可以并行组织只读调查；写工作也可以在同一 Task 内按模块并行，由主管为每个成员声明写入范围，存在范围重叠时明确告警并由主管决定。多个成果组合后，要检查最终组合，不能只汇总各自“通过”的报告。并行多个 Task 各用独立工作目录属于后续版本，首版不提供。

同一任务可以在同一阶段安排多个独立审核，分别保留结果。标准代码工作在本轮审核完成、必要问题处理并复审后，才进入测试；审核与测试不能作为同一阶段同时启动。

## D-04 适用工作如何完成

主管显式记录当前工作阶段；精确阶段值引用 [工具契约 G2](../../technicalnew/agents-and-tools.md#g2-模型工具)，不另立状态枚举。每次阶段切换前，主管显式更新 Task，记录上一阶段结果并进入当前适用阶段；实施、审核、测试与结算不能用一个 Session 的结束代替。主管与独立 Agent 判断授权含义、目标满足、问题处理、文档完整和适用责任；程序核对身份、状态、必要报告、实际交付与真实保存，不解析自然语言建立业务门禁，也不根据报告到达自动推进阶段。

| 工作场景 | 完成过程 | 适用条件 |
|---|---|---|
| 专业分析 | 简短安排 → 专业调查/分析 → 核对并保存结论、来源与未知 → 结束 | 只读辅助讨论，不修改正式知识或代码；不强制独立 Review/Test、结算或 Git 提交 |
| 标准代码工作 | 明确需求 → 计划 → 工程实施 → 独立审核 → 独立测试 → 结算 | 改变代码行为，包括业务、数据、接口、权限或交互语义 |
| 轻量修改 | 简短计划 → 适合的工程师修改 → 独立检查 → 结算 | 单一文案、纯样式、确定展示；不改变上述行为 |
| 设计与正式文档 | 工作计划 → 设计 Agent 分析/编写 → 独立审阅 → 结算 | 交付产品、需求与适用技术设计，或维护正式文档，不改变可执行代码 |

独立检查仍需执行与变化相称的内容、引用或实际检查。轻量和文档工作不强制额外建立测试职责，也不伪造测试报告。标准工作必须有独立测试；开发自己的检查是实施证据，不能替代。

一个按钮改变业务操作，即使只改少量内容，也采用标准工作。范围变大时补齐适用要求；不能因为想快速结束而删掉必需责任。

## D-05 审核、测试与返工

**独立验收优先验证端到端集成/E2E，单元测试属于开发 Agent 的内置责任。** 这是验证用户结果的优先级，不改变开发 → Review → Test 的顺序。

开发 Agent 对新增或修复的代码行为采用测试驱动开发（TDD）：先用有意义的单元测试复现目标行为或缺陷，再实现使其通过，重构后保持通过。单元测试保障开发方法和局部实现正确，在开发阶段完成，不交给测试 Agent 补做后才算实施完成。已有适用用例可以复用；纯文档、文案或样式不机械增加没有行为价值的单元测试。

测试 Agent 的主要责任是独立验证真实入口到最终结果：API 工作通过运行中的服务执行接口集成测试，检查响应及适用的存储/业务效果；UI 工作通过真实浏览器操作执行 E2E，检查交互、实际状态和用户可见结果。按本次需求覆盖正常、关键异常与相关回归，不为测试数量重复证明。开发 Agent 可以自行运行集成/E2E，但自己的通过记录不能代替独立 Test。

### 开发自查与独立 Test 的范围

开发阶段的自查按本次变更面收敛，不默认跑全量测试或整套浏览器 E2E：

- 后端行为改动：围绕被改函数、接口及直接契约边界运行定向单元/集成测试，证明本次行为与关键异常正确。
- 页面行为改动：仍先用单元测试复现并覆盖被改代码行为；再用一次聚焦真实浏览器路径验证被改交互和可见结果，不为一个局部页改动重跑全部页面。
- 全量套件或跨模块回归只在共享契约、数据迁移、权限/状态机、公共基础层或已知高风险改动时使用，并在报告中说明原因。

独立 Test 仍在 Review 后按本次验收和风险独立执行，不因开发自查收敛而省略；它负责覆盖变化的端到端结果和相关回归，而不是重复开发已经证明的局部单元。未运行的范围如实记录。

单元测试、Mock 或孤立组件通过不能证明端到端通过。未实际运行的链路、替代依赖和未覆盖边界明确说明；必要环境缺失时报告 blocked/not_run，由主管处理，不能降级为“单元测试通过，所以验收通过”。适用责任仍按 D-04 判断。

### 反证与检查器自检

测试和审核不能只证明“当前实现符合当前样例”。每个检查都要说明**期望值从哪里来**：正式需求、验收、独立事实或不变量；不能把实现输出、当前夹具或作者的假设抄成期望值。会随数据变化的规则用关系断言（集合包含、范围、唯一性、引用子集等），不把某一份盘、某一个 ID 或某一年的字面值当成产品规则。

标准代码工作的独立 Test 至少包含一个**负向控制**：已知错误输入、错误期望或实现变异（mutation）必须被检查拒绝；检查器或审计脚本还必须用一份已知坏样本自检。负向控制“按预期失败”才算通过；如果坏样本反而通过，说明测试或检查器本身有问题，Test 不得报告通过。无法构造反例时说明原因并保留为未覆盖或阻断，由主管决定，不得用全绿掩盖。

开发 TDD 的 red→green 证据、Test 的失败样本/检查器自检、Review 对期望值和负向控制的检查，都是本轮证据。只报“N/N 通过”不足以证明检查有效。

审核结果说明实际检查目标、问题位置、证据、影响，以及是否阻止完成。测试结果说明真实执行步骤、环境、观察、通过/失败，以及没有覆盖的部分。用户能够打开相应报告和证据。

实际失败或当前验收不满足，主管组织范围内修复，修复后重新独立审核，再执行适用测试。旧报告作为历史保留，不能用于证明已经改变的成果。

没有执行的检查明确为未执行或未覆盖，环境阻断明确说明原因和下一步，不能写“应该通过”。非阻断覆盖缺口需要用户明确处置并保留风险；真实缺陷不能被改写成未覆盖，重大问题未解决不能完成。

审核提出的新产品方向交用户决定；一般优化建议不自动扩大当前任务。用户接受某项建议后，按影响更新目标和计划，再执行适用检查。

## D-06 可见进展、持续工作与用户控制

任务详情至少显示目标、固定保存的总体 Plan、主管记录的当前阶段、参与 Session 与角色、已提交结果、需要处理的事项、下一步，以及实际成果和报告入口。收到专业结果后及时保存进展，阶段切换由主管显式记录，不要求用户手工维护每个小步骤。

用户能辨认以下情况：

- 正在推进：计划、实施或验证正在进行。
- 等待处理：缺模型、产品决定、结果、检查环境或实际影响核实，并说明需要谁做什么。
- 已暂停：停止继续实施，已有成果保留，用户可以继续。
- 正在结算：成果正在进入项目知识、摘要和归档，尚未满足最终完成要求。
- 已完成：适用验证、结算和成果保存均已核对。
- 已取消：执行已停止，已产生的影响和取消原因保留。

关闭浏览器、断线或切换项目不停止任务。总体 Plan、阶段结果、专业 Session 关联、交互请求及其解决情况、已知执行结果持续保存；再次打开看到原进展，不重发启动指令。工作台重新启动后，恢复 Task、Session 历史和已知成果，核实后继续剩余工作，已知成功阶段不重做。首版不恢复原工具执行栈，不自动重放未知操作；丢失的原等待调用通过新续办工作接续，不能宣称原操作已重新执行或完成。

同步委派期间，专业工作可以继续推进。用户请求沿用 Pi 原生确认、选择或输入语义，经主管协作入口呈现，不要求主管模型逐个登记或呈现。用户答复由宿主关联并直接解除原请求等待，不能排在正在等待的普通输入后；恢复原扩展/工具和专业 Session，需要模型判断的内容通过实际执行结果返回。当前任务的状态询问和补充信息保留，其他话题使用新的主管 Session。

用户主动暂停或取消后，先显示请求已收到；确认实际执行停止，才显示已暂停或已取消。取消不自动撤销已经产生的文件或外部影响。继续暂停任务需要用户明确操作，沿原工作核实后接续，不另建相同目标。等待超时不等于任务暂停；技术异常停止的子工作核实后可以补做剩余部分，用户主动暂停/取消不能自动重启。

无法确定操作是否生效时，保留已有成果并展示具体待核实事项。再次说“继续”不足以消除未知；主管组织核实或请用户确认具体事实后，再决定后续行动，不能盲目重复操作。

## D-07 结算与最终交付

只读 Task 按 D-04 在工作台保存结果并核对实际停稳后收口。下述结算适用于设计、实施与正式文档修改。

**结算把一次工作变成项目可以继续使用的成果。** 它在适用验证通过后进行，按实际影响核对下表：

| 核对内容 | 结算后用户得到什么 |
|---|---|
| 实际改变与验收 | 完成范围、执行过的检查、未覆盖与证据 |
| 产品/技术知识 | 受影响模块的当前实现、验证状态与差距 |
| 代码、测试和文档入口 | 可以找到实际成果、检查入口及相关依据 |
| 关联提案/需求 | 设计工作保存提案处理结论、需求与文档依据；实现工作保存完成摘要、实际成果、验证和剩余问题 |
| 任务历史 | 一份总体 Plan 及其修订、阶段结果、实施说明、审核、适用测试和结算记录 |
| 尚未解决事项 | 明确的问题、影响、处置或后续候选工作 |
| 成果保存 | 实际保存位置，以及本机保存或版本提交的真实结果 |

只更新受影响的知识；无影响的位置可以记录已检查，无需重写整个项目。详细过程放在任务记录，稳定事实放在权威知识，不把完整聊天复制成项目概况。具体组织见 [项目知识](project-knowledge.md)。

有 Git 的项目提交本次实际成果和交付记录，保留无关改动；遇到冲突或无关暂存内容，说明阻断并保留现场，不能覆盖、丢弃或顺带提交。**提交是收口条件**：被独立复核覆盖的交付文件在项目里仍未提交（含被 `.gitignore` 排除、或位于项目内嵌的另一个仓库里）时，任务不能结束，结束被拒绝并把未提交文件与所需动作返回给主管，由主管或结算角色完成提交后再收口。没有 Git 的项目仍保存同样的项目文件，明确标记本机保存；初始化 Git 由用户另行决定。

设计 Task 完成只表示本次设计产出已确认、审阅和结算，不表示实施需求已实现。实现结算时，主管依据需求范围与验收、真实 Review/Test 明确组织保存需求完成内容及状态，将该文件和报告纳入本次成果保存，再核对 Task 最终收口；保存与最终核对的可见结果引用 R-05。

完成条件：计划和授权有效、适用专业成果及独立验证有效、阻断问题已处理、结算更新完成、成果与归档已保存、相关提案/需求结果能够核对。缺项列明原因和下一步，任务保持未完成，修复保存问题不重做没有变化的已验证成果。

最终报告必须提供实际改变、验证结果、知识和交付记录位置、保存情况、未覆盖与剩余问题。不能只回复一句“完成了”。需求摘要已写出但最终收口中断时，显示完成记录待核对，沿已有成果收口。

## D-08 目标与成果变化后如何继续

已确认的新行为定义和文档归属在独立验证前写清，随实际成果检查。结算只回填已确认事实，不能在检查通过后偷偷改变目标、规则或代码。

验证后成果或依据发生实质改变，重新检查受影响部分；进度保留，旧结果不能证明新成果。多个修改组合也按最终目标检查。用户看到变更原因与当前有效结果。

已完成任务后的新改变形成关联新工作，保留上次交付，不把历史报告改写成新任务成果。

## D-09 设计工作的交付

用户可以单独委托设计，也可要求从已有依据补齐设计；主管判断当前缺口，组织一个或多个独立设计 Session。统一设计角色负责产品分析和适用技术设计，不要求每个模块分别运行两种角色，也不让一个 Session 默认加载整个项目。

设计 Agent 先理解用户问题、现有能力、限制与未知，明确产品目标、范围、行为与验收，再按内聚边界维护模块文档、形成实施需求；检查既有技术依据，只有未解决的实现问题才补充设计。涉及新架构、职责/状态归属、接口、跨模块依赖等问题时，明确必要契约与异常处理。已有依据充分则引用，不为每条需求强制新建技术文档。

产品文档回答用户行为与验收，技术文档回答职责与实现约束，实施需求描述本次交付变化，索引负责导航；共享事实只定义一次。

技术设计面向独立 Agent 实施。需要整体设计时用总体架构、必要链路子图和具有单一权威定义的契约串联，局部工作复用已有依据；明确组件职责、状态权威、输入输出、同步/异步边界、结果与关键异常。涉及持久化或恢复时，说明提交、等待、停止、重复与未知如何处理，不能只写“支持恢复”或“保证一致性”。图、字段、状态和示例一致，让开发者知道调用谁、传什么、写在哪里、失败如何继续，不自行补关键架构。优先采用已选框架原生能力，仅补项目必要职责，不把参考项目专用机制强制套入其他项目。

主管负责本次工作的总体 Plan，设计成果供后续实现制定自己的 Plan，不预先派发全部实现 Session。

设计交付物始终是一份整体，不能只交文档、只交需求或只交技术依据。每一次正式设计交付至少包含：

- 受影响的权威产品文档（新增或修订的模块正文与索引导航）；
- 分析得出的实施需求：可交付目标形成一条多条实施需求，尚待规划的部分保留或新建提案；
- 本次必须补充的技术依据（已有依据充分时明确引用，不新建）；
- 来源与覆盖说明：哪些目标已形成需求、哪些仍待用户决定、哪些被合并或明确不做。

交付前逐项核对上面的清单；缺失项要么补齐，要么明确说明为什么本次不需要，不能默认省略。实施需求与提案一律通过 requirement(op=save) 保存，不能只在报告或聊天里写出一份“需求整理结果”。

独立审阅检查目标覆盖、模块内聚、需求可验收、产品与技术一致、引用有效及未决问题是否阻止实施；不能只检查文档格式，也不能只看文档是否存在而不看需求是否真的形成。新产品决定经用户确认，已有决定不重复审批。设计结算保存正式依据、来源关系、需求与导航、已知缺口和审阅记录。未实现功能仍明确为待实现。

完成判据：后续独立实施 Session 按索引和选定需求即可找到足够依据，不需要设计聊天，也不必自行创造尚未规定的产品行为或关键契约。遇到目标需要重新划分，按 [返回设计](requirements.md#r-08-plan-发现无法实施时返回设计) 处理。
