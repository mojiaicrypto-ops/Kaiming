# 项目知识

## 用户目标与模块边界

用户和新会话能够知道项目当前做什么、已经做到哪里、相关依据和代码在哪里、还有什么未知，并在此基础上继续工作。

项目知识保存当前权威事实。需求提案保存意图，实施需求保存待交付改变，任务记录保存设计或实现过程，聊天保存讨论。需求规范见 [需求管理](requirements.md)，结算完成要求见 [任务交付](delivery.md)。

## K-01 项目记忆应该回答什么

项目概况说明定位、能力、当前进展、下一步和未知。产品模块说明完整用户行为与验收；技术模块说明对应职责、约束和实际设计；代码和测试入口帮助找到实现与检查；需求和交付记录用于理解改变及其证据。

“设计上要求这样”“代码已经存在”“实际验证通过”分别表达。没有观察或检查证据时明确未知；分析建议和聊天结论未经确认，不变成用户承诺或已实现事实。

工作台能展示和导航这些资料；新会话能够读取，无需依赖上一段完整聊天。初始化行为由 [项目工作区](project-workspace.md) 定义。

## K-02 固定文档职责，内容按项目组织

用户项目采用以下知识入口与目录职责：

| 位置 | 保存什么 | 使用时机 |
|---|---|---|
| 根 AGENTS.md | 项目协作入口、补充规则和参数 | 开始协作及适用规则变化 |
| `.dev/INDEX.md` | 知识导航、职责和何时读取 | 选择本次依据 |
| `.dev/PROJECT.md` | 项目定位、能力、进展与未知 | 新会话理解项目 |
| `.dev/product/` | 按用户能力内聚的产品模块及索引 | 讨论行为、需求、验收 |
| `.dev/technical/` | 按职责组织的设计与实现知识及索引 | 规划、实施、审核 |
| `.dev/maps/code.md`、`.dev/maps/tests.md` | 代码职责、入口、检查命令与覆盖 | 定位实现和实际验证 |
| `.dev/rules/` | 项目特有的补充协作规则及索引 | 触发相关工作时读取 |
| `.dev/requirements/` | 可区分需求提案与实施需求的独立 Markdown、格式及查询入口 | 规划提案、选择实施需求、追溯来源与交付 |
| `.dev/work/` | 每项 Task 的总体 Plan（固定为 `<taskId>/plan.md`）、阶段结果、报告与证据 | 推进、检查、结算和接续 |
| `.dev/issues.md` | 尚未解决的问题、影响与后续处置 | 继续工作与风险讨论 |

首次只建立真实可用的入口。模块、地图、问题和任务记录在需要时形成，没有调查的内容写未知，不填假链接。目录职责固定，模块名称和拆分粒度由 Agent 依项目自主决定。

固定位置是导航入口和新知识的默认位置。既有权威正文位于项目其他目录时，保留原正文并通过固定索引引用，后续维护这一份；迁移须展示差异并经用户确认，同时更新引用，不能复制出第二份权威正文。

索引记录路径、职责和读取时机，不复制正文。正式知识新增、移动或拆分后更新相应导航；需求按固定目录由列表发现，不逐条维护实时索引或状态。

## K-03 模块化、内聚与一份事实来源

写正式文档前，先查已有概况和相关索引，选择权威归属。产品按独立用户能力组织，技术知识按明确职责组织；具有独立变化、验收或依赖的内容再拆分，共用事实集中定义并引用。

例如，密码重置和登录属于账号访问能力，需求引用账号模块；不能因为分别有前端和后端工作，就再写两份完整的账号产品定义。实现职责可以分别说明，产品事实保持完整。

模块是长期能力与知识边界，不等于一次实施需求。一个模块可以关联多条需求，一个实施需求也可引用多个必要模块；按交付目标决定，不按文件数或工程角色机械拆分。

统一设计 Agent 可以同时维护产品与技术文档，但两类职责分开：产品说明用户目标、正常与异常行为、范围和验收；技术说明适用职责、契约、依赖和实现约束。已有技术依据充分时引用，不强制为每个模块或需求另写架构文档。

每个模块至少让读者找到职责与边界、行为或约束、验收或依赖、未知，以及当前实现与验证事实。内容可以自主组织，行为定义与实际状态明确分开。

实施需求按可分别交付和验收的目标拆分，模块按长期能力内聚；工程步骤、角色数量、文件数量和难度不能替代拆分依据。独立工作应能通过索引和选定依据理解目标，不必读完整项目或设计聊天；共享规则与接口集中定义，不交给各开发 Session 分别创造。

资料冲突、引用缺失或权威位置不清时，先调查并提出处理建议。已有项目规则、用户决定和共同约束不能在拆分时丢失；新的规则和产品选择由用户确认。

## K-04 Agent 如何使用这些知识

主管先通过概况和索引选择本次相关依据，给专业 Agent 目标、范围、规则与需求/计划路径、依赖、未知和期待成果。专业 Agent 获得自身角色、基础规则及任务说明后，可以自主补读和调查。

总体 Plan 由主管制定，固定保存为这项 Task 的共同依据。子 Session 的内部计划由其自主决定，也可直接完成简单工作；不强制将内部计划另存文件或逐份审批。专业结果、阶段事实和必要交互记录仍按实际交付要求保存，接续不依赖主管记住聊天。

不默认把整个项目、全部历史或其他 Agent 聊天交给每个角色。需要大量或有重要风险的工作，主管先简述准备使用的依据、理由和未知，用户能够纠正；这不是要求用户逐项批准上下文清单。

审核与测试使用正式依据、实际成果和真实证据，独立于开发聊天和自评。参与角色实际使用的依据与配置在交付记录中可追溯。新决定或成果变化时，检查使用当前有效材料。

## K-05 随交付维护当前事实

设计结算保存经确认与独立审阅的产品、技术依据、实施需求和来源关系；清楚区分待实现、观察到的代码和实际已验证行为，不将设计成果写成实现事实。设计交付应让后续独立 Session 无须读取设计聊天即可工作。

新行为和范围的正式定义在实施前明确，依据不足时返回设计。结算核对实际改变，将已经验证的成果回填到受影响知识、代码和测试入口、需求摘要和遗留问题；没有影响的内容不重复重写。

完整完成清单以 [结算要求](delivery.md) 为准。某项资料更新失败，显示缺项，保留已有成果继续补齐，不能以聊天总结代替。

新会话从入口能定位刚完成能力、实际代码、执行过的验证与差距，是结算成功的产品判据。仅保存一份历史报告而留下过期项目知识，不能算完整交付。

## K-06 项目规则与复盘

工作台内置基础协作规则；项目文件保存补充约束和已确定参数，例如计划如何确认。主管和专业 Agent 在对应工作前使用适用规则，不依赖用户每次重述。

默认每完成五项正式工作，以及发生漏检事故后，在下一次活跃协作中提出复盘：检查是否有效、哪里过重或遗漏、建议具体改变什么。用户可以在项目中选择其他节奏。

改进建议先给用户看具体差异及影响；同意后维护项目规则和入口，未同意保留建议，不改变生效规则。复盘不需要定时唤醒，也不要求用户额外主持一场固定会议。

## K-07 历史、迁移与后续工作

当前知识保持最新事实，详细历史放在需求摘要和任务交付记录，通过引用追溯。已完成工作后有新改变，保存关联新需求或任务，不覆盖历史交付。

项目文件能够随目录或版本管理一起保存、复制和迁移；项目知识、需求和项目内报告在另一环境仍可阅读。本环境会话、权限或未迁移的详细执行记录不能假设也存在，缺失明确说明。

不自动删除知识、需求和交付证据。用户清理已结束会话时，保留仍被有效工作或证据引用的资料，不破坏当前项目事实和可追溯性。
