# 主管对话

## 用户目标与模块边界

用户围绕项目持续讨论，获得分析、建议和协作结果，必要时让主管组织其他 Agent。主管是用户的主对话伙伴和协作组织者，职责贯穿讨论、需求、实施与反馈，不限于开发管理。

本模块负责沟通、意图和决定。需求保存由 [需求管理](requirements.md) 定义，正式工作的完成要求由 [任务交付](delivery.md) 定义。

## C-01 自由讨论与自主调查

用户可以提出想法、询问现状、要求分析、讨论方案或让主管整理表达。主管根据当前问题直接回答，按需读取项目资料或组织专业分析，不要求先有需求文件或开发任务，也不要求每次调用所有角色。主管自行回答不创建 Task；委派专业分析时采用 [分析工作](delivery.md#d-04-适用工作如何完成)，所有专业 Session 都绑定 Task。

主管区分当前事实、用户已确定的选择、候选建议和未知。分析报告或讨论结论可以作为对话成果，不能未经明确保存就宣称已经成为正式项目知识。

只讨论、只分析或只给方案，不自动写需求、修改产品范围或开始开发。调查发现额外需求时，先向用户提出。需要改变已有产品决定时，提供具体影响和可选择的处理办法。

## C-02 创建、选择与接续会话

一个主管 Session 只属于一个项目，同一时刻只推进一项未结束 Task；等待、暂停或结算中的任务仍占用这项工作。用户可创建多个主管 Session，分别处理其他话题或目标。当前任务完成、实际取消或安全交接给另一主管 Session 后，原主管 Session 可以承接下一项工作；选择既有会话时看到它自己的历史，不用“最近一次会话”替代。

新会话先从项目概况和索引了解当前事实，再按用户目标阅读相关知识；不会默认加载整个项目和其他会话聊天。主管说明相关依据、未知和接下来准备做什么，用户能够指出误解。

用户可以从未完成任务返回它的主管会话。原会话不可继续时，可选择没有其他未结束 Task 的新主管 Session 接续；已知目标、总体 Plan、决定、成果、专业 Session、交互请求、阻断和下一步保留。先确认仍在执行的工作或不确定影响，再交接继续，不能让两个主管 Session 重复实施同一 Task，也不能重复创建已有专业 Session。

新会话可以了解已有成果，但不能把旧聊天当作新的执行授权。历史需求与新工作的关系见 [需求管理](requirements.md)。

## C-03 让用户看懂回复与工作过程

用户能够区分主管回复、专业结果、实际操作结果和正式任务进展。主管汇总时给出依据和成果位置，不用自己的判断代替独立审核或测试报告。

“指令已收到”“正在处理”“等待用户”“操作成功/失败”和“正式交付完成”分别说明。模型回复结束或某个操作成功，不显示为整项任务完成。

用户能够查看参与角色、主要工作说明和专业结果，按需展开详细报告或证据。查看过程不会改变成果或工作状态。

## C-04 从对话进入需求或任务

“整理需求”“分析是否值得做”先在对话中给出结果；“保存为需求”“加入需求队列”保存提案，已有充分内容时可直接保存实施需求；“帮我设计”“形成正式方案”进入设计工作；“实现”“开始修改”进入实现流程。主管理解目标并按规则组织，不要求用户使用固定命令格式。

意图确实不明确时，主管给出简短澄清。明确保存或实施已有授权时，不反复要求用户确认同一操作。范围内整理和修复可自主推进；新增目标、范围、规则和重要风险接受由用户决定。

主管根据目标与已有事实判断需要设计还是可以实施，自主决定专业 Session 和上下文，用户不必手动派发。只委托设计就交付设计，不自动开发；明确给出开发目标时，补齐必要依据后沿有效授权推进，不要求先保存再重新启动。宽泛目标需先形成实施需求，不能用“用户说实现”替代设计依据。

## C-05 用户决定与原生交互

需要用户决定时，主管或专业 Agent 说明正在处理的事情、待决定内容、影响和适用选项。用户可以确认、拒绝、选择或输入文字；已有授权不重复询问，未答复不视为同意，拒绝后不执行原待授权动作。

所有确认、选择与输入沿用 Pi 的原生交互语义，不另建 Plan、需求、范围等业务确认类型，也不要求模型调用一套请求登记、呈现、解决或失效操作。业务含义由问题内容表达，具体入口及适配属于技术实现。

专业 Session 的请求经过主管协作通道统一呈现，用户能看清来源及关联工作；不要求用户另行订阅子 Session，也不绕过主管协作入口。主管可以理解和解释问题，但请求转发、答复关联、等待解除及保存恢复由宿主完成，不依赖主管模型逐个调用呈现工具或再确认一次。

原生答复返回发起交互的扩展或工具，恢复对应等待；需要模型判断时由实际执行结果携带答复，不假定 Pi 自动把答复追加为普通用户消息。用户文字答复明确对应某个请求时，宿主将其接入原请求；不能猜测文字对应多个待处理问题中的哪一个。普通对话不是未解决原生请求的替代响应。

答复不排在正在等待的普通输入后。解决后继续原专业 Session 和原工作，不重复创建；多个请求分别关联，重复答复不重复执行。待决定内容变化后，旧请求不再继续原动作，旧答复不能授权新内容。提交选择先显示答复已收到，实际执行结果单独报告。

未答复保留等待与已有成果；断线后可找回原请求和已知答复。任务停止或请求取消后不得继续原动作；无需把底层请求状态维护交给模型。当前 Task 中不依赖该答复的工作可以按已有授权推进，其他话题使用新的主管 Session。

## C-06 工作进行中的沟通

任务进行中，用户可以查看进展、问状态或提供补充信息；其他想法和目标在新的主管 Session 中讨论。主管说明当前任务相关消息如何处理，用户看到消息已经收到；针对具体交互请求的答复直接解决该请求，不排在普通输入后等待。

普通状态询问不暂停、取消或重建任务。影响当前目标的补充由主管核对范围后处理，已有成果和决定不被新问答覆盖。用户要停止当前工作时，使用明确的暂停或取消意图，按 [任务控制](delivery.md) 执行。
