# 外部 Agent 接入（MCP）

## 用户目标与模块边界

用户不一定总在浏览器里。他常常正在用 Codex、Claude Code、Grok 这类编码 Agent 干活，希望让这些 Agent 把一项工作交给工作台：说清目标，看到阶段进展，回答主管提出的问题，拿回真实成果（报告、Plan、改动），必要时取消。

本模块定义这条**第二接入面**。它是同一台工作台的另一个入口；除 X-02 声明的一处例外，不改变浏览器工作流的既有规则：Task 仍分只读与修改，仍要独立 Review、适用 Test 和结算，授权与完成判断仍按 [任务交付](delivery.md) 执行。

本模块不负责：
- 不新增业务工作流、策略层或第二套权限系统。外部 Agent 在产品语义里**就是一个用户**（见 X-03）。
- 不把专业 Session 暴露成独立会话。一次委派在外部看来是一件工作，在内部仍由主管组织设计、开发、审核、测试、结算。
- 不新做一个界面。外部 Agent 的会话与工作，在浏览器里同样可见、可操作。

## X-01 以标准 MCP 服务接入同一工作台

工作台提供 MCP 服务，供编码 Agent 调用。两种连接方式并存：

| 连接 | 用在什么时候 | 用户需要做的 |
|---|---|---|
| 本地 stdio | 客户端把工作台作为子进程拉起（Codex、Claude Code、Grok 都支持） | 在客户端的 MCP 配置里写一条命令与环境变量 |
| 常驻 HTTP 端点 | 多个调用方、或另一台机器上的服务远程调用 | 配置地址与访问口令 |

两种连接使用**同一个 Server、同一份项目与会话数据**；同一部署仍然只有一个 Server、一个数据库。机器调用方使用与浏览器相同的访问口令，未认证的请求被拒绝并说明原因，不因为来自本机就放行。

外部 Agent 能做的事：查看已登记项目与需求列表、查看该项目最近的工作、委派一项工作、查询与等待进展、回答主管的问题、补充指令、取消、读取报告与 Plan。它看不到、也不接受任意路径——所有读取都经过项目归属检查。

## X-02 每个项目一条固定会话

外部 Agent 的委派**不新建会话**：每个项目有一条固定的主管会话，专供外部接入使用。第一次委派时创建，之后一直复用，因此上下文连续——同一项目的约定、上一次工作的结论、已知的失败与决定都还在，用户不必每次重新交代。
这是对 [主管对话](chief-conversation.md) 与 [任务交付](delivery.md) 里「其他话题在新的主管 Session 中处理」的**一处有意例外**：外部调用方无法选择会话，按话题新建会话会切断上下文连续性；因此同一项目的委派一律进入这条固定会话——前一项未结束时排队，而不是新开主管会话。

- 这条会话在浏览器里就是一个普通的主管会话：能看到它的历史、参与角色、Task 与报告；用户可以给它改名，**名字只影响显示**，不改这条会话的身份与归属。
- 一个主管会话同时只推进一项未结束 Task（与 [主管对话](chief-conversation.md) 同一条规则）。同一项目里前一项工作还没结束时，新的委派**排在后面**，并如实说明挡在前面的那一项；不同项目互不影响。
- 排在前面的工作卡住（等待决定、暂停或长时间无进展）时，后续委派一直排队。外部 Agent 可以取消它或补充指令，工作台**不会自动取消**——那是替用户做决定。
- 用户清理这条会话时（沿用既有清理规则：没有未结束工作、也没有被 Task 或成果引用），外部接入随之"忘掉"此前上下文：下一次委派按固定规则重建一条并说明；用旧运行标识查询时回答"查不到这次运行"，不假装成新的一轮。会话被引用时清理会被拒绝：会话保留并说明原因；若仍有未结束 Task，新委派继续排在那项工作后面，否则照常执行。

## X-03 委派就是一次用户输入

外部 Agent 提交的目标就是一条用户输入。主管按既有规则判断这是讨论、只读调查还是修改交付，决定 Task 类型、阶段和是否需要提问；程序**不因为来源是 Agent** 就加门禁，也**不因为来源是机器**就放宽核对。

- 委派里可以给出模式（评审、实施、测试）、验收、范围与是否要求测试。这些是给主管的明确指令，不是程序强制的类型约束：Task 类型仍由主管按 [D-04](delivery.md#d-04-适用工作如何完成) 判断，程序不从自然语言推断。
- 授权引用就是这次委派输入本身；不需要外部 Agent 另外构造审批对象，也不存在"机器专用授权"。
- 需要变更目标、范围、验收或项目规则时，仍由用户决定：这类问题按 X-05 出现在查询结果里，可以由外部 Agent 显式答复（与浏览器作答同一条路径）；外部 Agent 不能在未被提问时自行变更这些内容。

## X-04 结果、进度与权威事实

一次委派返回一个**运行标识**，之后可以随时按它查询。查询结果至少包含：

- 状态：进行中、排队中、等待用户答复、已暂停、执行情况未知（待核实）、已完成、已失败、已取消；「已暂停」与「执行情况未知」都要说明需要谁做什么，外部 Agent 只能补充指令或取消，不能自行恢复或当成已完成；
- 阶段清单：已经走过的阶段与轮次（同一阶段返工即新的一轮）、当前进行中的阶段、以及**计划内尚未开始的阶段**——与浏览器任务清单同一套推导，不能出现两处说法不一致；
- 成员：每个阶段由哪些角色承担、是否已交出正式结果、是否有未通过的报告；
- 最近一条工作说明，以及主管当前是否在等用户答复。

宿主支持时，阶段推进与成员结束可以作为进度通知推送；不支持时，查询与等待接口照样给出同一份事实。等待接口在有变化或到达本次等待上限时返回当前状态，单次调用不阻塞到整项工作结束；调用方可以按运行标识继续等待。

**权威事实是 Task 记录、总体 Plan 与正式报告**，不是聊天记忆。长期使用的固定会话会被工作台压缩上下文，早期的对话内容可能只剩摘要；外部 Agent 要判断"做完了没、做了什么"，必须看报告与 Plan，并可以读取最近对话与项目文件作为补充。

## X-05 提问与答复

主管需要用户决定时（确认、选择、补充信息），该问题出现在查询结果里，状态为"等待用户答复"。外部 Agent 显式答复后，工作原样继续，与用户在浏览器里作答走同一条路径。

- 客户端具备交互界面时，可以就地弹出表单让用户选择，答复同样生效；用户拒绝或关闭表单**不算拒绝整项工作**，工作仍在等待答复。
- 工作台不自动替用户答复，也不因为超时替用户答复：没有答复就一直等待，直到被答复或取消。
- 问题、答复内容与答复来源都留档，用户在浏览器里能看到是谁答的。

## X-06 项目与需求列表

外部 Agent 在决定委派什么之前，可以先查看事实：

- **已登记项目**：项目标识、目录、目录是否仍存在、会话与任务数量、最后活动时间；只读，不读项目文件、不调用模型。
- **项目需求**：提案与实施需求、状态、标题、更新时间、能否正常读取；列表不隐藏非法文件，而是如实列为问题项；可以按标识读取单条需求的完整内容。

两个列表都只读。外部 Agent 不能通过它们修改需求或工作状态。

## X-07 取消、排队与接续

- 取消请求"已收到"与"实际已停止"要能区分（与 [主管对话](chief-conversation.md) 与 [任务交付](delivery.md) 一致）；取消不重写已有成果，也不假装自动回滚。
- 工作台重启或以新的进程继续运行时，运行标识仍可查询——状态来自持久记录，不来自内存。
- 已知成功的工作不重做，情况未知的工作不自动重放；断线后客户端按运行标识重新查询即可接上，不需要重新委派。

## X-08 信任边界

- **外部 Agent 的运行沙箱不约束工作台**。工作台在自己的运行环境里读写项目、执行命令；一个以只读沙箱运行的客户端，仍可能通过委派产生写入。用户要以"授权一个 Agent 在这个项目里干活"的标准来选择调用方。
- 外部 Agent 可以代表用户答复问题，但必须显式提交；答复入档可审计。工作台不会把"调用方的模型猜了一个答案"当成用户答复。
- 外部 Agent **不能绕过**产品既有的检查与结算：不能跳过独立 Review、必要 Test 或结算，也不能自己宣称完成。完成由程序核对事实。
- 访问口令与调用方凭证不进入工具结果、日志或对话记录。

## 失败与边界

| 情况 | 产品行为 |
|---|---|
| 没有可用模型 | 委派被接纳但排队，明确说明缺配置；已有项目、需求与历史照常可读 |
| 项目目录不可访问或已移动 | 说明原因，不创建会话、不伪造进展 |
| 未认证 / 口令错误 | 拒绝请求并说明需要认证，不来自本机就放行 |
| 同一项目已有未结束 Task | 新委派排队，指出挡在前面的那一项；不并行推进两项 |
| 固定会话被删除（仅限可清理的会话） | 下次委派重建并说明；旧运行标识回答"查不到这次运行"；被引用而无法清理时，会话保留并说明原因 |
| MCP 进程无法启动或附着工作台 | 连接失败并说明是哪一项不可用（数据库锁被另一个实例持有、端口不可用）；不静默改用另一个数据库或另起实例 |
| 客户端不支持就地交互（未声明 elicitation） | 问题留在查询结果里等待显式答复，工作不失败 |
| 客户端超时或断线 | 工作继续；用运行标识重新查询接上，不重复委派 |
| 委派调用在返回运行标识前超时或断线 | 不自动重复委派：先按该项目最近的工作核对是否已接纳，已接纳就按那个运行标识接上，未接纳再重新委派 |
| 工作台重启 | 运行标识仍然有效；未核实的执行结果标注为「执行情况未知」，该项目的新委派在此之前排队并说明原因，需用户在浏览器核实后才能继续；不自动重放 |

## 本模块验收

| 场景 | 必须观察到的结果 |
|---|---|
| 用 Codex 或 Claude Code 委派一次只读评审 | 客户端能列出可用能力；委派后拿到运行标识；阶段清单包含真实走过的阶段与计划内未开始的阶段；能读到真实报告；浏览器里同一条会话显示同一项 Task |
| 同一项目连续两次委派 | 两次落在同一条固定会话里，第二次看得到第一次的结论；第一次未结束时第二次如实排队并指出挡在前面的工作；在浏览器暂停第一项后，查询显示已暂停并说明需用户在浏览器继续，外部 Agent 的补充指令或取消都被接受，不能自行恢复；取消后如实停止 |
| 主管在委派中提问 | 有人值守时客户端能就地作答并继续；无人值守或用户关闭表单时不自动替答，问题一直挂在查询结果里，直到显式答复 |
| 重启、断线与删除固定会话 | 重启后运行标识仍能查到真实状态，未核实的结果标为「执行情况未知」且新委派排队并说明需核实；委派在返回运行标识前断线时，按该项目最近的工作核对后接上而不重复委派；在一个项目里先委派一个只需主管直接回答的问题（不建 Task；若仍建了 Task，改用只讨论的问题重试），确认固定会话未被引用后删除它，再重新委派：重建并说明，旧标识明确查不到；被报告引用而无法删除时说明原因并保留会话 |
| 未认证访问与只读列表 | 未认证请求被拒；项目与需求列表只读、不隐藏非法文件、改动不了任何状态 |

依据本页 X-01～X-08。完整可执行场景见 [产品验收](../acceptance.md)（AC-38～AC-42）。
