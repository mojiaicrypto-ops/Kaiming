# 待办与规格

## 用户目标与模块边界

用户把以后可能做的事记下来，在需要时交给 AI 设计或实现，并且能从项目中看出系统由哪些模块组成、现在在做什么、接下来做什么。用户不需要维护待办的格式或状态。

这个模块定义四样东西的分工，以及从不同起点开始工作的方式。具体内容由各自的模块承载：

- 待办：保存“以后可能做什么”，属于本模块；
- 规格与模块地图：保存“系统是什么、怎么切分”，属于[项目知识](project-knowledge.md)；
- Task：保存“这次改什么、改到哪、怎么验收”，属于[任务交付](delivery.md)。

## BL-01 四样东西各自负责什么

| 记录 | 回答的问题 | 位置 | 由谁维护 |
|---|---|---|---|
| 待办 | 以后可能做什么 | `.dev/backlog.md` | 用户（界面或编辑器）、主管、设计、结算 |
| 规格 | 系统应该是什么、实际做到了哪里 | `.dev/product/`、`.dev/technical/`；小项目可以只用 `.dev/PROJECT.md` | 设计、结算 |
| 模块地图 | 系统由哪些模块组成：职责、代码位置、规格和对外接口 | `.dev/PROJECT.md` 中的「模块」一节 | 设计提出，用户确认 |
| Task 契约 | 这一次改什么、改到哪、怎么判断做完 | Task 记录，加上 `.dev/work/<taskId>/plan.md` | 主管 |

一项行为只在规格中完整定义一次。待办和 Task 引用规格的文件与标题，不另写一份行为定义。

## BL-02 记录待办

以下情况可以新增待办：

- 用户明确说“记下来”“加到待办”“以后再做”时，由主管新增；
- 用户在项目页直接新增，或在编辑器里直接写进文件；
- 设计工作把产出的切片记为待办；
- 结算把遗留问题记为待办，并标明来源。

主管在讨论中发现的其他事项，先作为建议说出来，用户同意后才记。

新增只需要标题，正文写一两句话即可。记录待办不会启动设计或开发。

每条待办有：稳定编号、标题、状态（未完成 / 已完成 / 已放弃），以及可选的正文、规格引用、关闭说明。通过工具或界面新增时，编号、来源、操作者和时间自动记录。

## BL-03 待办文件可以直接编辑

待办文件是一份普通的项目文件，以文件内容为准。用户可以在编辑器里直接改；主管可以按原文修改其中的条目，用来修正、合并、拆分、改号或批量整理，每次修改后都会立即看到是否写坏。新增和关闭通常通过专门的操作或界面完成，因为它们会自动分配编号、记录来源，并要求写关闭说明。

直接编辑只需要遵守一条简单的约定：每条以“编号 + 标题”开头，写明状态，编号不重复。文件开头有一段说明，打开就能看到。

写得不合约定时，工作台的处理是：

- **一看就是写坏的**（缺少状态、状态不合法或写了两次、缺少编号、编号重复）：作为问题单独显示位置和原因；这一条不能被实施，也不能通过界面或专门的操作去关闭、修改，只能改它的原文来修复；其余条目照常；
- **写法不同但没有歧义**（中英文混用、放错分节、多写了其他内容）：照常读取，多出的内容原样保留；
- **格式合法但可能有误**（关闭了却没写说明、Task 关联的条目不见了、进行中的 Task 关联的条目被写坏）：显示警告或待核对提示，后者在项目页的“进行中”上直接标出，不必等到结算才发现；
- **整份文件一条都识别不出来**：明确提示“可能格式已被改动”，不会显示成“没有待办”。

工作台不替人猜测意图，也不自动修复。主管看到问题后可以直接修复；修复需要判断用户意图时（例如两条重复编号分不清哪条是哪条，或者被删的条目要不要恢复），先请用户决定。

修复重复编号时，已被 Task 关联或被其他条目引用的那一条保留原号，另一条改为新号。

## BL-04 项目页

工作台的「项目」页回答三个问题：现在在做什么、接下来做什么、系统由哪几块组成。页面依次显示：

1. **问题提示**：待办文件中有需要修复的地方时，显示数量，点击后在文件查看器中定位到对应行；
2. **进行中**：未结束的 Task、它们的当前步骤和关联的待办；**等待用户决定**的单独标出，并能直接跳到需要回答的问题；最近完成的一项；
3. **待办**：默认只显示未完成的条目，按有没有规格引用分成「就绪」和「想法」两组；已完成和已放弃的折叠在后面。“进行中”“待核对”根据关联 Task 的真实状态显示，不另外保存一份。可以直接新增；
4. **模块**：项目概况中「模块」一节的只读显示，代码位置和规格可以直接打开；
5. **早期文件**：项目中有早期需求文件时，显示一个入口。

待办详情显示：正文、规格引用（可以直接打开到对应位置）、来源、关联的 Task 及其真实状态、关闭说明。

页面直接从项目文件和工作记录生成，不需要模型也能读取。没有内容的区块折叠为一行或不显示，小项目看到的只有“进行中”和新增输入框。

模块的实现进度不在页面上汇总，点开规格即可查看。

## BL-05 规格

规格按长期能力（产品）和明确职责（技术）组织，规则见 [K-03](project-knowledge.md)。每个模块至少要让读者找到四样东西：

- 职责与边界；
- 每项行为的正常结果、异常处理和验收要点；
- 实现状态；
- 未知。

技术模块还要写清对外接口。被多个切片共同依赖的接口，要先写进规格，再开始实现。

每项行为用一个稳定的标题，供待办和 Task 引用。实现状态逐项区分“未实现 / 已实现（观察）/ 已实现 / 已验证”，并附上交付它的 Task；设计完成不能写成已实现；“已实现（观察）”只表示从已有代码中看到，不表示已经验证。

小项目可以不建独立的规格目录，在项目概况里用几段话说明行为即可；需要拆分时再拆，不预先建空模块。

## BL-06 模块地图与边界变化

项目概况中有一节「模块」，列出每个模块的职责、代码位置、规格和对外接口。小项目只有一行。

**新增模块、移动模块边界、改变对外接口，都是设计决定**：AI 提出方案和理由，由用户确认后才写入；未经确认，不能用实现结果改变边界。模块内部的组织方式和交付怎么切，由 AI 自行决定。

## BL-07 从待办或直接目标进入实现

用户说“实施 B-12”或直接给出开发目标时，主管先核对依据：

- 引用的规格已经足够写出可观察的验收：直接建实现 Task，验收从规格推出；
- 没有规格，但目标小而明确：主管在 Plan 里直接写验收，展示给用户后开工；结算时把新行为补进规格；
- 行为有待决定的取舍，或者目标宽泛（例如“做支付网关”）：先组织设计（BL-08）。

修改 Task 的 Plan 要写两节：

- **验收**：这是 Task 能够建立的前提。验收必须在开发之前写下，来自规格或用户确认，不能在实现之后按结果补写；没有验收的修改 Task 建不起来，检查项见 [G2 task](../../technicalnew/agents-and-tools.md)。
- **范围**：改哪个模块、哪些路径，依赖和提供哪些接口。程序把实际改动与这一节的差集列为越界文件，是否阻断由 Review 判断。

实施过程中，如果改变了验收，或者需要越出范围：

- 改变验收超出原授权的，按 [D-08](delivery.md) 由用户决定；
- 需要越出范围的，先修订 Plan；涉及模块边界的，按 BL-06 处理。

一条待办同一时间只能关联一个未结束的 Task；重复启动时返回已有进展。一个 Task 可以一并完成几条相关的小待办。

**按顺序实施多条**：用户说“按顺序实施 B-1～B-6”时，主管依次建立 Task，同一时间只有一个未结束，每个 Task 都完整经过计划、开发、审核、测试和结算。出现阻塞决定、返工后仍未通过的审核或测试、依赖尚未完成，或下一条待办有问题时，停下来等用户决定。

## BL-08 大功能的设计与切片确认

宽泛的目标先交给设计。设计的产出是：规格、先行定义的接口、需要的模块地图变化，以及切片清单（就绪待办）；来源覆盖说明随同一次交付一并给出（[D-09](delivery.md)）。

每个切片应该满足：

- 可以独立验收；
- 写入集中在一个模块内部；
- 依赖的接口已经写在规格里；
- 一次 Review 能看完。

切片清单有 2 条或更多时，开工前把清单交给用户确认一次。确认之后，原待办写明拆分去向并关闭；用户再逐条或按顺序实施。设计本身不会启动开发。

## BL-09 新项目的起步

**已有需求文档时**：

- 文档保持原样，作为设计的来源，不直接当作规格；用户明确表示以后维护这份文档时，它就是产品规格，设计只补技术部分；
- 主管先展示要建立的项目入口，用户确认后建立；
- 设计一次交付：模块地图、技术选型与总体架构、产品规格、必要的接口、切片清单，以及来源覆盖说明（文档的每一部分进了哪份规格、成为哪条待办、尚待决定或明确不做）；
- 模块地图、技术选型和切片清单都需要用户确认。技术栈是用户的决定，AI 提出方案和理由；
- 新项目的切片清单默认以“可运行的骨架”开始：能构建、能启动、有测试入口，并有一条确认会失败的自检；以“联调验收”结束：按来源文档中的关键用户路径跨模块走一遍；
- 之后每个切片单独实施。开发只读它负责的模块的规格、接口和计划，不读来源文档原文和设计聊天。

**只有想法时**：主管先在对话中把想法整理成目标、用户、关键路径和不做什么，展示给用户确认。确认后可以直接进入设计，整理结果就是设计的来源；也可以按用户的要求先记为一条待办。

## BL-10 已有代码的项目第一次接入

1. 先用一个只读任务调查现有能力、文档、代码入口，以及构建和测试方式；
2. 模块地图根据代码结构提出，用户确认后才写入。从代码中看到的结构不会自动成为确认的边界；
3. 规格按需补写：某个模块第一次要被修改时才补，已有行为标为“已实现（观察）”。不要求一次补全整个项目的规格。

## BL-11 完成、放弃与重开

- **完成**：实现 Task 的结算把它完成的待办标为已完成，并写明交付它的 Task。只完成一部分时，二选一并写明：要么保留原条目，要么关闭原条目、把剩余部分记成新待办。
- **取消 Task**：不会关闭待办。条目仍为未完成，并显示上一次的 Task 已取消（最近一次关联的 Task 从记录中派生）。
- **放弃**：用户明确放弃一件事时，标为已放弃，并写一句原因。放弃一条仍被未结束 Task 关联的待办前，先暂停或取消那项工作（[D-06](delivery.md)），不自动取消。
- **拆分与合并**：设计把一个大想法拆成多条待办后，原条目以“已拆为 B-x～B-y”关闭；合并时以“合并到 B-x”关闭。这两种关闭用状态「已放弃」并写明去向；只有真正交付完成才用「已完成」。旧需求的「已归档」没有对应状态：已交付的标已完成，内容作废的由用户放弃。
- **重开**：已关闭的条目可以重开，并写一句原因。关闭不会删除条目，正文和关闭说明都会保留。

## BL-12 Plan 发现依据不足时回到设计

在制定 Plan 或实施过程中，可能发现目标混杂、行为不清、验收写不出来，或者需要改动范围之外的模块。这时：

1. 主管停止相关的实现写入，在原 Task 内委派设计补齐规格或接口；
2. 涉及模块边界的，先请用户确认；
3. 修订 Plan 的验收和范围，然后继续。

如果只是工作量大，调整分工即可，不需要回到设计。

确实需要拆成不同交付目标时：新增相应的待办，原待办写明拆分去向；原 Task 安全取消，不能标为完成；新目标分别启动 Task，不与旧工作重复执行。

## BL-13 早期需求文件与问题记录

项目中已有的 `.dev/requirements/` 和 `.dev/issues.md` 都保留为普通历史文档。它们可以在文件查看器中阅读；工作台不解析其中的状态，也不会自动转换或删除。用户要求时，主管可以把其中未完成的内容整理成待办，并在待办里引用原文件。

新的遗留问题一律记为待办。如果需要区分风险，在标题前加“风险：”即可，不另设字段。
