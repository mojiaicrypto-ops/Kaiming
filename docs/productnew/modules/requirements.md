# 需求管理

## 用户目标与模块边界

用户保存尚待规划的意图，由 AI 组织设计，得到明确的实施需求，再选择实现并查看交付结果。用户不需要亲自拆需求或维护专业分工。

需求提案保存尚未规划的目标、问题与限制；实施需求保存一次可验收的改变；[项目知识](project-knowledge.md) 保存完整产品能力和技术依据；[任务交付](delivery.md) 保存设计或实现这次工作的过程。模块是长期知识边界，不等于一条实施需求或一个 Task。

## R-01 明确保存与两类记录

用户明确要求“保存”“加入需求队列”后，主管保存需求提案。提案只需让读者了解用户意图、来源、已知限制和未知；允许粗略，不要求提前补齐行为、验收或技术方案。已有明确实施需求时可以直接保存该需求，不强制再建提案。保存不启动设计或开发；主动发现的额外目标先作为建议，用户同意后才保存。

实施需求由设计工作形成或经核对已有充分依据后保存，包含以下内容：

- 目标：解决什么用户问题，完成后有什么变化。
- 范围：这次处理什么、不处理什么，与已有能力如何衔接、有哪些前置依赖。
- 行为与异常：输入、正常结果、异常与失败处理。
- 验收：可观察、可检查的完成条件。
- 来源与决定：提案来源、已确认选择、产品与适用技术文档引用。
- 未知：尚未明确的事项，以及是否阻止实施。
- 完成摘要：交付后记录实际成果、验证、未覆盖与剩余问题。

提案和实施需求各有稳定编号、类型、标题、状态、时间及关联入口，各自一份项目 Markdown 文件；状态有单一来源。实施需求采用上述七部分，提案正文保持轻量，不套用完整实施模板。固定位置见 [知识目录](project-knowledge.md)，精确字段与校验格式在技术契约中规定。

提案和实施需求可以按路径直接读取，也可通过需求工具查询，列表使用需求查询工具。正式新建、修改和状态保存必须通过需求保存工具，不直接用普通写入、编辑或脚本覆盖需求文件；修改已有记录前读取工具返回的当前原文与版本。产品、技术和索引文档仍通过普通文件工具维护。

工具校验对应类型的格式、版本与引用，可靠保存并返回真实结果；失败保留原文件，错误原文仍可阅读、修复。内容是否内聚、拆分是否完整、验收是否合理，由主管、设计 Agent 和独立审阅判断，程序不从聊天猜测。

## R-02 列表与详情

用户能区分待规划提案与待实施需求，按各自状态查看。列表至少显示编号、类型、标题、状态和最近修改时间，最新修改在前，同一时间排序稳定。

提案详情能找到处理结论、设计工作和产出的实施需求；实施需求详情能找到来源、产品模块、适用技术依据、实现 Task 与完成摘要。未规划提案不显示成已具备实施条件。

列表从项目文件生成，保存后刷新，重新打开或手动刷新时反映当前文件。无需模型也能读取。非法文件单独显示位置和原因，不因筛选隐藏，不把“读不了”显示成“没有需求”。索引提供格式和查询入口，不手工逐条维护实时状态；主管先查摘要，再按需读取正文。

## R-03 修改内容与文档归属

用户继续讨论并明确保存修改时，保留编号和决定来源。保存提案不自动改写正式产品定义。

设计 Agent 先检查已有产品、技术索引，维护已有权威模块；新增模块必须有明确职责与边界。实施需求引用内聚产品能力，共用事实集中定义并引用，不按前端、后端或数据库分工复制产品说明。

实施中修改目标、范围或验收，主管说明影响，在有效用户授权内更新需求及 Plan，需新增决定时先取得确认；受影响成果重新检查。不能修改验收来掩盖实际缺陷。已完成需求产生新改变时，创建关联新需求，保留原完成事实。

## R-04 从实施需求进入实现流程

一个可实施需求由一个实现 Task 流程负责完整交付。可实施意味着目标、范围和验收明确，具有足以制定 Plan 的产品与适用技术依据；并非所有未知都必须消失，但阻止实现的未知必须先解决。

用户明确实施后，主管读取这些依据并核对前置需求和接口是否具备；依赖未满足时说明等待原因，不当作已具备条件。条件具备后创建或接续关联实现 Task，再制定总体 Plan。多个开发、Review、Test Session 是同一流程中的分工，不创建小 Task。同一实施需求同一时刻只有一个未结束的实现 Task；重复启动返回既有进展。暂停、范围内返工与恢复沿原工作接续。

直接给出开发目标时，主管判断是否已足够明确；充分则补存实施需求并沿原授权启动。不充分则组织必要设计，形成明确实施需求后继续原授权内工作，不要求重复保存或重新启动；不能把宽泛提案直接当成可实施需求。产品选择、范围或验收尚需用户决定时保留等待。若设计形成多条实施需求，主管按依赖与授权安排次序，在同一主管 Session 中逐条完成实现流程；需要独立并行目标时使用不同主管 Session，不建立包住所有需求的父 Task。

设计 Task 可以覆盖多个模块、处理多条提案、产出多条实施需求，它与需求是来源/产出关系；不是每条需求都必须再启动一项完整设计 Task。设计交付不关闭实施需求。

主管 Session 同时只推进一项未结束 Task。需求详情显示对应实现进展；暂停、阻断和下一步在 Task 中说明，不能只从“进行中”判断操作仍在运行。

## R-05 状态、完成与归档

提案能区分待规划、规划中、已归档和已取消。用户授权正式设计后进入规划中；设计产出经确认、独立审阅和结算保存，来源与实施需求关联可查后归档。处理结论也可以是合并已有需求或不实施，但必须有已确认的依据；未处理的范围不能被归档掩盖。提案归档不代表产品已实现。设计工作失败或取消且不再有有效设计工作承接时，保留成果与原因，提案回到待规划；只有用户明确取消该提案才进入已取消。正常等待或暂停仍保留规划中，并展示对应进展。

实施需求能区分待实现、进行中、已完成、已取消和已归档。开始实现 Task 后进入进行中；完成范围、适用验证、结算与保存核对后才完成。暂停或返回设计不退回待实现，也不自动标记完成。用户可归档已结束的需求，正文、摘要与历史关联保留，不按状态移动或删除文件。

主管通过工具显式更新真实状态与结论，程序不按 Task 数量或 Session 结束自动判断需求完成。已写摘要而最终收口未结束时，显示“完成记录待核对”及具体进展，沿已有成果补齐，不重做已知成功工作。

## R-06 在另一环境查看或继续

项目文件复制或从版本管理取出后，两类记录可直接读取。已归档提案仍能找到规划结论与需求；已完成需求显示完成摘要。本环境没有详细执行记录时明确缺失，不能编造阶段报告。

历史进行中记录没有本环境执行工作时显示待继续。用户明确继续后，先核对已有成果、缺口与本次目标，再接续或建立适用工作；读取文件不自动执行或继承权限。

## R-07 从提案形成实施需求

用户要求设计某个目标时，主管组织设计工作，不要求用户亲自拆模块或选择每个专业 Session。设计 Agent 同时负责产品分析与必要技术设计，交付责任见 [设计工作](delivery.md#d-09-设计工作的交付)。

按用户结果和业务边界组织内聚模块，从中形成范围明确、可验收的实施需求。一个提案可以形成一条或多条需求，也可以合并进已有需求；多条相关提案可共同支撑一条需求。设计产出说明哪些目标已覆盖、哪些尚待决定，不强制需求树或固定拆分数量。

既有模块和技术依据充分时复用，不重复设计。工程分工、步骤多或实现难度高本身不是拆需求的理由；可分别验收、分别交付的目标才考虑拆分。拆分不得遗漏原意图、共同约束或已确认验收。

## R-08 Plan 发现无法实施时返回设计

制定 Plan 或实施中发现目标混杂、范围不清、验收无法明确时，主管停止相关实现写入，记录原因，委派设计 Agent 重新分析、必要拆分并更新文档。技术职责、接口或依赖不清时补齐技术设计；只是工作量大或需要并行工程时继续原流程，拆 Session 分工。

同一交付目标补充设计时，在原 Task 内保留成果，记录返回设计，委派设计 Session；适用确认、独立审阅及保存完成后修订总体 Plan，并重新核对受影响成果，再继续实现。这是停止实现、转入设计工作，不等同用户主动暂停整个 Task；主动暂停时不运行任何新设计，须先恢复。

若确需拆成不同交付目标，先确认并保存替代需求、来源关系和已有成果处置；旧需求按取消且由新需求替代保留，旧实现 Task 安全停止并取消，不能标记完成。新需求按原授权涵盖范围或新的用户决定启动各自实现流程，不同时保留旧目标和替代目标重复实施。不建立父子 Task 树。
