# 需求管理

## 用户目标与模块边界

用户把明确要做的改变保存下来，知道哪些尚未实施、哪些正在推进、哪些已经结束，能从需求找到验收和成果。

需求描述一项改变，包含目标、范围、行为、验收和依据；[项目知识](project-knowledge.md) 描述项目当前完整能力；[任务交付](delivery.md) 记录这次实际工作。三者关联，不分别复制一套完整产品说明。

## R-01 明确保存与需求规范

明确保存后，主管定位相关产品模块，整理一条内聚需求。用户得到以下内容：

- 目标：解决什么用户问题，完成后有什么变化。
- 范围：这次处理什么、不处理什么，与已有能力如何衔接。
- 行为与异常：什么情况下输入什么，发生什么，失败怎样处理。
- 验收：如何观察或检查是否做到。
- 来源与决定：哪些由用户确定，哪些引用已有文档，哪些仍是建议。
- 未知：保存时尚未明确什么，哪些必须在实施前补齐。
- 完成摘要：结束后记录实际成果、验证、未覆盖与剩余问题。

资料不足可以保存待实现草稿，不能伪造已经明确的决定。保存成功不启动开发。主动发现的新需求先作为建议，用户同意保存后才加入列表。

一条需求一个 Markdown 文件，头部用固定 YAML 元数据记录稳定编号、标题、状态、创建/更新时间和关联模块，正文保存上述七部分。编号与文件名对应，状态只有头部一份来源；具体文档位置见 [知识目录](project-knowledge.md)。

用户和 AI 按同一模板编写；程序校验字段与结构，不猜正文中的状态。格式错误不被接受为保存成功，编辑失败保留原文件；错误原文仍可阅读、修复。需求内容是否内聚、验收是否合理，由主管和适用独立角色判断。

## R-02 列表与详情

需求列表提供全部、待实现、进行中、已完成、已取消、已归档的查看方式，至少显示编号、标题、状态和最近修改时间。最新修改在前，同一时间的顺序稳定。用户可以打开完整正文、关联知识和已有任务。

列表从项目文件生成，保存后刷新，重新打开或手动刷新时反映当前文件。无需模型也能读取。非法文件单独显示位置和原因，不因为状态筛选而隐藏，也不把“读不了”显示成“没有需求”。

索引提供格式和查询入口，不手工逐条维护需求列表或状态。用户与主管查看同一份事实；主管先查摘要，再按需阅读选定正文。

## R-03 修改内容与文档归属

用户可以继续讨论并明确保存修改，保留原编号和已有决定。标题、描述和状态不需要用户另开完整交付任务逐项维护。

需求优先引用已有内聚模块。新增能力尚无正式模块时，明确拟议归属，不填不存在的引用，也不因为保存需求就改写正式产品定义。

实施中修改目标、范围或验收时，主管说明影响，取得相应用户决定后更新需求和计划；受影响成果必须重新检查。不能用编辑需求来把实际缺陷改成符合验收。已结束需求产生新改变时，创建关联的新需求，保留历史完成内容。

## R-04 从需求开始实施

用户明确选择实施后，主管建立或关联正式任务。内容有缺口时先补齐影响实现的行为与验收，明确等待的问题；不能拿一个未知草稿直接开发并自称完成。

同一需求同一时刻只存在一项未结束的正式工作，重复启动显示既有进展。用户直接给出开发目标时，必要需求由主管整理，并沿原指令继续，不要求再次启动。

需求进行中显示关联任务入口和实际阶段。需求状态描述改变的总体进展，暂停、阻断和具体下一步在任务中说明，不能只从“进行中”判断某项操作仍在运行。

## R-05 状态、完成与归档

| 状态 | 用户理解 | 进入条件 |
|---|---|---|
| 待实现 | 已保存，尚未正式实施 | 明确保存成功 |
| 进行中 | 这项改变已经开始推进 | 用户明确实施，相关工作有效开始 |
| 已完成 | 适用验证和结算已完成 | 成果、完成摘要、知识与记录已核对 |
| 已取消 | 用户决定不做或停止，影响已说明 | 未启动的需求取消，或执行已安全停止 |
| 已归档 | 已结束，作为历史保留 | 用户归档已完成或已取消需求 |

暂停任务不把需求退回待实现。取消与归档保留正文、已有成果和关联记录，不按状态移动文件，也不删除历史。

结算已写需求完成摘要而任务最终检查尚未结束时，显示“完成记录待核对”及具体任务进展，不能谎称整个工作已完成，也不能因此重做已知成果。

## R-06 在另一环境查看或继续

项目文件复制或从版本管理取出后，需求可直接读取。已完成需求显示完成摘要；本环境没有详细执行记录时，明确标注，不能编造阶段报告。

历史进行中需求没有本环境正在执行的任务时，显示待继续。用户明确继续后，先核对已有成果、缺口和本次目标，再建立适用工作；读取文件不自动恢复执行或权限。
