# 完整用户流程

本页从用户的行动说明产品如何使用。总体定义见 [产品总览](README.md)，具体行为由相应模块定义。

## J-01 第一次使用并打开项目

用户按照随产品交付的说明启动工作台，取得访问凭证并通过浏览器进入。工作台给出模型设置入口，用户配置默认模型并检查可用性。没有模型也能查看已有项目资料和记录，不能假装已经开始 AI 工作。

该开明实例只有一个全局 Server，用户接入多个 Project、创建主管或专业 Session 都由同一 Server 管理。项目和会话记录各自保留归属。

用户选择或输入工作台运行环境中的一个既有目录。空目录可作为新项目，已有代码目录可作为已有项目；新项目按 J-12 或 J-13 起步。添加项目表示把这个目录纳入工作台，并不自动生成应用代码。已经接入的目录返回原项目及会话、待办、未完成工作。

用户开始主管会话后可以立即讨论。首次正式保存或实施前，主管说明将创建的项目知识入口及补充规则，保留已有文件，展示差异，用户确认后建立。已有项目先调查并标记观察事实与未知，不能把有代码直接说成已验收。

结束时，用户得到可协作的项目空间、清晰的知识入口和一段可以继续的会话。无法访问目录、没有模型或入口建立失败，分别说明原因，不显示已经初始化成功。

依据：[项目工作区](modules/project-workspace.md)、[项目知识](modules/project-knowledge.md)。验收：AC-01～AC-03、AC-27。

## J-02 自由讨论，暂时不开发

用户说：“我想给账号功能加密码重置，先聊聊有没有必要。”主管可以直接讨论，也可以按需调查或请专业 Agent 分析，说明当前事实、选项、成本和未知。

主管发现“通知偏好”也是值得考虑的事，可以提出建议，但不能因此记为待办或开始实现。用户说“整理一下”时，主管先在对话中给出整理结果；用户明确说“记下来”“加到待办”，才记录。

需要独立专业分析时，主管建立只读 Task，在工作台保存简短 Plan 与专业报告后核对结果并结束；这不启动开发，也不强制改写知识或 Git 提交。主管自己回答时无需 Task。

结束时，用户得到讨论结果和可选择的下一步。用户不作决定，可以继续讨论或离开；没有被隐式创建的开发任务。

依据：[主管对话](modules/chief-conversation.md)。验收：AC-06、AC-07。

## J-03 记下一个想法，或整理成就绪待办

用户说：“记下来：给账号功能加密码重置。”主管新增一条待办，只记录标题和一两句话，不启动设计或开发。用户也可以在项目页直接新增，或者在编辑器里写进 `.dev/backlog.md`；通过工具或界面新增的条目自动带有编号、来源、创建人和时间。

已有规格依据时，可以附上规格引用，条目在项目页显示为就绪；没有引用的显示为想法。用户说“整理一下”时，主管先在对话中给出整理结果，用户明确要求后才记录，同一要求不重复询问。

保存失败时说明原因并保留输入，不重复创建同一条待办。

结束时，用户得到一条可以在项目页看到的待办，开发尚未开始。大功能的设计转化见 J-09。

依据：[待办与规格](modules/backlog-and-specs.md)。验收：AC-07～AC-09、AC-24。

## J-04 实施待办，或者直接给出开发目标

用户从项目页的待办里选择密码重置并点「实施」，也可以直接说：“给登录模块增加密码重置，按我们确定的范围实现。”主管先核对依据：引用的规格是否足够写出可观察的验收；不够，或者目标宽泛时，先组织设计（J-09），不把“实现支付网关”这样的宽泛目标直接当作工程 Plan。

每次实施为本次目标建立一项修改 Task，可以携带 0～n 条待办；同一条待办同一时间只关联一个未结束的 Task，重复启动时返回已有进展。用户要求按顺序实施多条时，主管依次建立 Task，同一时间只有一个未结束，每个都完整经过计划、开发、审核、测试和结算；遇到阻塞决定、返工后仍未通过、依赖尚未完成或下一条待办有问题时，停下等用户决定。

修改 Task 的 Plan 先写验收与范围（要求见 [BL-07](modules/backlog-and-specs.md)），并固定保存到 `.dev/work/<taskId>/plan.md`。默认情况下，明确的实施指令已经授权范围内的总体 Plan；项目若选择逐计划确认，取得总体 Plan 的确认后继续。子 Session 可自主制定内部计划或直接完成简单工作。

主管按当前步骤创建或绑定专业 Session 并运行，在阶段切换前显式记录上一阶段结果和当前阶段。用户在任务详情看到总体 Plan、进展、成果与待处理问题。标准代码成果必须经过独立审核与测试，当前目标内的缺陷由主管组织修复并再次检查。

结束时要么完成正式交付和结算，要么明确停在等待、暂停或执行情况待核实。不能因为工程师回复结束就标记完成。

依据：[待办与规格](modules/backlog-and-specs.md)、[任务交付](modules/delivery.md)。验收：AC-10～AC-12、AC-14、AC-16～AC-18。

## J-05 做一个很小的修改，或者只交付文档

用户说：“把按钮文案从提交改为保存。”主管给出并保存简短的总体 Plan，安排适合的工程师修改；工程师可以直接完成这项简单工作，由独立 Agent 检查目标替换及适用检查，再结算。纯样式、文案和确定展示的修改可以采用轻量路线；一个按钮如果改变了业务行为，仍采用标准代码路线。

用户说：“把已经确定的账号行为整理进规格。”主管给出并保存文档工作的总体 Plan，由设计角色整理，独立检查内容、结构、语义一致性和引用，再结算；只交付文档不要求制造一个不存在的代码测试报告。

整理过程中确定为可交付目标的内容形成就绪待办或规格（[BL-08](modules/backlog-and-specs.md)），尚待决定的范围如实保留。结论只写在聊天或报告里、项目里没有规格或待办记录，不算完成这次整理。

两种情况都保留实际成果和必要记录，只更新受影响的知识。记录一条待办本身不强制走上述正式文档交付流程。

依据：[任务交付](modules/delivery.md)。验收：AC-13、AC-15。

## J-06 工作中需要用户决定，或用户改变主意

审核发现当前验收未满足，主管在原目标内组织修复，无需让用户重新批准每一步。发现新增业务范围时，主管展示影响和建议，用户选择本次处理、以后处理或不采纳。

本次处理：更新明确的目标和同一份总体 Plan，重新检查受影响的成果。以后处理：用户同意后记为另一条待办，当前目标继续；需要讨论或推进另一目标时使用新的主管 Session。不同意：保留决定，不把建议变成承诺。

确认、选择和输入沿用 Pi 原生交互语义，不按 Plan、待办或范围再划分确认类型。用户能够看清正在决定什么、影响什么；答复已收到和事情已执行成功分别显示。文字答复须明确对应原请求，内容变化后旧答复不授权新操作。

进程仍在时，任何子 Session 的用户交互都保留原 Session 和等待，经主管协作入口统一呈现。转发、答复关联、记录和恢复由宿主处理，不要求主管模型依次调用登记、呈现、解决工具。父委派保持等待，答复直接恢复发起请求的扩展或工具，不能排在等待中的普通输入后；需要模型判断时通过实际执行结果返回。Server 重启后保留问答事实，原调用不存在时模型按剩余工作重新询问，不伪造旧等待，不重复创建工作。

依据：[主管对话](modules/chief-conversation.md)、[任务交付](modules/delivery.md)。验收：AC-12、AC-16、AC-20。

## J-07 离开、暂停、取消与接续

用户关闭浏览器，后台工作继续；需要决定时保留成果并等待。再次打开项目，看到原任务及真实进展，没有重新投递开发指令。

用户主动暂停时，停止继续实施并保留已知成果。用户继续时，沿原任务接续。用户取消时，先确认实际执行已经停止，再显示取消，保留已产生的文件或影响，不能假装已经回滚。

工作台被停止后重新启动，总体 Plan、阶段结果、专业 Session、待处理交互和已解决决定仍可找到。可以确认进展时继续原工作与等待；某个操作是否已经生效无法确认时，显示具体待核实事项，核实后再继续，避免重复产生影响。

原主管会话不可继续时，用户可以选择没有其他未结束 Task 的新主管 Session 接续未完成任务。先明确当前进展和待处理事项并安全交接，再继续；已有成功成果和专业 Session 不重新创建，原主管完成交接后可处理下一项工作。

依据：[主管对话](modules/chief-conversation.md)、[任务交付](modules/delivery.md)。验收：AC-19、AC-21、AC-22、AC-25。

## J-08 取得成果，并在下一次工作中使用

完成适用 Review、Test 后，主管显式记录阶段结果并进入 settle。结算核对实际改变，把稳定事实更新到受影响规格的实现状态并附上交付它的 Task；将总体 Plan、阶段结果、实施说明、审核、适用测试和结算报告保存到交付记录；关闭已完成的待办并写明 Task，遗留问题记为新的待办。适用验证、结算、规格与待办更新未齐全，Task 不显示完成。

有版本管理的项目保存本次成果与记录，保留无关改动；没有版本管理的项目仍保存相同项目文件，并明确说明保存位置。保存失败，任务保持未完成，已有成果保留供重试。

用户最终能打开实际成果、相关知识与报告，看到完成范围、执行过的检查、未覆盖事项和遗留问题。新会话从项目入口了解当前事实，再按本次目标阅读相关模块，不需要上一轮完整聊天。

项目复制到另一环境后，待办、模块地图和规格仍可阅读；没有随项目迁移的详细执行记录明确标记缺失。未完成的待办不会因为被读取就自动执行。

依据：[任务交付](modules/delivery.md)、[项目知识](modules/project-knowledge.md)。验收：AC-23～AC-26、AC-28。

## J-09 让 AI 完成设计，形成规格与切片清单

用户说：“先设计支付网关，不要开发。”主管建立一项 `workKind=design` 的主设计 Task，制定工作 Plan，组织统一设计角色；较大项目可按边界分多个 Session，不默认加载全部历史。

设计 Agent 复用现有权威知识，产出四样东西：规格（行为、异常、验收要点、接口、实现状态与未知）、被多个切片共同依赖的接口、需要的模块地图变化，以及切片清单。每个切片应该可以独立验收、写入集中在一个模块内、依赖的接口已经写在规格里、一次 Review 能看完。

模块地图变化和新增或改变的对外接口以待决问题请用户确认，确认前不写入；设计交付先经独立审阅，再把切片清单交给用户确认。确认后，原待办写明拆分去向并关闭，切片记录产生它的设计 Task 并显示“来自设计”，用户再逐条或按顺序实施（J-04）。确认前，切片标“待设计确认”，建实施 Task 会被拒绝。

项目页把 B-x 放在“设计中”，显示设计完成链、返工次数和是否在等用户确认；设计结算后 B-x 进入“已完成”并显示拆分去向。设计不启动开发，代码未被修改；规格实现状态仍为未实现。用户得到规格、接口、模块地图变化、就绪待办与来源覆盖说明。已有充分依据时直接使用，不重做全部设计。

依据：[设计交付](modules/delivery.md)、[待办与规格](modules/backlog-and-specs.md)、[项目知识](modules/project-knowledge.md)。验收：AC-29～AC-32、AC-54、AC-59、AC-61。

## J-10 制定 Plan 时发现依据不足

主管发现支付通知的行为不清时，停止相关实现写入，保留成果与阻断原因，在原实施 Task 内把阶段切到 `design`，委派设计 Session 补齐规格或接口；这是补充设计，不创建第二个竞争 Task。只是工作量大时调整分工，不重新拆设计。

仍是同一交付目标时，确认、独立审阅并保存补充规格，修订 Plan 的验收与范围、重新检查受影响的依据与成果，继续原 Task；实施 Task 的 `design` 阶段是合法的返工步骤。涉及模块边界时先请用户确认。用户主动暂停整个 Task 时不启动设计，恢复后再处理。

若形成不同交付目标，新增相应的待办，原待办写明拆分去向；原 Task 安全取消，不能标为完成；新目标分别启动 Task，不与旧工作重复执行，Review/Test 不借用不匹配的旧结果。

依据：[待办与规格](modules/backlog-and-specs.md)、[任务交付](modules/delivery.md)。验收：AC-33、AC-34。

## J-11 用别的编码 Agent 委派一项工作

用户正在 Codex、Claude Code 或 Grok 里干活，需要把一件事交给工作台。他在客户端的 MCP 配置里加一条记录：本地子进程（stdio）或常驻地址加访问口令。未认证的请求被拒绝，本机也不例外。

接入后，外部 Agent 先看事实：已登记的项目，每个项目的待办列表（条目、状态、是否有规格引用、是否有问题）。它据此决定委派什么，不需要用户先打开浏览器。

委派时它给出目标、范围、验收与需要的模式（评审／实施／测试）。主管按既有规则判断这是讨论、只读调查还是修改交付，可能直接回答，也可能建立 Task 组织专业工作；Task 类型与阶段由主管判断，外部 Agent 给的模式是指令而不是强制类型。

委派返回一个运行标识。外部 Agent 用它查询：状态、走过的阶段与轮次、当前阶段、**计划内还没开始的阶段**、参与的成员、最近一条工作说明，以及是否在等用户答复。宿主支持时还会收到进度通知。一个项目只有一条固定会话，所以上下文连续：上一次的结论、失败和决定都还在。

主管需要用户决定时，问题出现在查询结果里。客户端能就地弹表单就让用户选；不能就挂着等显式答复——工作台不会自动替用户答，也不会因为超时替答。答复之后工作原样继续，浏览器里能看到问题和是谁答的。

前一项工作还没结束时新的委派会排队，并说明挡在前面的是哪一项；不同项目互不影响。用户可以取消，取消请求与实际停止可区分，已有成果不被重写。断线或工作台重启后用运行标识重新查询就能接上，已知成功的工作不重做。

工作结束时，外部 Agent 读到真实报告与 Plan，而不是只凭聊天记忆——固定会话会被压缩上下文。用户在浏览器里能打开同一条会话，看到同一项 Task、成员、报告与待答问题，也能自己决定、取消或改名。

依据：[外部 Agent 接入](modules/external-agents.md)。验收：AC-38～AC-42。

## J-12 从一份需求文档开始一个新项目

用户在空目录里放一份需求文档，要求开始做这个项目。主管展示要建立的项目入口，用户确认后建立；文档保持原样，作为设计的来源，不直接当作规格。

设计一次交付模块地图、技术选型与总体架构、产品规格、必要的接口、切片清单，以及来源覆盖说明——文档的每一部分进了哪份规格、成为哪条待办、尚待决定或明确不做。模块地图、技术选型和切片清单都需要用户确认；技术栈是用户的决定。

确认后，切片从“可运行的骨架”开始（能构建、能启动、有测试入口，并有一条确认会失败的自检），以“联调验收”结束（按文档中的关键用户路径跨模块走一遍）。之后每个切片单独实施（J-04），开发只读它负责的模块的规格、接口和计划。

结束时，用户得到可运行的骨架和按顺序推进的切片；确认之前没有开始开发。

依据：[待办与规格](modules/backlog-and-specs.md)、[项目工作区](modules/project-workspace.md)。验收：AC-56。

## J-13 接入一个已有代码的项目

用户接入一个已有代码、没有项目入口的仓库，要求修改其中一个模块。主管先用一个只读任务调查现有能力、文档、代码入口，以及构建和测试方式。

模块地图根据代码结构提出，用户确认后才写入；从代码中看到的结构不会自动成为确认的边界。规格按需补写：只有第一次要被修改的模块才补，其中已有行为标为“已实现（观察）”，不写成已验证。不要求一次补全整个项目的规格。

此后进入日常迭代（J-03、J-04）。结束时，用户得到经确认的模块地图、被修改模块的规格和本次交付的成果。

依据：[待办与规格](modules/backlog-and-specs.md)、[项目工作区](modules/project-workspace.md)、[项目知识](modules/project-knowledge.md)。验收：AC-57。
