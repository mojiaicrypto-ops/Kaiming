# 完整用户流程

本页从用户的行动说明产品如何使用。总体定义见 [产品总览](README.md)，具体行为由相应模块定义。

## J-01 第一次使用并打开项目

用户按照随产品交付的说明启动工作台，取得访问凭证并通过浏览器进入。工作台给出模型设置入口，用户配置默认模型并检查可用性。没有模型也能查看已有项目资料和记录，不能假装已经开始 AI 工作。

该开明实例只有一个全局 Server，用户接入多个 Project、创建主管或专业 Session 都由同一 Server 管理。项目和会话记录各自保留归属。

用户选择或输入工作台运行环境中的一个既有目录。空目录可作为新项目，已有代码目录可作为已有项目。添加项目表示把这个目录纳入工作台，并不自动生成应用代码。已经接入的目录返回原项目及会话、需求、未完成工作。

用户开始主管会话后可以立即讨论。首次正式保存或实施前，主管说明将创建的项目知识入口及补充规则，保留已有文件，展示差异，用户确认后建立。已有项目先调查并标记观察事实与未知，不能把有代码直接说成已验收。

结束时，用户得到可协作的项目空间、清晰的知识入口和一段可以继续的会话。无法访问目录、没有模型或入口建立失败，分别说明原因，不显示已经初始化成功。

依据：[项目工作区](modules/project-workspace.md)、[项目知识](modules/project-knowledge.md)。验收：AC-01～AC-03、AC-27。

## J-02 自由讨论，暂时不开发

用户说：“我想给账号功能加密码重置，先聊聊有没有必要。”主管可以直接讨论，也可以按需调查或请专业 Agent 分析，说明当前事实、选项、成本和未知。

主管发现“通知偏好”也是值得考虑的需求，可以提出建议，但不能因此写入需求队列或开始实现。用户说“整理一下需求”时，主管先在对话中给出整理结果；用户明确说“保存”“加入队列”，才进入保存流程。

需要独立专业分析时，主管建立只读 Task，在工作台保存简短 Plan 与专业报告后核对结果并结束；这不启动开发，也不强制改写知识或 Git 提交。主管自己回答时无需 Task。

结束时，用户得到讨论结果和可选择的下一步。用户不作决定，可以继续讨论或离开；没有被隐式创建的开发任务。

依据：[主管对话](modules/chief-conversation.md)。验收：AC-06、AC-07。

## J-03 保存提案，或保存已有依据的实施需求

用户说：“把刚才确定的密码重置内容保存为需求。”主管判断内容是否已形成明确交付目标。尚待规划则保存轻量提案，记录意图、来源、限制与未知；已有充分依据则保存实施需求，按规范记录范围、行为、验收及相关文档。

用户不用逐项维护状态。保存后，记录出现在对应提案或实施需求列表，可打开正文和来源。提案不显示成已具备实施条件，保存不启动正式设计或开发。

如果格式不合法或文件保存失败，用户看到具体错误和待修正事项；如果本机保存成功但版本提交失败，分别报告两个结果，不再创建一条重复需求。

结束时，用户取得可继续规划的提案，或有明确依据的实施需求，开发尚未开始。设计转化见 J-09。

依据：[需求管理](modules/requirements.md)。验收：AC-07～AC-09、AC-24。

## J-04 启动需求，或者直接给出开发任务

用户从需求列表选择密码重置，并明确要求实施；也可以直接说：“给登录模块增加密码重置，按我们确定的范围实现。”第二种情况下，主管先整理必要需求，沿原实施指令继续，不让用户再次保存、再点击开始。

主管先核对是否已有可实施需求与充分依据。不充分则在有效授权内组织设计，形成明确交付单元后继续，新增产品选择需用户决定；不把“实现支付网关”这样的宽泛目标直接作为工程 Plan。设计形成多条需求时，主管按依赖与有效授权逐条安排实现；独立目标需要并行时使用不同主管 Session，不强迫用户逐次重复原授权。

主管 Session 为选定实施需求的完整交付建立一项 Task，同时只推进这项未结束任务。用户另有话题或目标时，新建主管 Session；暂停和等待不会释放原任务关联。

主管明确本次目标和验收，制定一份总体 Plan，固定保存到 `.dev/work/<taskId>/plan.md`，说明依据与安排。默认情况下，明确实施指令已经授权范围内总体 Plan；项目若选择逐计划确认，取得总体 Plan 的确认后继续。子 Session 可自主制定内部计划或直接完成简单工作，不要求另存计划文件或逐份审批；已有授权政策仍适用。缺少会影响实现的产品选择时，主管给出具体问题和建议，等待用户决定。

主管按当前步骤创建或绑定一个或多个专业 Session 并运行，委派同步推进当前 Task。主管在阶段切换前显式记录上一阶段结果和当前阶段，用户在任务详情看到总体 Plan、进展、成果与待处理问题。标准代码成果必须经过独立审核与测试，同阶段可有多个 Review；本轮审核完成且必要问题处理并复审后才进入 Test。当前目标内的缺陷由主管组织修复并再次检查。

结束时要么完成正式交付和结算，要么明确停在等待、暂停或执行情况待核实。不能因为工程师回复结束就标记完成。

依据：[需求管理](modules/requirements.md)、[任务交付](modules/delivery.md)。验收：AC-10～AC-12、AC-14、AC-16～AC-18。

## J-05 做一个很小的修改，或者只交付文档

用户说：“把按钮文案从提交改为保存。”主管给出并保存简短的总体 Plan，安排适合的工程师修改；工程师可以直接完成这项简单工作，由独立 Agent 检查目标替换及适用检查，再结算。纯样式、文案和确定展示的修改可以采用轻量路线；一个按钮如果改变了业务行为，仍采用标准代码路线。

用户说：“把已经确定的账号需求整理成正式产品文档。”主管给出并保存文档工作的总体 Plan，由设计角色整理，独立检查内容、结构、语义一致性和引用，再结算；只交付文档不要求制造一个不存在的代码测试报告。

文档整理仍要产出实施需求：整理过程中确定为可交付目标的内容按 [需求管理 R-07](modules/requirements.md#r-07-从提案形成实施需求) 形成并用需求工具保存，尚待决定的范围如实保留。结论只写在聊天或报告里、项目里没有需求记录，不算完成这次整理。

两种情况都保留实际成果和必要记录，只更新受影响的知识。保存轻量提案本身不强制走上述正式文档交付流程。

依据：[任务交付](modules/delivery.md)。验收：AC-13、AC-15。

## J-06 工作中需要用户决定，或用户改变主意

审核发现当前验收未满足，主管在原目标内组织修复，无需让用户重新批准每一步。发现新增业务范围时，主管展示影响和建议，用户选择本次处理、以后处理或不采纳。

本次处理：更新明确的目标和同一份总体 Plan，重新检查受影响的成果。以后处理：用户同意后保存另一条需求，当前目标继续；需要讨论或推进另一目标时使用新的主管 Session。不同意：保留决定，不把建议变成承诺。

确认、选择和输入沿用 Pi 原生交互语义，不按 Plan、需求或范围再划分确认类型。用户能够看清正在决定什么、影响什么；答复已收到和事情已执行成功分别显示。文字答复须明确对应原请求，内容变化后旧答复不授权新操作。

进程仍在时，任何子 Session 的用户交互都保留原 Session 和等待，经主管协作入口统一呈现。转发、答复关联、记录和恢复由宿主处理，不要求主管模型依次调用登记、呈现、解决工具。父委派保持等待，答复直接恢复发起请求的扩展或工具，不能排在等待中的普通输入后；需要模型判断时通过实际执行结果返回。Server 重启后保留问答事实，原调用不存在时模型按剩余工作重新询问，不伪造旧等待，不重复创建工作。

依据：[主管对话](modules/chief-conversation.md)、[任务交付](modules/delivery.md)。验收：AC-12、AC-16、AC-20。

## J-07 离开、暂停、取消与接续

用户关闭浏览器，后台工作继续；需要决定时保留成果并等待。再次打开项目，看到原任务及真实进展，没有重新投递开发指令。

用户主动暂停时，停止继续实施并保留已知成果。用户继续时，沿原任务接续。用户取消时，先确认实际执行已经停止，再显示取消，保留已产生的文件或影响，不能假装已经回滚。

工作台被停止后重新启动，总体 Plan、阶段结果、专业 Session、待处理交互和已解决决定仍可找到。可以确认进展时继续原工作与等待；某个操作是否已经生效无法确认时，显示具体待核实事项，核实后再继续，避免重复产生影响。

原主管会话不可继续时，用户可以选择没有其他未结束 Task 的新主管 Session 接续未完成任务。先明确当前进展和待处理事项并安全交接，再继续；已有成功成果和专业 Session 不重新创建，原主管完成交接后可处理下一项工作。

依据：[主管对话](modules/chief-conversation.md)、[任务交付](modules/delivery.md)。验收：AC-19、AC-21、AC-22、AC-25。

## J-08 取得成果，并在下一次工作中使用

完成适用 Review、Test 后，主管显式记录阶段结果并进入 settle。结算核对实际改变，把稳定事实更新到受影响的项目知识；将总体 Plan、阶段结果、实施说明、审核、适用测试和结算报告保存到交付记录；需求留下完成摘要、证据与剩余问题。适用验证、结算和成果保存未齐全，Task 不显示完成。

有版本管理的项目保存本次成果与记录，保留无关改动；没有版本管理的项目仍保存相同项目文件，并明确说明保存位置。保存失败，任务保持未完成，已有成果保留供重试。

用户最终能打开实际成果、相关知识与报告，看到完成范围、执行过的检查、未覆盖事项和遗留问题。新会话从项目入口了解当前事实，再按本次目标阅读相关模块，不需要上一轮完整聊天。

项目复制到另一环境后，需求和项目知识仍可阅读；没有随项目迁移的详细执行记录明确标记缺失。历史上进行中的需求不会因为被读取就自动恢复执行。

依据：[任务交付](modules/delivery.md)、[项目知识](modules/project-knowledge.md)。验收：AC-23～AC-26、AC-28。

## J-09 让 AI 完成设计，形成可实施需求

用户说：“先设计支付网关，不要开发。”主管围绕本次目标建立设计工作，制定工作 Plan，组织统一设计角色；同一角色完成产品分析和必要技术设计，较大项目可按边界分多个 Session，不默认加载全部历史。

设计 Agent 复用现有权威知识，明确产品范围、行为与验收，形成内聚模块和实施需求，再补齐尚未解决的技术职责、接口与依赖。已有技术设计足够时引用，不要求每个模块新写一份架构。主管组织独立审阅，检查覆盖原意图、拆分合理性、产品技术一致性、引用和未决事项。需要用户决定的范围与验收明确呈现，已有决定不反复审批。

确认、审阅及保存完成后结算设计工作，维护索引与来源，归档已处理提案；用户得到产品与适用技术文档、实施需求、依赖及未知。实施需求尚未完成，代码未被自动修改。用户后续选择需求进入 J-04。已有充分依据时直接使用，不重做全部设计。

依据：[设计交付](modules/delivery.md#d-09-设计工作的交付)、[需求转化](modules/requirements.md#r-07-从提案形成实施需求)、[项目知识](modules/project-knowledge.md)。验收：AC-29～AC-32。

## J-10 制定 Plan 时发现需求需要重新设计

主管发现支付通知需求的产品范围混杂时，停止相关实现写入，保留成果与阻断原因，在原 Task 中委派设计 Session 重新分析。技术接口不清则补技术依据；单纯工作量大只拆专业分工，不重新拆需求。

仍是同一交付目标时，确认、独立审阅并保存补充设计，修订 Plan、重新检查受影响依据与成果，继续原 Task。用户主动暂停整个 Task 时不启动设计，恢复后再处理。

若形成不同交付目标，先保存经确认的替代需求和已有成果处置，安全取消旧 Task 与旧需求，保留替代关系；新需求按有效授权分别进入实现流程。旧工作不伪装成完成，也不与替代工作重复执行。其他路径仍按原 Task 暂停、恢复和范围内返工规则处理。

依据：[返回设计](modules/requirements.md#r-08-plan-发现无法实施时返回设计)、[任务交付](modules/delivery.md)。验收：AC-33、AC-34。

## J-11 用别的编码 Agent 委派一项工作

用户正在 Codex、Claude Code 或 Grok 里干活，需要把一件事交给工作台。他在客户端的 MCP 配置里加一条记录：本地子进程（stdio）或常驻地址加访问口令。未认证的请求被拒绝，本机也不例外。

接入后，外部 Agent 先看事实：已登记的项目、每个项目的需求列表（提案与实施需求、状态、是否可读）。它据此决定委派什么，不需要用户先打开浏览器。

委派时它给出目标、范围、验收与需要的模式（评审／实施／测试）。主管按既有规则判断这是讨论、只读调查还是修改交付，可能直接回答，也可能建立 Task 组织专业工作；Task 类型与阶段由主管判断，外部 Agent 给的模式是指令而不是强制类型。

委派返回一个运行标识。外部 Agent 用它查询：状态、走过的阶段与轮次、当前阶段、**计划内还没开始的阶段**、参与的成员、最近一条工作说明，以及是否在等用户答复。宿主支持时还会收到进度通知。一个项目只有一条固定会话，所以上下文连续：上一次的结论、失败和决定都还在。

主管需要用户决定时，问题出现在查询结果里。客户端能就地弹表单就让用户选；不能就挂着等显式答复——工作台不会自动替用户答，也不会因为超时替答。答复之后工作原样继续，浏览器里能看到问题和是谁答的。

前一项工作还没结束时新的委派会排队，并说明挡在前面的是哪一项；不同项目互不影响。用户可以取消，取消请求与实际停止可区分，已有成果不被重写。断线或工作台重启后用运行标识重新查询就能接上，已知成功的工作不重做。

工作结束时，外部 Agent 读到真实报告与 Plan，而不是只凭聊天记忆——固定会话会被压缩上下文。用户在浏览器里能打开同一条会话，看到同一项 Task、成员、报告与待答问题，也能自己决定、取消或改名。

依据：[外部 Agent 接入](modules/external-agents.md)。验收：AC-38～AC-42。
