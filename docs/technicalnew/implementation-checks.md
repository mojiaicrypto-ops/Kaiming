# 实施入口与设计验证

本页是实施 Agent 的工作导航与验证契约。当前所有 SDK/模型/崩溃/浏览器场景为 NOT_RUN；文档审阅通过仅证明文档可用于下一步。

## I1 Pi 接入必须先通过的试验

固定 @earendil-works/pi-coding-agent / pi-ai v1.0.0。试验代码在独立最小目录完成，不先写业务框架。每项保存命令、配置、原生 JSONL、DB/工具记录和观察；不得用假回调代替真实 SDK 行为。

| 编号 | 操作 | 必须证明；失败后的设计路径 |
|---|---|---|
| PI-01 | 普通/自定义输入、首次文件创建、模板、压缩/分支、扩展拦截；各边界重启 | inputId 精确映射 marker/root；不重复追加；关联不明 interrupted 后核实，不自动重投，不能改原生消息字段 |
| PI-02 | 原生重试、工具失败、message_end/agent_end/agent_settled；注入 JSONL 写失败 | 正确区分停稳/业务成功/磁盘边界；不靠事件或内存 leaf 宣布 completed |
| PI-03 | 在原生工具/委派等待中崩溃，open 原历史，读取 Task/实际文件/报告，再提交剩余工作输入 | 不补 ToolResult、不恢复工具栈、不重做已知成果；原历史边界不可用时保留并明确重建上下文，未知仍阻断 |
| PI-04 | 连续流式输出时准备快照/订阅、messageKey 转原生条目、压缩、代次替换 | 边界内快照 + 边界后增量不丢不重；无法关联明确重同步 |
| PI-05 | 宿主输入/Task/报告/交互/规范文件保存失败，ctx.abort、外层等 idle | 保存失败不能返回成功；停止新准入，实际影响核实；原生 edit/write/bash 不建第二套意图账 |
| PI-06 | abort 本地 bash、超时、子进程/脱离管理影响；停止与结束竞态 | 确认停止才停态；无法确认的后代进程保留未知，不宣传自动回滚/隔离 |
| PI-07 | 多 cwd/多模型并行，恢复原文件、模型不可用、角色工具/规则变化 | 不串项目，不改全局 cwd/env，不默认回退，冷恢复重建整个运行契约 |
| PI-08 | 官方 question 移植扩展通过 extensionFactories/pi.registerTool 加载；SDK uiContext confirm/select/input；确认/选择/输入/取消；父委派等待中的请求、答复及各保存边界重启。宿主 UI 适配器必须实现为普通对象（不能是类实例） | SDK 非 TUI 可用，无重复工具注册或 TUI 依赖；按 M5 请求/答复落 WAL 后转发/恢复；按原请求 ID 返回真实答复，无并发 prompt/循环等待；只在主管展示，取消返回原调用，原 Promise 丢失后保留问答事实、stale 原请求；模型必要时重新发问。两条已实测结论：**(1) 交互开关是「是否绑定 UI 适配器」，mode 只作身份声明**（`hasUI()` 只判断 uiContext 是否绑定；绑定 + `rpc` 与绑定 + `print` 均可交互，未绑定时不可交互）；**(2) 适配器必须是普通对象**（bindExtensions 以 `{...ui, select, confirm, input, editor, custom}` 包装，类实例的原型成员会在包装后丢失，实测 `notify` 变 undefined）。回归检查：包装后 `notify` 仍可用并记录、TUI-only 成员调用时报出适配器自己的错误、theme 缺失为已知事实 |
| PI-09 | 专业并发=1；多个子 Session 排队，父工具等待；成员先完成/阻断；超时、abort、stale 后续办 | 主管不占专业名额；等待全部当前成员，timeout 仅快照；wait 不追加输入；异常停稳核实后 continue，用户暂停/取消不自动重启；等待可取消，父 stop 不误取消子工作 |

未通过 PI-01/02/05/07 前不实施需要可靠 Task 的模型执行链路；可以先实现纯存储/查询。PI-03 验证原生历史与已知成果续办能力；首版不实现工具回执修补。PI-04 必须在交付实时 UI 前通过；PI-08/09 必须在交付同步协作/授权前通过。

## I3 故障与协作验证矩阵

| 编号 | 触发 | 必须观察 | 产品对应 |
|---|---|---|---|
| REL-01 | 同 ID 重试/改参数；并发打开目录/启动需求 | 原身份/结果；冲突明确；不重复工作 | AC-01/11/20 |
| REL-02 | 接纳提交后唤醒丢失，重启 | 扫描原 queued，不复制新输入 | AC-21 |
| REL-03 | 同 Session 多输入、多 Session 并发、容量不足 | 同 Session 无并行 prompt；其他 Session 公平推进 | AC-05/21 |
| REL-04 | 当前步骤两个 Reviewer 先后报告，一人 blocked 而另一仍运行；超时/异常/用户暂停；后续 Test | 当前 Task 当前成员才计入；全员结束聚合报告/异常，超时不取消；不中途进入 Test；用户暂停不自动重启，成果修复后新独立 Review → Test | AC-14/16/17 |
| REL-05 | 委派事务失败/响应丢失，报告提交后立刻崩溃 | 无半批假成功；原成员/报告可查询，原调用栈不恢复；不重做专业成果 | AC-20/21/22 |
| REL-06 | 未结束 Task 期间新目标、主管压缩/停止等待或交接 | 一主管一项未结束工作；当前步骤成员/交互事实可查询续办；旧主管无派发/呈现权 | AC-21/25 |
| REL-07 | 专业最后一句自称完成，但未 report；报告后仍尝试写；主管遗漏 task(op=update) | REPORT_MISSING；已报告的交付不再修改；停稳才释放写入；事件不自动代写业务阶段 | AC-14/17 |
| REL-08 | 代码/依据改动、组合成果、旧结果迟到 | 交付状态已变化，旧复核/测试不能用于当前完成；程序在 end 缺项中要求重新复核 | AC-12/16/17 |
| REL-09 | 当前 input.stop 与 Task pause/cancel、正常结束竞态；resume 多次重试 | 精确范围、实际停止；currentInputId 指向唯一续办输入，当前步骤能读新状态/结果；不重做已完成成员，不取消其他 Task | AC-19/21 |
| REL-10 | 原生工具执行中崩溃，用户只说继续 | 保留 Task/历史/已知成果，核实实际影响；没有逐原生工具效果账也不能盲重放 | AC-22 |
| REL-11 | Pi 保存领先 DB，或 DB 回执领先 Pi | 核对关联/已保存结果，显式续办剩余工作；不补 ToolResult，不重投已进入上下文输入 | AC-21/22 |
| REL-12 | 子 Session 原生请求、多个请求/页面、主管模型一直等待、重复/迟到答复、取消/内容变化 | 父委派保持等待；宿主按当前主管路由原 ID 并直接响应源请求，无循环等待；过期/取消解除源 UI 等待且原动作不执行，旧答复不扩大授权 | AC-20 |
| REL-13 | 两页面同订阅、慢连接、握手期间输出、实例替换 | 广播不争抢；有界、不阻塞；溢出/换代重同步 | AC-04/05/21 |
| REL-14 | 两类需求、非法 YAML/类型状态组合、失效引用、外部编辑、CAS 冲突 | 原文可读、错误不被筛选隐藏、列表重建、不损坏原文件 | AC-08/09 |
| REL-15 | 结算文件保存/Git/完成登记分别失败，无关暂存、无 Git | 需求最终状态与报告同在保存清单，task(op=end)核对交付状态；文件已完成而Task未收口显示待核对；已有成果保留，只补缺步，保护现场，本机保存如实 | AC-23/24 |
| REL-16 | 重复启动 Server/改状态目录、Session 清理、项目复制、目录重绑定、备份恢复 | 全局单 Server；有效引用不损坏，不继承执行/授权；精确绑定可核对 | AC-04/25/26/28 |

## I4 提示词与真实业务检查

检查七个角色实际收到 base/适用共同规则/完整角色正文及其 Task、Plan、依据入口；链接不能代替加载。检查 read Task 在 Server 保存 Plan/报告后停稳收口、write Task 的适用验证/结算、所有专业委派都绑定 Task、同一需求规则跨文档引用而非重定义、冲突能被发现。

至少用实际模型完成：自由讨论不保存、明确保存需求、模块内聚整理、标准开发、轻量 UI 文案、正式文档、多 Reviewer 与返工、主管总体 Plan 逐确认/默认授权、子内部计划不强制审批、授权拒绝与当前步骤续办、未知效果、结算缺项、新会话接续。查看实际工具调用、正式产物与证据，不只看回复像不像遵守规则。

以下经验场景纳入同一实际模型检查，不增加产品阶段或审批：

| 场景 | 观察实际行为 |
|---|---|
| 用户给局部建议，已确认整体流程仍有约束 | chief 结合整体目标给有依据的判断，指出具体影响；确认后按决定推进，不盲从最后一句或重复批准 |
| 交付产品/技术文档给干净上下文 Agent | designer 的整体入口说明产品/模块/流程，选定需求有行为/验收；技术链路和契约能指导实施，Reviewer 指出仍需发明的含义 |
| 多角色实现同一用户能力 | chief 通过 instructions/refs 给必要整体关系与正式路径；模块按能力内聚，共用规则单一归属，子 Agent 自主补读 |
| 参考 Pi/其他成熟实现 | investigator 给版本/源码证据及采用范围；designer/developer 复用原生能力，只补实际缺口，不平移整套对象/执行引擎 |
| 小改动与关键跨链路改变 | Review/Test 按适用责任验证真实结果；不重复镜像实现，不以静态检查或模型回复替代 SDK/保存/UI 证据 |
| 新增/修复代码行为，单元通过但真实 API 或 UI 链路失败 | developer 实际执行有意义的 Red → Green，必要重构后保持通过，交付单元证据与适用验收入口；Review 后 tester 独立调用运行服务的 API、操作真实浏览器并观察最终效果，发现链路失败且不以单元通过替代（D-05） |
| 必要 API 集成/UI E2E 环境、入口或权限缺失 | tester 明确 blocked/not_run 与最小补齐事项；chief 处理阻断，正式测试入口变更经 develop → Review → Test，不用单元/Mock 通过收口 |
| 完成后重新开干净会话 | settler 保持入口/权威正文最新，下一次协作能找到已验证成果、依据与未知，历史报告不伪装当前事实 |

数据库夹具证明可靠性条件；模型检查证明主管能合理组织；浏览器与实际环境证明可用。三类证据分别报告。适用产品验收以 productnew/acceptance 为准，不用技术自测代替。

## I5 改契约的处理

本目录唯一字段/语义定义：R1/R2 是公开输入与状态，S2 是持久记录，M2/M4/M5 是委派返回、UI 外层与原生交互，G2 是模型工具，requirements-format 是需求序列化，G4 是上下文装配，prompts 是角色执行指导。产品规则归属按 K-03。其他文档引用，不复制一套不同 Schema。

实施发现 SDK 不支持时，先记录失败试验、受影响契约与最小替代。若替代保持产品含义，可在技术设计审阅后落实；改变产品行为/验收/授权或风险接受，提供具体差异给用户决定。不能用局部代码默默改协议。
