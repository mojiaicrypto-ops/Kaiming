## 本轮继承的方向

- 一个 Server 服务多个项目，统一管理多个独立 Pi Session；模型循环先在 Server 进程内运行。
- Server 保存统一的运行数据库，用户项目保存需求、知识和可迁移的交付记录。
- 继续使用当前锁定的 Pi，暂不升级 1.0，也不将 Durable 作为运行底座；参考其执行意图、结果持久化、恢复与环境抽象。
- 主管自主理解、选择依据、拆分和协调；程序保证真实结果、持久状态、独立验证和必要完成条件。
- 工具执行位置可扩展到 Local、Remote、Sandbox；首版先完整实现 Local。
- 公开协议和事件语义以保留为目标；能否保持现有 UI 不改，必须由后续兼容清单和实际验证判断。

## 开发流程的最新决定

需求确认后先完成适用的技术设计与审阅。已有设计能够覆盖本次需求时复用，不为每个小任务重写整套架构。

开始实施后，主管给出目标、范围、依据路径、依赖和验收；实施 Agent 先制定本任务 Plan，经适用确认后由同一个 Agent 实施。确认遵守项目政策和已有授权，不默认增加用户点击。独立审核和适用测试保持职责与上下文分离。

规划是一项责任，不强制每个任务都建立单独 Planning Agent。技术设计确定实现约束，实施 Plan 确定当前任务的修改步骤与验证；发现要改变共同架构或契约时先处理设计影响。

这些是本次用户已认可的设计输入；通用 dev skill 的修改需另行形成具体规则差异，本轮不直接修改外部 skill。

## 如何评审

重点检查：产品完整闭环是否被支持；每个状态是否只有一个权威；多项目/多会话是否混淆；主管是否仍拥有组织能力；已知成果和未知副作用是否在重启后被正确区分；首版是否引入不必要的框架。

技术架构审阅通过只说明此层方案可继续展开，不能替代契约设计、实施验证或用户对整体架构的确认。工作过程和审阅证据放在 archive/，不作为默认设计输入。
