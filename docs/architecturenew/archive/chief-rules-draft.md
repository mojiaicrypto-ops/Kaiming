# 归档：主管规则讨论稿

本文件是讨论存档，不属于产品规格，不参与默认读取，不作为 Agent 内置规则。

日期：2026-10-02。状态：建议稿，未批准为正式规则，未接入运行代码。

本稿依据本轮讨论与现行产品/工作流整理。它不修改正式角色、流程或验收；提示词、规则文件布局和工具名称均可继续调整。

范围补充：用户随后明确要求优化并实现完整 skill 功能。详见 [完整能力覆盖目标](workflow-skill-coverage.md)。本稿是主管接入示例；下面的分拆结构不是删减能力的依据。当前推荐先保留完整 SKILL.md、references 与模板规则包，再按产品接入优化。

## 1. 本轮设计前提

- Agent 优先：主管自主理解意图、选择上下文、拆分任务、派发角色和组织返工。
- 用户可以自由讨论。明确要求保存时按规范写文档，明确要求实现时进入适用交付流程。
- 主管可提供文档引用、说明、相关需求、已知结论和未知；不限定为固定上下文字段。
- 子 Agent 启动输入为角色规则、基础规则和主管提供的任务上下文，之后自行调查和补读。
- 开发任务必须持久记录，并完成适用的独立验证与结算；任务具体拆分由主管决定。
- 需求文档作为需求事实来源，查询读取文档；本机任务/Session/执行进度留在 Server，不维护另一份需求生命周期权威。
- 用户 action 可以向主管投递明确指令及内容引用，实际业务由 Agent 按规则调用工具执行。

## 2. 推荐规则结构

以下为 AgentDev 安装包内部逻辑路径示例，不是用户项目目录：

```text
rules/
  core.md                    全角色共用的短规则
  roles/chief.md             主管职责与协作方法
  roles/product.md           产品/需求整理职责
  roles/planning.md          规划职责
  roles/frontend.md          前端职责
  roles/backend.md           后端职责
  roles/review.md            独立审核职责
  roles/test.md              独立测试职责
  roles/settlement.md        结算职责
skills/
  project-memory/SKILL.md     初始化与文档组织规范
  requirements/SKILL.md       需求保存、更新、归档规范
  delivery/SKILL.md           交付路线与返工规则
  settlement/SKILL.md         项目事实更新与完成核对
```

核心规则和角色规则作为启动时实际提供的正文；skill 目录提供名称、用途、触发条件和文件位置，详细正文通过读取工具按需加载。目录发现或 skill 注册不等于详细正文已经进入模型上下文。

项目 `AGENTS.md` 提供项目特有约束和导航。通用工作流随安装包维护，项目内容随项目文件维护，避免复制多份通用规则。

## 3. 主管启动规则正文示例

下面是 `core.md + roles/chief.md` 的合并示例，用于讨论，正式实现时拆分去重：

```text
你是 AgentDev 的主管 Agent，负责与用户协作、理解项目、组织专业 Agent
完成工作，并使项目知识随实际交付持续更新。

【讨论与执行】
用户可以自由讨论、调查和比较。讨论本身不自动创建需求、不自动启动开发。
用户明确要求保存时，按对应规则组织并保存；明确要求实现时，组织适用流程。
保存需求与启动实现分别理解。模型发现的新需求先作为建议，不自动扩大工作。
用户的明确自然语言指令与对应按钮答复都可以表达授权，不重复询问已明确的意图。

【理解项目】
根据项目 AGENTS.md 和索引定位相关事实，按任务读取详细文档与代码。
区分用户意图、已确认设计、实际实现、验证结果和未知。
你自主选择任务上下文，可以组合多个相关需求、约束、来源和调查结论。
不要为了建立全面理解而默认读取全部文档或复制全部历史聊天。

【组织专业工作】
根据任务调用适用角色。委派时给出明确目标、执行范围、必要说明和来源。
子 Agent 有独立 Session，自行读取和核对依据，可以补读并提出异议。
Review/Test 使用独立上下文，不能依靠开发聊天或开发自评证明正确。
是否拆分、并行、补充调查及范围内返工，由你依据工作流自主判断。

【任务与交付】
开始开发前读取交付规则，使用任务工具建立或关联持久任务。
通过派发及结果工具记录实际进展；以保存的任务进展和真实结果决定下一步。
开发结束后继续组织适用的独立审核、测试与结算。
审核或测试失败时组织修复并重新验证，不能把失败结果改写为成功。
结算未完成时，保持任务未完成并报告剩余工作。
会话恢复时先查看未完成任务，再决定继续、调查或请求用户决定。

【文档与项目记忆】
保存需求或修改正式文档前，读取对应文档规则和相关项目索引。
优先更新已有权威文档；新增或拆分时按功能/技术职责组织并维护引用与索引。
保留未知与来源，不将讨论建议写成已实现或已验证事实。
结算必须更新受影响的当前知识、入口和需求摘要，不能只生成完成总结。

【结果】
依据真实工具结果、文件和验证证据报告成功、失败、阻断与未完成项。
子 Agent 的执行结束不等于整个开发任务完成。
```

小修改与复杂交付的具体路线仍以适用工作流为准，详细条件放在 delivery skill，不在多个系统提示中重复维护。

## 4. 详细规则的触发

| 当前意图 | 读取规则 |
|---|---|
| 自由讨论/只读调查 | 基础与主管规则；按需读项目依据 |
| 生成/初始化/拆分项目知识文档 | project-memory |
| 将讨论保存为需求、更新或归档需求 | requirements；涉及文档重组时补读 project-memory |
| 启动代码修改、修复、审核或测试 | delivery 及对应角色规则 |
| 更新交付后的项目事实并完成工作 | settlement |

触发原则放进常驻规则；具体字段、目录与编写方法保存在详细规则。程序不需要理解每次自然语言的全部业务语义来决定 skill，主管按规则选用。

## 5. 如何接入 Pi Session

创建主管 Session 时：

1. 提供 Pi 的基础运行提示，以及 AgentDev 的核心/主管规则。实现时应保留 Pi 原有工具使用指导，避免替换提示时无意丢失。
2. 提供已信任项目的 `AGENTS.md` 内容及明确的项目根、文档入口和规则目录位置。
3. 注册内置 skills 的入口信息和读取能力。
4. 注册文件、任务、委派和交互等实际工具。名称、参数与返回语义由工具定义提供，不要求模型从普通文本猜调用格式。
5. 用户消息、action 答复、子任务结果和未完成任务摘要进入本次执行输入，不永久拼进系统提示。

创建子 Agent Session 时采用相同基础规则，加对应角色规则及主管任务输入；不复制主管的全部会话。

恢复已有 Session 时同样提供当前安装包规则和项目入口，并读取持久任务现场；不能只靠旧会话历史保留流程责任。规则更新对活动任务的生效时机后续确定。

## 6. 与工具的连接

提示词必须明确什么时候调用什么能力；工具必须真实存在。建议的最小能力是：

- 文件读取/写入：读取规则和项目事实，按规范产生文件。
- 任务能力：建立/查看开发任务，记录进展，提交最终完成。
- 委派能力：按角色创建独立执行，持久关联任务和结果。
- 交互能力：提供用户 action；答复回到主管，继续按规则执行。

派发和子任务结果提交可顺带记录进展，避免同一事实依赖额外重复调用才保存。收口工具检查适用验证与结算结果是否齐全。具体工具 Schema 和最终阶段路线尚未冻结。
