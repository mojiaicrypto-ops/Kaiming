# 归档：协议讨论

本文件是讨论存档，不属于产品规格，不参与默认读取，不作为消息协议依据。

记录日期：2026-10-02。状态：用户认可总体方向，细节待讨论。

本文件是架构讨论记忆，不是正式协议、实现 Plan 或已实现功能说明。正式依据仍以 [文档索引](../INDEX.md) 为准。本轮仅保存讨论，不修改 UI、代码、正式协议或门禁规则。

## 1. 本轮上下文

- 用户已基本认可统一 Server/Runtime 管理多个 Pi Session 的运行结构，下一步讨论消息与业务协议。
- 已读取现行 `docs/architecture/protocol.md`，梳理公开 RPC、事件订阅、内部执行接口和 HTTP 接口；旧文档将业务操作与跨进程调用统一列为协议方法。
- 本轮聚焦协议边界及扩展入口，不重新开展 Durable/Pi 上游能力验证，不冻结完整实体 Schema。
- 讨论基础：Pi 提供 Agent 消息及执行事件；AgentDev 提供产品归属、运行管理与业务能力。Pi 能否直接复用某种确认机制尚未核实。

## 2. 已认可的分层方向

### 基础消息层

- 尽量复用 Pi 原生用户/助手消息、工具调用与工具结果，以及执行事件，避免重新定义整套 Agent 消息再来回转换。
- AgentDev 在外层补充必要的项目、Session、执行归属与顺序信息；具体字段和排序范围未定。
- 不把 UI 事件保存等同于执行恢复日志。保存消息、工具操作意图、结果与 checkpoint 的职责需要分别确定。

### Runtime 与协作调度

- 持久化和恢复是 Runtime 实现机制；协议仅表达相关操作意图、结果与状态，不描述存储算法或恢复步骤。
- 调度是运行行为。`assessment.submit`、`agent.dispatch`、`stage.submit` 本质是工作评估、Agent 分派和交付，不属于基础消息格式。
- 这些行为过去因跨进程调用被协议化；新运行结构可以采用服务调用，Agent 需要触发时通过 tool 暴露业务能力。
- Session/Run 生命周期未定：此前“一 Run 一专业 Session”与后续“持续 Session、多次执行 Run”建议需要统一，暂不将任一方案视为最终决定。

### 确认与业务扩展

- 权限门禁确认预留交互接口；可以评估复用 Pi 能力或自定义，尚未决定。
- 产品独有操作采用明确业务命令，如“将讨论加入需求队列”“开始实现指定需求/迭代”，不伪装为普通 Pi 聊天消息。
- 用户认可聊天机器人式交互：内容配按钮，点击后统一回传动作，由服务端执行对应业务。

## 3. 初步对象：Message、Interaction、Action

- Message：Agent 消息内容，基础载荷优先沿用 Pi。
- Interaction：附加交互卡片，表达正文、选项、按钮及处理状态；不要求写入 Pi 的模型上下文。
- Action：可选择的动作，页面展示 label/style，服务端保存其业务含义。

示例仅用于讨论，不是冻结的 wire schema：

```json
{
  "type": "interaction",
  "interactionId": "int-123",
  "projectId": "project-1",
  "sessionId": "session-1",
  "messageId": "message-20",
  "kind": "actions",
  "text": "将这次讨论放入需求队列？",
  "status": "pending",
  "actions": [
    { "actionId": "action-1", "label": "加入需求队列", "style": "primary" },
    { "actionId": "action-2", "label": "暂不处理", "style": "secondary" }
  ]
}
```

页面只需理解通用交互结构，不承担具体业务执行逻辑。项目归属和用户身份仍由服务端核验，不能因载荷中有 ID 就视为已授权。

## 4. 通用按钮回调

初步建议统一入口 `interaction.respond`：

```json
{
  "method": "interaction.respond",
  "idempotencyKey": "click-123",
  "params": {
    "interactionId": "int-123",
    "actionId": "action-1"
  }
}
```

服务端解析动作对应的业务命令，例如：

```json
{
  "type": "requirement.enqueue",
  "input": {
    "sourceMessageIds": ["message-18", "message-19", "message-20"]
  }
}
```

流程：生成交互 → 页面渲染 → 点击回传动作 ID → 服务端校验并解析 → 调用业务服务 → 返回结果并更新交互。

- 页面回传动作 ID，不携带任意可执行方法、脚本或可随意修改的业务参数。
- 服务端检查项目归属、调用主体、动作是否仍有效，以及当前业务前提是否成立。
- 重复点击应返回已有结果，避免重复创建需求或启动执行；幂等键与动作单次消费的具体配合尚未设计。
- 过期动作提示重新获取；处理中与完成后更新原交互，避免按钮看起来仍然有效。
- `interaction.respond` 是入口适配，不应成为所有业务逻辑聚集的地方。

## 5. 业务命令独立于交互入口

| 示例命令 | 意图 |
|---|---|
| `requirement.enqueue` | 从讨论形成需求并加入队列 |
| `requirement.start` | 开始实现指定需求 |
| `iteration.start` | 开始指定迭代 |
| `execution.cancel` | 取消执行 |

以上名称均未冻结。业务服务可以由聊天按钮、独立页面操作或 Agent tool 调用；这些入口共享业务语义与校验，不要求每次调用先生成交互卡片。

## 6. 第一版交互范围建议

- `actions`：操作按钮。
- `confirm`：批准/拒绝等确认。
- `select`：从有限选项中选择。
- 状态初步建议 `pending / submitted / resolved / expired`，失败、重试与并发处理细节待定。
- 权限确认复用交互外壳；真正的批准范围、有效期和执行准入由权限服务负责，普通按钮点击不自动成为通用授权。
- 先不建设通用表单、页面布局 DSL 或自定义前端回调脚本。优先稳定“内容＋动作＋统一答复＋状态更新”。

## 7. 后续待定

1. Pi 版本对应的消息/事件类型及确认机制，哪些直接复用、哪些仅适配。
2. 身份封套的最小字段、Session/Run 生命周期与事件顺序范围。
3. Interaction 是独立资源还是消息附件；持久化、重连和原消息关联方式。
4. 动作是否一次性、处理中如何反馈、失败是否允许重试，以及如何避免并发重复执行。
5. 业务输入/输出和错误的统一形状；长操作的接受与最终完成如何区分。
6. 已存在 UI 协议的兼容方式：新交互结构是否需要 UI 扩展，不能默认现有页面已经支持。
