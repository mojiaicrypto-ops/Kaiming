# 初始化、模块化知识与需求编写规则

触发：初始化项目、保存需求、写正式产品/技术文档。执行前 read 本文及项目 `.dev/INDEX.md`、相关模块索引；位置不存在先说明，初始化按用户批准的差异写。

1. 固定根 `.dev/`，各位置职责按 knowledge.md 的目录。初始化使用模板，保留 AGENTS 原文，追加托管入口和参数；没有调查的代码/测试位置写未知，不推测项目能力。用户确认初始化差异后写文件，再 project_ready 登记 ready；文件存在本身不伪造初始化批准。
2. 先定位已有权威，再决定新增/拆分。按独立用户能力或技术责任内聚；共用约束集中定义、引用，避免按聊天、页面、前后端分别复制完整需求。同一事实只有一份完整定义。
3. 正式模块用 `## 定义` 与末尾 `## 实现与验证`：前者写职责/边界/行为约束/验收依赖，后者写代码测试/设计实现验证状态/证据差距，不在事实区段藏新定义。调查只产事实/未知，不能升级为用户承诺。
4. 保存需求使用 templates/requirement.md 固定 YAML 字段与章节。ID 稳定、文件名匹配；status 初始 queued。写目标、范围、可观察行为、失败、验收、来源/决定、未知。已有模块引用，不复制全文。资料不足可保存草稿，但开发前必须明确行为/验收。
5. 自己发现的额外需求未经用户同意只列候选；明确保存指令不再要求同一按钮确认。保存不等于启动。
6. 编辑已有文档先 read 取得 contentHash，再 write/edit 携 expectedHash；冲突重新读取并协调，不盲目覆盖。新增/拆分后更新最近索引和必要上级链接。
7. 写后读回、检查 YAML/引用、查询是否可读。专业角色 agent_result 提交真实文件清单与证据，由主管 project_publish。主管直接保存需求时可自行发布需求文件/入口；正式模块修改交给专业角色。无 Git 或提交失败区分报告，保留本机文件与重试入口，不重建需求。
8. 当前知识只放最新事实；work 放详细证据；完成/取消/归档写摘要及引用，不按状态移动需求。队列查询读取文件，不能指望一句“保存成功”让程序同步。

工具：read/edit/write；专业角色最后 agent_result，需要决定交主管。主管使用 user_request/project_publish，并根据真实读取/发布结果向用户报告。
