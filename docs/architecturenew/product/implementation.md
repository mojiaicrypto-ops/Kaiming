# 需求到实施的顺序

本页是开发交接与退出条件，不是代码实现 Plan。用户批准本套需求后，Planning 按下表形成实际 Plan，选择模块/库并锁定依赖。所有单元需要独立 Review、实际检查与结算；不能以模板/文档存在代替实现。

| 单元 | 依赖 | 实际输出 | 退出条件/验收 |
|---|---|---|---|
| I0 Pi 适配探针 | 产品需求批准 | 锁定 Pi 版本；create/open、cwd、工具/规则注入、事件、busy 输入、abort/恢复的可运行样例 | 两项目/多 Session 实际隔离，恢复指定文件；列出已验证 API 与缺口，不做界面 |
| I1 项目与中央记录 | I0 | 中央 DB、项目 realpath/信任/初始化状态、主管 Session 列表/指定恢复、角色配置 | 目录唯一/错误、信任/初始化、指定Session与模型配置子条件通过；运行task/恢复条件在I3/I6收口，无模型仍能查询 |
| I2 项目知识与需求 | I1 | 固定目录/模板、文件原子写/CAS、YAML 解析、文件查询和变化刷新、Git 发布 | AC-M01～M06及M07文件查询部分通过；M07启动部分在I3/I4收口，无第二份需求事实 |
| I3 task 与专业会话 | I1/I2 | task 工具、派发/结果/wait、独立角色 Session、单工作区写约束、结果归档与通知 | 派发/结果/去重/角色隔离/持久进展子条件通过；完整路线与finish在I4收口，不实现通用任务图引擎 |
| I4 验证与结算 | I3 | 最终目标指纹、独立验证结果、返工、结算与发布/finish | AC-T01～T07、A01～A03、S01～S03的交付条件通过，M07启动闭环收口；轻量/标准/document真实完成 |
| I5 消息和 action | I1/I3 | 请求幂等、Pi 封套、Server 事件、快照重连、action 答复 | AC-E01～E05 通过；按钮只是统一答复入口 |
| I6 中断接续与复盘 | I3/I4/I5 | 输入/通知未处理记录、Server 重启接续、未知效果阻断、完成中断核对、复盘/清理约束 | AC-R01～R04、S04 通过；实际 kill/restart 故障演练 |
| I7 完整工作台验收 | I2～I6 | 消息、项目/需求/任务/证据/设置的可用客户端与错误反馈 | acceptance.md 全部执行，真实 Provider 和浏览器走完整旅程；不存在缺失必需能力却宣称完整 |

早期单元只验证已经交付的子条件，跨单元用例标 PARTIAL 并列待覆盖子句，不能提前记完整 PASS。I7 对完整用例重新核对及补齐；没有为前序退出反过来依赖尚未开发的后序能力。

每个单元的 Plan 必须列需求编号、修改范围、角色、检查命令/场景和不做什么。代码包拆分是技术选择，但不得把每份产品文档变成一个独立 Runtime 服务。

首条纵向路径先做：打开项目→信任/初始化→保存需求→standard task→专业实施→Review/Test→结算→新会话读取。再补 compact/document、错误和故障场景；不要先搭一个大调度框架再寻找业务。

技术边界：Pi 会话和流复用 SDK；业务 task/结果使用中央持久记录；文件查询负责需求列表；宿主工具适配器留远程执行入口。库版本和具体 SQL Schema 在实现 Plan 确定，产品字段/行为按 contracts.md 不变。
