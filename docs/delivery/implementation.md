# 实施工作包与交付规则

## 1. 开发入口

先读文档索引与产品方案，选择工作包后只加载关联产品、规则、架构和验收。每工作包形成实现Plan，列实际文件、任务DAG、接口、权限、验收ID、检查命令及回退；已明确的产品契约直接执行。发现实现冲突先形成具体问题与证据，产品语义变化由人决定。

代码写入遵循适用L1/L2/L3；每个实际专业角色由主管独立调度。实现Plan决定函数与文件内部结构，不重新发明产品字段、状态、授权或用户行为。共享Schema先于客户端/服务端分开实现。

## 3. 工程检查命令

根package.json提供以下脚本，WP-00建立并在各包增加后接入：

| 命令 | 执行范围 | 通过条件 |
|---|---|---|
| pnpm install --frozen-lockfile | 固定依赖 | 锁文件一致且安装退出0 |
| pnpm typecheck | 全Workspace tsc --noEmit | strict无错误 |
| pnpm lint | TypeScript与格式 | 退出0 |
| pnpm test:unit | Vitest领域/Schema | 全通过 |
| pnpm test:integration | SQLite/Git/Pi/WS/容器 | 全通过，失败无残留工具进程 |
| pnpm test:e2e | Playwright+真实Core+Provider桩 | UI与协议一致 |
| pnpm test:acceptance | fixture及AC证据汇总 | 必需AC全有结果，无未处置失败 |
| pnpm test:live | 用户已配置的真实Provider纵向演练 | HTML、L1、L2+结算三路径成功 |
| pnpm docs:check | Markdown链接、Schema引用和需求映射 | 无断链或未定义引用 |
| pnpm build | daemon/runner/web/cli | 可启动发布产物 |

命令是待交付工程接口，当前仓库原型不具有这些脚本。开发Agent必须在相应工作包实现它们；报告中区分文档检查与真实运行检查。

## 4. 完成证据

每个Task保存Plan/CompactPlan、实际Diff、独立Review、适用Test/Check、Settlement。每次测试记录AC ID、命令/步骤、输入Revision、环境/镜像、退出状态、输出Ref与Hash。最终发布以所有工作包和完整验收矩阵为准，不以页面数量或Agent口头完成为准。

## 5. 变更处理

可内部决定：模块内部函数拆分、等价实现、在固定接口范围内的优化。需先更新规范并确认：用户行为、数据含义、角色权限、交付门禁、风险接受。已经给出的数值默认为可直接实施的基线，性能测量需要调整时保留原结果与新验证，配置范围内覆盖按规则生效。
