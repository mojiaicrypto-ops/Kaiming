# AgentDev Workspace 产品方案

版本：2.0。适用：单用户正式交付版。产品行为由本文件及所链接的规则定义；技术与验收入口见 [文档索引](../INDEX.md)。

## 1. 产品与用户结果

AgentDev 是可在个人电脑或个人服务器运行的 AI 研发工作台。用户通过主管 Chief 自由讨论项目、调查实现、生成说明产物、设计产品和交付改动。主管基于共享项目知识理解请求，选择专业角色与模型，决定各独立 Agent 的任务和注入上下文，并协调结果。

产品向用户提供三个结果：随时了解当前产品及其实现；以匹配任务影响的流程完成工作；新会话可从更新后的知识继续研发。

## 2. 能力结构

| 能力 | 用户结果 | 规则 |
|---|---|---|
| 主管协作 | 问答、调查、比较、HTML说明及附件产物 | [交互](experience.md) |
| 项目知识 | 产品全貌、功能状态、模块关系、代码和测试入口 | [知识](knowledge.md) |
| 专业Agent | 按职责配置不同模型，独立上下文执行 | [角色](../rules/agents.md) |
| 分级交付 | 轻量修改、标准开发、高风险开发 | [路由与流程](../rules/workflow.md) |
| 工作台 | 项目切换、需求看板、版本化产物、文件、运行和决定 | [交互](experience.md) |
| 可靠运行 | 界面断开后继续、权限控制、异常恢复 | [执行](../architecture/execution.md)、[恢复](../architecture/reliability.md) |

## 3. 核心对象

| 对象 | 含义 | 生命周期/归属 |
|---|---|---|
| Project | 一个规范化仓库根或目录及其产品知识 | 项目隔离边界 |
| Conversation | 用户与主管的连续对话 | Project拥有；用户创建/切换 |
| Work | 一次工作请求的内部记录 | 问答、产物、文档维护或交付；所有Run有workId |
| Feature | 持续演进的产品能力 | 正式文档维护当前状态，关联历次需求 |
| Requirement | 随Git迁移的产品改变及历史摘要 | Queued、Active、Completed、Cancelled、Archived；[需求池规则](requirements.md) |
| Task | 一项可独立执行验证的修改 | 属于Work，可引用Requirement |
| Role / Profile | 固定专业职责与模型工具配置 | 每个角色可独立覆盖配置 |
| Run / Attempt | 一次角色工作与一次实际运行尝试 | 独立Session、快照、权限、预算 |
| Artifact | 说明、Plan、Diff、Review、Test等产物 | 不可变版本及有效性 |
| Decision | 用户对特定版本/范围的决定 | 来源消息或明确按钮动作 |

Work是内部追踪记录，问答和小修改直接在Chief对话中展示。Requirement进入需求看板；L2/L3交付均关联Requirement。独立L1修改使用一个Work和一个Task；已有Requirement内的L1修改关联该需求。

## 4. 用户旅程

### 4.1 理解与生成说明

用户询问现有模式并要求HTML架构说明。Chief读取相关知识与代码，必要时委派后端调查、前端制作说明；所有子Agent各有独立Context。Chief交付带来源的解释及可预览下载的HTML Artifact。该工作按直接协作完成，保存文件到Artifact目录不触发研发流程。

### 4.2 新项目

创建目录 → 讨论用户/问题/边界 → 确认产品结论 → 保存产品总览及功能目录 → 明确启动功能 → 分级计划/开发/验证/结算。确认设计与已实现能力分别标注。保存设计结论可独立完成，与启动开发分别授权。

### 4.3 旧项目

打开目录 → 确认信任 → 有界调查入口 → 生成能力导航、来源和未知 → 校正必要产品意图 → 按当前任务深入。首次使用可先回答具体问题；初始化只补齐必要知识。具体范围和预算见知识规则。

### 4.4 小改动

用户明确替换普通错字。Chief判为L1并记录一句话Plan，触发相应独立执行Agent、独立Review和Settlement。用户收到实际Diff、检查结果和完成摘要。流程无需表单、单独Planning/Test角色或看板建单。

### 4.5 功能交付

用户明确目标并启动Requirement。Product、Planning和开发角色按适用Gate独立执行；Review读取冻结代码及正式依据，Test执行真实检查，Settlement更新知识。主管显示当前进展、必要决定和最终结果。范围内返工自动继续。

## 5. 人工决定与自主工作

人控制产品意图、开发承诺、权限与风险接受。明确的自然语言执行指令与按钮授权等价；已有授权范围内执行和验证由Chief自动协调。系统把来源、目标、范围和版本持久化。缺少授权时可调查或提出选项；沉默不产生授权。

产品结论确认后可立即写入设计事实；实现、验证与已知差距随实际证据更新。任务执行不会因另一个Conversation打开而停止。

需求池及已完成需求摘要属于Git正式知识；新服务器Clone后无需旧聊天和数据库即可展示。执行现场独立恢复，详见[需求池与迁移](requirements.md)。

## 6. 发布能力与完成定义

本版提供单用户、多项目、自托管Web工作台、八固定角色、一个Git根内的代码与正式文档、Workspace/Autonomous/Full Access执行模式、一层Chief子Agent调度、内置扩展接口及可恢复后台运行。项目接入后的修改通过AgentDev进行。客户端协议同时服务Web及本机CLI；图形TUI不属于本版验收项。

Requirement完成要求适用Gate通过、最终版本证据一致、知识和入口更新、阻断项关闭。产品版本发布要求 [验收目录](../delivery/acceptance.md) 全部适用用例通过并保存证据。当前仓库的实现起点见[文档索引](../INDEX.md)，文档规范与运行能力分开管理。
