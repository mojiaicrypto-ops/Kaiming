# AI 说“完成了”，然后呢？从会写代码到可交付的 Agent

你让 AI 补一个功能。它改了代码，跑了测试，最后回复：“已完成，全部通过。”

你打开页面，才发现按钮有了，关键流程没接上；正常情况能走，失败后用户却不知道发生了什么。再追问测试怎么做的，它确实运行了测试，只是那些用例恰好都在验证它自己对需求的理解。

几轮修补之后，终于能用了。过几天换个会话，新的 Agent 不知道当时为什么这样设计，也不知道哪些边界仍未验证。你又成了项目的人工记忆：重新解释需求、翻聊天、辨认哪一句“完成”值得相信。

这些场景背后有一个共同问题：**我们把“执行结束”“检查通过”和“用户目标达成”，当成了同一件事。**

它们之间其实隔着一条需要被证明的链路。开始写代码之前，Agent 是否找到了完整、有效的需求，也需要有依据。代码写出来了，未必实现了正确行为；测试运行过了，未必能识别错误；这次确实做对了，也未必留下足够依据让下次继续。

在“开明”这个项目里，我们尝试围绕这条链路设计一个持续推进软件项目的 AI 工作台。模型能力当然重要，但我们更关心另一个问题：怎样让一次生成，成为可以核对、可以追溯、可以接续的交付？

## 从用户拿到什么，反推系统需要什么

先不谈多 Agent，也不谈工作流引擎。假设我们把一项工作交出去，最后究竟要拿到什么？

首先是实际成果：功能能用，或文档足以支持下一步。其次是可信的边界：检查过哪些情况，哪里失败，哪里还不知道。最后是可接续的项目：换一个人或会话，仍能找到当前行为、实现位置、验证证据和下一步。

由此反推，交付系统必须保存的就不只是对话。它要保存目标和验收，区分执行与检查，保留实际证据，并把确认后的结果写回项目知识。这些机制分别消除一种具体的不确定性，不能靠一段更有把握的总结互相替代。

用一个**假设案例**贯穿全文：给业务系统增加“导出订单”功能。以下要求只是为了说明方法，不代表开明实际交付过这个业务功能。

假设用户已确认：导出结果遵循当前筛选条件，只包含账号有权查看的订单；成功时能下载有效文件；失败时明确提示，并允许再次尝试。

如果只看实现动作，新增按钮、接口和下载逻辑，就很像做完了。如果看用户结果，问题会具体得多：文件里的订单是否符合筛选？有没有混入其他账号的数据？服务报错时，页面会不会仍然显示成功？再次点击是否还能工作？

**完成标准必须先于实现存在。** 否则，“完成”就会悄悄变成“当前代码已经做到的那些事情”。

## 把工作从聊天里拿出来

聊天适合表达意图、讨论取舍，却不适合独自承担交付记录。一段对话可能穿插多个目标，包含被放弃的建议、临时判断和后来修正的结论。下一位 Agent 不应该靠重读整段历史，猜出哪一版才生效。

因此，开明把一次正式工作组织为 Task：保存这次要达到的目标、适用依据、当前阶段、参与角色和交付报告。Task 的边界是一次明确的交付，不是把整个项目塞进一个永远结束不了的任务。

围绕 Task，主管保存一份与规模相称的 Plan。它最关键的两部分是验收和范围：什么结果算完成，这次允许改哪里。导出功能的验收来自已确认的业务要求；范围则约束实现落在哪些模块，是否涉及已有权限规则或接口契约。发现依据不足时，应补设计或请求用户决定，不能由开发者自行补出产品承诺。

Plan 不必很长。明确的小修改可以用一段话说清楚；复杂工作才需要展开依赖、角色和风险。用户已经明确授权的目标，主管可以在范围内推进，没必要每一步重复批准。但改变目标、验收或重要契约，不能藏进“顺手优化”里。

待办、规格和 Task 也各有用途：待办记以后可能做什么，规格定义应有行为，Task 组织本次交付。明确的小修复可以直接建立 Task，不必先造一条待办。只讨论建议，也不必自动启动开发。

入口可以轻，交付依据要清楚。否则，再完整的看板也只是把模糊工作换了一个展示位置。

## 文档也是给 Agent 设计的工作界面

有了 Task 和 Plan，还要回答：其中引用的需求，Agent 能不能找到、读明白？把全部文档、聊天和代码塞进长上下文，并不能自动解决这个问题。当前规则、旧提议和无关模块混在一起，关键约束更难辨认，理解需求的注意力也可能被稀释。

[《Lost in the Middle》（TACL 2024）](https://aclanthology.org/2024.tacl-1.9/)在所测的多文档问答与键值检索任务中发现，相关信息的位置会影响表现，位于长上下文中间的信息可能更难被有效利用。这提醒我们“能装下”不等于“能稳定用好”，但不能据此断言所有当前模型、所有代码任务都会按固定规律退化。

因此，在开明的设计里，文档组织也是开发前的基础工作。产品需求按长期用户能力内聚，技术说明按明确职责组织。订单筛选、导出行为和失败重试应在所属能力中说完整，不能仅因前后端分工就拆成两份产品定义；也不按页数或聊天轮次机械切文件。模块是长期知识边界，交付切片是本次可验收的目标，两者不必一一对应。小项目用几段规格和一行模块地图就够，无需预建空目录。

如果起点是一份总需求，拆分时还要交代原文各部分的去向：进入哪份规格、对应哪个切片，哪些尚待决定，哪些已明确不做。否则，文件变短了，需求却可能丢了。确认以模块规格为后续依据后，原文保留供追溯，不再并行维护另一套生效规则。

格式也应服务查找和判断。结构化 Markdown 可以用稳定标题标识一项行为，让 Task 引用具体章节；读者应能定位职责与边界、正常结果、异常处理、验收要点、实现状态和未知。产品规格回答用户会遇到什么，技术规格回答接口、依赖和实现约束。格式本身不会让模型正确，但能让缺项和冲突更容易被看见。

共享权限规则只在一个权威位置完整定义，订单导出引用它；待办和 Plan 也引用规格，不各自改写一套规则。设计要求、观察到的实现和实际验证分开记录，尚未核实就保留未知。否则，一份排版整齐的文档，也可能把猜测包装成事实。

## 按模块理解，才有条件独立开发

拆成许多文件之后，如果仍然要逐个打开才能知道该读什么，问题只是换了位置。索引要告诉 Agent 三件事：路径在哪里、这份资料负责什么、什么时候需要读。模块地图再把职责、规格、代码位置和对外接口连接起来。它们负责导航，正文仍保留在原权威位置，避免索引变成另一份逐渐过期的需求。

一条简洁的阅读路径可以是：**项目入口 → 模块地图 → 目标模块规格及必要接口 → 本次 Plan → 相关代码与测试。**

沿用订单导出的假设案例，开发 Agent（developer）先读负责模块的行为和验收，再读筛选语义、共享权限契约、相关实现与测试入口。不默认加载支付、营销等无关模块，无须重读总需求原文，也不靠设计聊天猜最终决定。主管选择最小但充分的依据，开发者遇到依赖或未知可以继续补读；发现行为尚未定义，就先补设计。按需加载的目标是保留必要约束，让它们更容易被使用，不能为了省 token 删掉权限边界。

这样的上下文才支持独立开发。先明确规格与共享接口，再切出可以独立验收、写入集中、依赖清楚、一次 Review 能覆盖的工作。例如下载交互依赖已明确的导出接口与错误语义，服务端依赖既有筛选和权限契约；各自可以在独立上下文中推进，不必反复向同一段聊天确认含义。

独立开发仍然有依赖。接口含糊时，两边各自猜测，只会把分歧推迟到联调。需要协作时，同一 Task 内要声明各成员写入范围，协调重叠与依赖；最终还要检查组合后的筛选、权限、下载和重试路径，不能把各自“通过”相加就当成整体通过。

文档、索引和切片在这里形成一条连续的准备工作：先让需求能够被独立理解，再让实现能够被独立推进，最后让成果接受独立检查。接下来，检查本身也必须经得起质疑。

## 测试全绿，为什么仍然不够

回到订单导出。开发者先写一个函数，再用函数当前返回的内容作为期望值；或者 Mock 一个成功响应，只断言下载方法被调用。这样的用例即使全绿，也可能没有回答“筛选和权限是否正确”。

问题不在于测试是 AI 写的，而在于测试与实现共享了同一个未经核实的假设。两者彼此吻合，并不能证明它们吻合用户要求。

因此，审核首先要问：**期望值从哪里来？**

在假设案例中，筛选规则和可访问范围应来自已确认的验收与权限事实。可以准备一组独立可控的数据：筛选内且可访问的订单、筛选外的订单、无权访问的订单。检查结果应与预先确定的应导出集合一致，同时满足筛选与权限约束，而不是把程序第一次导出的文件保存下来，当作以后永远正确的答案。

数据会变，断言也不一定非要写死一串 ID。集合相等、范围、唯一性、引用关系等不变量，往往更能表达真正的业务规则。但关系断言同样需要依据，不能因为写得抽象，就默认它正确。

还有一个更尖锐的问题：如果结果是错的，这个检查真的会发现吗？

可以给导出文件检查器喂一份刻意混入越权订单的坏文件。检查器必须真实拒绝，并指出越权记录。若它仍然通过，就说明“检查通过”没有足够区分力；若它因为文件打不开、依赖缺失或超时而报错，也不能算识别出了权限问题。

这就是负向控制的意义：让已知错误因预期原因失败，检验检查本身是否有效。报告需要保留输入、命令、实际观察和拒绝原因，不能只留下一个通过数量。

失败反馈同样如此。让服务返回明确失败后，需要观察页面是否提示错误、是否恢复可操作状态、是否还能重试。只证明成功下载过一次，覆盖不了这些要求。

单元测试和 Mock 在这里仍然有价值。它们适合开发阶段快速定位逻辑、复现缺陷，让局部行为经历有意义的先失败、再通过。但它们的证据有边界：Mock 成功证明的是替代依赖下的行为，函数返回正确证明的是局部逻辑，均不能直接证明真实服务、权限数据、浏览器和下载文件组成的整条路径正确。

适用的独立 Test 要从真实入口走到最终结果：API 变化观察运行中服务的响应及业务效果，页面交互观察浏览器里的操作、状态和产物。环境缺失就记录阻断或未执行，不能用局部全绿替换端到端验收。

负向控制也不是正确性的保证。一个坏样本被抓住，只说明这一类已知错误能被识别；未知缺陷和遗漏的需求仍可能存在。它的价值是减少自证循环，不是颁发一张“绝对正确”的证书。

## 独立检查，要独立到哪里

最容易实现的“多 Agent”，是让另一个角色阅读作者总结，再回复一份审核意见。角色名称变了，判断却可能仍被同一套解释牵引。

开明要求 Review 使用独立上下文，读取目标、Plan 的验收和范围、正式依据、实际成果与真实证据，不读取作者或主管聊天中的自评。审核者需要自己建立判断：这次导出要求是否完整，实际改动是否越界，测试的期望值是否有独立来源，证据是否真的支持结论。

标准代码工作的 Test 在 Review 之后执行，独立验证用户结果及相关回归。发现缺陷，返回开发修复，再重新审核和执行适用测试；不能修改了成果，却继续借用旧报告证明现在的版本。

这里的独立，是责任和信息来源的独立。同一模型可以承担不同角色，换一个模型也不能自动产生独立证据。多个模型若都照抄同一份错误验收，仍然可能一致通过。隔离上下文能减少作者叙述带来的偏向，却不能保证零漏检，验收本身也必须接受质疑。

因此，多 Agent 的价值不能用数量衡量。我们需要的是：**执行者的结论，有机会被另一个上下文依据实际成果推翻。**

## 程序守住事实，模型承担判断

仅靠提示词要求“先审核、再测试、最后结算”，仍然留下一个问题：这些事情到底发生过没有？

程序擅长核对可观察的事实：报告是否存在、提交者是否属于当前 Task、必要成员是否停稳、文件是否保存、被审阅的交付物后来是否改变。这些不应该依赖主管在聊天里回忆。

模型则承担业务判断：验收是否满足，越界改动是否合理，问题是否闭合，用户授权是否覆盖当前动作。程序能够检查 Plan 有没有验收一节，不能由此知道验收写得是否充分；能够确认测试报告存在，不能由此知道测试有没有按用户要求设计。

在实现层，开明把 Review/Test 与程序观察的交付状态关联。被审阅的交付物发生变化，旧结论就不能继续作为完成依据。结束时还要核对适用报告和实际保存；有 Git 的项目，已复核交付路径是否相对 HEAD 提交，也属于可观察的事实。

这些事实门可以阻止一部分没有证据的收口，却不会自动识别所有假测试。报告内容的质量、期望值的来源和业务结果，仍需要主管与独立 Agent 判断。提示词约束与程序强制也必须分开表达，不能因为规则写进文档，就宣称模型已经稳定遵守。

## 流程的重量，应该与风险相称

如果改一个按钮颜色也要跑完整套产品验收，流程会很快失去使用价值；如果改权限规则只测按钮能不能点，流程又失去了保护作用。

所以，代码与展示类工作在 Plan 中选择验证档。`visual` 适用于不改变事件、状态、请求和数据，也不修改公共布局或共享设计令牌的纯展示变化：独立 Review 后结算，不建立 Test 阶段。`focused` 面向一个局部行为，开发做定向检查，页面交互再走一条聚焦浏览器路径，独立 Test 覆盖本次验收与相关回归。`broad` 用于共享契约、迁移、权限或状态机等高风险变化，才有理由扩大到全量或跨模块验证。

假设的导出功能涉及权限契约，就不能因为界面只多了一个按钮，把它算成轻量修改。反过来，纯文稿和正式设计文档走独立审阅与结算，不需要虚构代码测试。只读调查保存结论、来源与未知，也不必经过完整开发链。

减少无关检查，才能把注意力留给真正可能出错的地方。轻量化应削减无关成本，不能削掉当前工作必需的责任。

同样的原则也约束系统本身。开明使用 Pi 的 coding-agent SDK 承担模型循环、原生工具与历史，工作台围绕 Task 保存协作和交付事实；浏览器与外部 Agent 的 MCP 接入复用同一条责任链。没有必要为了管理流程，再造一套通用工作流 DSL，或为每个例外新增对象和审批类型。每增加一个机制，都应该能说明它解决了当前哪个具体问题。

## 交付的最后一公里，是让项目记住

即使导出功能已经通过检查，如果结论只存在于当前聊天，下次仍然要重新发现它。

结算因此是交付的一部分。它把已确认的行为和实现状态写回相应规格，留下代码、检查与证据入口，处理关联待办，记录遗留问题。项目入口负责导航，权威定义保留一份，各角色按需读取，避免维护多份逐渐漂移的“事实”。

记录还要区分三个层次：设计要求如此、从代码观察到如此、实际运行验证如此。看到接口存在，不能写成浏览器已验收；一次成功，也不能外推所有异常分支都可靠。对导出功能而言，下个会话应能直接找到权限规则、实现位置、实际检查与未覆盖项，而不必先相信上一位作者的总结。

持久化也不是魔法。重启后恢复的是任务记录、原生历史和已知成果；应先核实实际影响，再续办剩余工作。结果未知的操作不能盲目重放，更不能把“恢复了记录”写成“恢复了原工具执行现场”。

这套标准同样适用于开明自己。按项目 2026 年 11 月 9 日的验证记录，真实模型已经跑通过单项完整链路：创建 Task、开发、Review、Test、结算、结束，交付文件真实存在，测试实际运行，报告有保存。其中一次调用因为 Plan 缺少验收被程序拒绝，模型补齐后才继续。

这证明了相应程序路径能够在真实模型下走通，但不等于整个产品已经验收。新项目与已有项目接入等人工界面走查仍有未执行项，部分设计流水线场景也尚未逐条完成产品验收；负向控制要求和验证档规则是否被真实模型持续遵守，仍需要后续观察。已有证据、未执行检查和设计目标必须并列呈现。

对使用者而言，判断一项 Agent 工作是否值得接收，最终可以落到几个朴素问题：依据从哪里来，实际交付了什么，凭什么说它满足要求，检查能否识别错误，还有哪些边界未知，下次从哪里继续？

一套交付系统的作用，就是让这些答案留在项目里，能够被打开、核对和质疑。这样，“完成了”才有机会从一句让人放心的话，变成一个有证据支持、也允许被推翻的结论。
