# 从会写代码到可交付：Agent 怎样把一个系统真正做完

Claude Code、Codex 已经是很强的研发工具。[Claude Code](https://support.claude.com/en/articles/14554922-claude-code-user-faq) 能读取仓库、修改多个文件、运行命令；[Codex](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) 也把编写、审查和交付代码作为自己的工作。需求明确、边界清楚时，把一个功能乃至一个简单系统交给 Agent 推进，已经是值得认真采用的工作方式。

但当目标变成一个包含多个模块、需要持续演进的业务系统，问题会发生变化。我们不只要知道某段代码能不能运行，还要知道：各模块实现的是不是同一个需求，接口两端对“成功”的理解是否一致，测试有没有验证真正的用户结果，以及几周后换一个会话，项目还能不能从正确的位置继续。

这些本来就是软件工程长期面对的问题，不能都归因于 AI。Agent 场景尤其需要警惕的是：同一个未经确认的假设，可以在很短时间内贯穿设计、实现、测试和完成总结。很强的模型可能把这个假设实现得十分完整；两个各自合理的模块可能在组合后违背用户要求；大量通过的测试甚至会加强这种错觉，因为测试和实现来自同一份误解。生成更快、角色更多或换一个模型，都不会自动改变假设的来源。

开明尝试解决的，就是这一层工作。这里所说的“可交付 Agent”，指的是一种工作能力：让需求经过可检查的转化进入实现，让成果接受有独立依据的质疑，让“完成”对应当前成果和实际证据，并把这些结果留在项目里。它需要模型做判断，也需要文档、角色和程序共同承担责任。下面用同一个假设系统，说明这些机制为什么需要存在，以及它们到底能解决到哪一步。

## 一个取消订单的需求，为什么能做出三种“成功”

假设要开发一个订单系统，涉及订单、支付和用户页面。原始需求只有一句：“未发货订单可以取消，已付款的原路退款。”这个案例仅用于解释工程问题，不代表开明已经交付过订单系统。

如果立即拆给几个 Agent，订单开发者可能把取消理解成把订单状态改成“已取消”；支付开发者认为退款是独立操作，等别人调用退款接口；页面开发者看到取消接口成功，就显示“订单已取消，退款成功”。三个人都可能写出清楚、整洁、通过局部测试的代码，但没有任何人真正完成了用户要的事情。

问题先出在理解上。“可以取消”没有说明取消和退款是否必须同时完成，“原路退款”没有说明渠道只受理请求、尚未退回资金时应该如何展示。实现者不得不补齐空白，补出来的答案又变成其他模块的前提。一旦这些前提没有共同确认，代码越快写完，不一致就越快固化。

为了继续讨论，假设用户确认了以下行为：系统接受取消后，就不能再把这张订单推进到发货；已经确认收款的，应发起原路退款；退款可以异步完成，受理请求不等于退款成功；页面只有在支付渠道确认退款成功后，才显示“已退款”。退款明确失败时，应显示失败和后续处理入口；结果暂时未知时，不能显示成功，也不能当成明确失败重复发起。重复点击取消或收到重复通知，不能产生重复退款。

这些约定没有指定使用哪种框架，却已经排除了几种错误实现。它们同时把产品取舍暴露出来：用户愿不愿意接受“订单已取消，退款处理中”？退款失败后由谁处理？如果付款确认晚于取消到达，系统应怎样履行退款承诺？这些不是开发者为了让接口跑通就能随意决定的细节。

假设在本例中进一步确认：付款晚到不恢复已经取消的订单；一旦确认确实收到了款，仍应进入退款处理。这样，产品层面的含义才算足够清楚，架构才有可以落实的对象。

## 架构首先要决定：谁有权认定一件事已经发生

很多架构说明到“订单模块调用支付模块，前端调用后端”就结束了。这张调用图没有回答最容易出错的问题：谁保存订单是否取消的事实，谁保存资金是否退回的事实，谁有权改变它们，发生冲突时听谁的。

在这个假设系统里，可以让订单模块负责订单生命周期，以及是否还允许发货；支付模块负责付款、退款请求和渠道确认的结果。页面读取这些事实后展示，不凭一次按钮请求的成功自行创造“已退款”的结论。订单模块需要引用退款进展时，应明确它来自支付侧，不能再维护一套可以独立决定资金结果的业务真相。

这不要求订单和支付必须拆成微服务。一个单体应用、一个数据库也需要明确这个责任。否则，订单取消接口、发货接口、支付回调和页面刷新都可能各改一部分状态，系统没有一个位置能够保证“已取消订单不能发货”。架构的价值首先在于约束谁能改变什么，而不是增加多少层或多少进程。

接口也必须表达它真正完成了什么。取消接口成功，可以表示取消决定已经保存、后续不再允许发货；它不能顺便承诺资金已经到账。退款接口返回“已受理”，只能支持页面显示处理中。支付模块收到并确认渠道结果后，才有依据更新退款结果。这些语义应该同时进入接口约定、页面行为和测试验收，而不是靠字段都叫 `success` 就认为两端理解一致。

接下来要处理的是失败责任。订单已经保存取消，但向支付模块提交退款之前进程退出了，这笔退款由谁发现并继续？设计至少要让应退款的责任能够从已保存事实中重新找到，不能只依靠一次可能中断的函数调用。例如，在订单与支付共用数据库的方案中，可以把取消决定和这笔已收款订单的待退款记录放在同一事务保存。支付模块负责读取、处理这些记录；恢复运行时，重新找到尚未完成的退款，沿用原来的业务请求身份查询或继续处理，而不是因为上次调用中断就重新创造一笔退款。这样，即使进程退出，已经接受的取消也有可追查的后续责任。是否需要跨库消息等更复杂的机制，要看实际边界。

退款请求交出去以后，还有另一种失败。假如订单已经取消，调用退款渠道时网络超时，系统不能撤回已经给用户的取消承诺，也不能把超时直接解释为渠道没有收到请求。支付侧需要保留可追查的请求身份，按照渠道能力查询结果，确认可以重试时再重试；需要人工处理的情况也应有明确去向。如果渠道支持幂等请求，可以复用其能力，避免每次重试都变成一次新的退款。具体机制取决于实际依赖，不能仅凭一句“保证幂等”就当作问题已经解决。

付款回调与取消请求并发，更能检验架构是否说清楚了。取消已被接受，晚来的付款确认就不能把订单重新变成可发货；付款事实也不能因为订单取消而被丢弃。订单一侧要守住取消与发货之间的约束，支付一侧要如实记录收款，并依据已确认的规则继续退款。哪些更新需要在同一事务中完成，跨边界通知失败后如何补齐，是技术设计必须给出的实现约束。它们不能分别留给两个开发会话猜测。

这里没有一种脱离具体系统的标准答案。单库事务能解决的问题，不必先建消息平台；渠道已有的查询与幂等能力，也不必重复实现。需要先得到的是一份足以解释正常、冲突和失败情形的责任分配。架构越早把这些语义确定下来，后续独立开发的成果才越有可能按同一约定组合。

## 需求怎样成为不同 Agent 都能使用的依据

上述讨论如果只留在聊天里，下一位开发者仍然需要猜：最开始说的“取消即退款”和后来接受的“异步退款”，究竟哪个生效？聊天包含探索过程，里面有建议、反例、被放弃的方案和最终决定。保存全部聊天很有价值，但让每个开发者重新解释一遍，等于把已经作出的设计决定反复交给实现者重做。

所以，原始需求需要转化为可实施规格。这里的转化不是把长文切成短文，而是把用户目标展开为正常行为、异常行为、边界、验收和未知，并把产品取舍与技术责任接起来。订单产品规格说明什么时候允许取消、用户会看到什么、哪些结果尚未发生；技术规格说明状态归属、接口成功的含义、支付结果如何传播，以及相关实现约束。两者回答不同问题，但技术实现不能悄悄改变产品承诺。

原始需求的每一部分也应有去向。在本例中，“未发货可以取消”进入订单行为，“已付款原路退款”进入取消后的资金处理要求，尚未决定的人工处理方式保留为待决事项。如果原文还提到了取消后的库存释放，就不能因为第一轮只讨论了订单和支付而让它消失。来源覆盖说明要能指出它落在哪份规格、哪个切片，或为何明确不做。否则，规格再完整，也可能只是把被保留下来的那部分需求写完整了。

规格按长期能力组织，通常比按角色分文件更可靠。取消订单是一个完整的用户能力，不能因为前后端分别开发，就在前端文档和后端文档里各定义一遍取消规则。支付结果的含义在支付契约中完整定义，其他模块引用它；待办和 Plan 也引用规格，不再改写一套近似说法。这样，当“退款处理中”的规则变化时，可以找到唯一的定义及其使用方，而不必在多份摘要之间判断谁更新得更晚。

文档还需要支持定位。索引告诉 Agent 每份资料负责什么、什么时候应读；模块地图把职责、规格、代码位置和对外接口连接起来；稳定的章节标题让一次 Task 能引用具体行为。正文则保留足够完整的语义，包括例外和未知。只有标题和几句摘要，虽然容易塞进上下文，却很容易删掉最需要遵守的限制。

开发订单取消的 Agent，应从项目入口定位订单规格，读取支付接口的必要章节、共享权限要求和本次 Plan，再找到相关代码与测试。它不必读取营销、推荐等无关模块，也不必重读全部设计聊天；发现引用缺失或依赖不足时，可以继续补读。主管的工作是给出最小但足够的起点，不能把“最小”理解成限制开发者只能看几段材料。

这种组织方式解决的首先是权威与依赖问题。全量上下文没有自动区分有效决定和历史提议的能力，碎片化摘要又可能丢掉关键条件。模块内聚、单一权威定义和明确引用，使一个独立会话有机会从项目文件重建正确的任务理解。它仍然需要读懂材料，也仍然可能发现规格有错；文档结构只是让这些错误更容易被定位和讨论。

对于已有代码的项目，同样没有必要先写完整套理想文档。可以先调查现有能力和代码入口，确认模块边界，在第一次修改相关模块时补齐规格。尤其要把“观察到代码这样做”与“确认应该这样做”分开，否则整理文档会把现有缺陷合法化。

## Task 和 Plan，把一次交付的边界固定下来

有了规格，仍然不能把“实现订单系统”当成一个无限延长的任务。这样的目标没有稳定的结束条件：支付做完以后还有退款，退款做完以后还有异常补偿，最后任何缺口都可以被解释为下一步。

在开明的设计里，Task 保存一次正式工作的目标、关联依据、阶段、参与角色、结果与报告。它可以是一项设计、一段实现、一份正式文档，也可以是只读调查。它让用户和后续会话能够回答“这一次在交付什么”，不需要从长对话中重新拼出进度。待办保存以后可能做的事，规格保存系统行为，Task 保存本次工作的事实，三者没有必要互相代替。

Task 的总体 Plan 在修改之前写下验收和范围。沿用本例，一项“实现已付款订单取消”的工作，可以引用已经确认的取消与退款规格，并明确本次要验证：取消后无法发货；退款只受理时页面不显示已退款；渠道确认后显示相应结果；重复请求不会形成多笔退款。范围同时说明改哪些模块、依赖哪些接口，已有支付查询能力是否需要改变。

先写这些内容，有一个直接作用：开发者不能在实现之后，把验收改写成自己恰好完成的事情。如果当前代码只做到订单状态变更，先前留下的验收会把退款缺失暴露出来；如果为了跑通流程顺手改了共享权限规则，范围会让这项影响进入审阅，而不是消失在“相关优化”里。

Plan 也不是冻结一切的合同。实施中发现渠道根本不支持原定的退款方式，继续照旧实现没有意义；应该把事实带回设计，说明可选方案及影响，由用户决定产品承诺是否改变，再更新规格和 Plan。范围内的普通技术选择则由 Agent 自主处理，不需要每个步骤都请求批准。计划的作用是保留改变的依据，让越界和改验收成为可见决定。

大功能还需要切成可分别交付和验收的目标，先明确共享接口，再安排依赖。一项切片通常应把写入集中在一个模块，使一次 Review 能看清；但局部可验收不意味着整个用户流程已经可用。订单接口、支付适配和页面分别完成后，还要有明确的组合验收，走通本例的取消、处理中、成功及关键失败路径。最终系统不能靠把三份“通过”相加来成立。

设计 Task 交付的是经过独立审阅、完成必要用户确认的规格和切片，不能因此宣称功能已实现。只读调查交付的是结论、来源与未知，不应顺势修改代码。行为实现才承担开发、独立审核、适用测试和结算的责任。区分这些完成条件，才能既避免漏掉检查，也避免每次讨论都被迫进入完整开发流程。

## 独立角色，究竟要独立什么

主管需要理解总目标、选择依据、协调依赖，给每个专业 Session 明确的工作范围和预期结果。多个开发者可以在边界清楚时并行，但不能同时改同一份文件再由最后一次写入决定结果；当前步骤还有成员未结束时，也不能拿先到的一份报告宣布整步完成。

不过，多 Agent 的主要价值并不在于并发。开发者一旦采用了某种理解，就会围绕它建立实现、测试和解释。如果同一会话接着“切换为审核员”，原来的解释仍在上下文里。让它再认真一点有帮助，却没有改变证据来源。

因此，Review 应从独立上下文读取用户目标、Plan 的验收和范围、正式规格、实际成果与运行证据，不读取作者或主管聊天中的自评。审核者需要重新回答：取消和退款的责任是否落实在了正确的位置？页面是否把受理当成完成？测试的期望是不是从实现输出反推出来的？这次改动是否影响了范围外的发货路径？作者报告可以索引变更和命令，但“这已经充分覆盖”本身不是证据。

Review 和 Test 也不是两个人重复做同一件事。Review 更适合检查需求到实现的对应关系、责任边界、遗漏和证据质量；Test 则需要从真实入口执行已约定的路径，观察系统实际产生的结果。代码审阅发现退款结果没有被持久化，就应先修复和复审，不必让测试者继续在已知不成立的实现上收集通过记录。审阅通过后再进行独立 Test，测试发现问题则回到开发、重新审阅，再验证变化后的成果。

独立上下文只能减少作者叙述带来的偏向，不能凭空创造正确答案。同一个模型可以在隔离上下文中承担不同责任；换成不同模型，也可能共同相信一份错误规格。如果需求本来就遗漏了“取消后不得发货”，几个角色完全一致并不奇怪。因此，审核不仅要查实现是否遵循规格，也要检查规格与原始目标、已确认决定之间是否存在明显断裂。发现产品取舍未定，应把问题带回去，而不是替用户选择最容易通过的答案。

## 测试要先回答：什么使这个结果成为正确答案

假设开发者写了一组取消测试：调用接口，返回成功，数据库订单状态变成已取消。这些测试能够证明局部行为，却没有验证退款。继续增加不同订单编号和不同金额，可能只是把同一份遗漏重复证明了很多遍。

测试需要一个判断正确与否的依据，工程上常称为 test oracle。它可以来自用户确认的验收、独立可控的数据、接口契约，或由业务约束推出的不变量。这里最重要的是来源，而不是术语：不能先运行当前实现，再把它的输出保存下来，称为标准答案。

在本例中，用户已经确认“渠道只受理时不得显示已退款”。测试就可以构造一个确实处于受理阶段的支付结果，检查页面仍显示处理中；之后送入渠道确认，再检查页面变化和保存的退款记录。重复通知用例应检查同一次退款业务结果保持唯一，而不是只看第二次请求有没有返回成功。金额相关断言也应从测试前独立设定的付款事实推导，不能照抄被测接口给出的金额。

还要进一步检验：如果系统违反这条规则，测试会不会真的失败？可以在隔离测试副本中，故意把“退款受理”映射成“退款成功”，运行同一检查。它应因为页面提前显示已退款而失败。若测试照样通过，说明它没有观察到关键结果；若只是依赖没装好、服务没启动或超时报错，也没有证明它能识别这一类缺陷。

这就是负向控制的作用。已知错误必须按预期原因被拒绝，检查器才显示出区分这一类对错的能力。测试报告应保留错误样本或变异方式、运行步骤、实际失败和原因。开发阶段有意义的先失败再通过，可以帮助确认新测试确实覆盖了待修行为；独立 Test 仍应有自己的负向控制，不能只接收作者提供的一串通过数字。

一个坏样本被识别，只证明这一类错误能被发现。它不证明所有并发情况都覆盖，也不证明规格没有遗漏。测试的说服力来自一组有来源、有区分力、与风险对应的检查，不能由用例数量代替。

Mock 和单元测试仍然非常必要。开发者可以快速模拟退款受理、失败、超时，检查局部状态转换。问题是这些证据的适用范围：Mock 出一个渠道回调，不等于真实渠道使用同样的字段、签名和重试方式；函数返回正确，不等于服务已经保存结果；页面组件收到正确属性，不等于浏览器通过实际接口能拿到它。

所以，适用的独立测试必须继续走到运行中的服务和真实页面，核对请求、保存结果和用户可见状态之间的关系。支付依赖可以在渠道测试环境中验证，但报告应说明它能证明什么，不能把沙箱成功写成生产资金链路已经通过。最终组合验收尤其要覆盖跨模块的交接处：取消已保存但退款尚未完成、晚到的付款确认、重复通知，以及明确失败后的用户反馈。

如果本次验收要求验证真实渠道，而环境没有准备好，当前结论就是阻断或未执行。可以保存已经取得的单元和集成证据，继续完成不依赖该环境的工作；不能把尚未发生的检查改写成“基本通过”。如需缩小交付目标或接受某项非阻断覆盖缺口，应明确交由用户决定，并保留这个决定。已经观察到的功能缺陷也不能通过改名为“未覆盖”消失。

## 程序能核对证据是否存在，不能替证据作结论

仅靠提示词写上“必须独立审核、必须测试”，还不足以知道这些工作是否真的发生。一个会话的总结可能把开发自测说成独立测试，也可能引用上一次任务的报告，或者在检查通过后又改了代码。

这些问题中，有一部分适合由程序核对。报告提交者是否属于当前 Task，角色和报告种类是否符合本次工作，必要成员是否已经停止执行，报告有没有实际保存，被检查的文件是否还是当前文件，都可以通过明确记录比较。开明的技术契约把这些事实交给程序，而把验收是否充分、问题是否解决、授权是否覆盖当前动作等语义判断留给主管与独立角色。

这条分工很具体。程序可以拒绝一份没有验收章节的 Plan，但不能因此保证补上的验收有意义；可以确认存在一份测试通过报告，但不能凭标题判断其中的步骤有效；可以列出实际变更与声明范围的差异，但是否属于合理的依赖调整，仍要结合用户授权和业务影响判断。把这些含义全部编码成关键词规则，只会让系统逐渐围绕措辞运行。

成果版本是另一类可以核对的事实。假设订单取消实现经过 Review 和 Test，随后开发者又“顺手”把退款重试条件改了。旧报告可能完全真实，但证明的是修改之前的成果。继续引用它，会把“过去检查过”偷换成“现在检查过”。

开明的做法是由程序记录报告所覆盖的交付路径及内容摘要，完成时重新核对。被检查的代码发生变化，原报告不再足以支持结束，需要重新审核并进行适用测试。代码任务的结算文档有单独边界，正常回填记录不应导致无意义的重审重测；交付物本身就是文档时，文档仍要绑定审阅。目的在于保持证据和成果对应，而不是任何文件变化都重新启动全部流程。

内容摘要也有边界。它能说明所绑定的文件没有变化，不能说明外部服务、配置和数据从此不会变化，更不能证明测试报告里的业务推理正确。检查环境、替代依赖、执行时间和未覆盖项仍需随证据保留。这也是为什么一份保存完整的报告，既重要又不足以单独宣布交付。

Task 的结束因此包含两种责任：模型依据正式要求和检查结果判断目标是否满足；程序核对适用报告、当前成果、成员状态及真实保存等必要事实。对于有 Git 的项目，被复核的交付路径是否相对 HEAD 已提交，也是可以核对的保存事实。程序不代替模型写出“业务正确”的结论，模型也不能用一句“已经保存”代替实际保存。

## 结算，让这次做对的事情成为下次工作的起点

假设订单取消终于完成了验证，规格中的实现状态却仍标着“未实现”，代码入口还指向旧接口，已经验证过哪些路径也只有历史报告里能找到。下一个 Agent 接手时，可能重复实现已有能力，也可能为了补一个自以为缺失的功能，破坏已经成立的约定。于是，今天的验证成果没有成为项目当前事实，只是被保存在某段历史里。

结算要解决的正是这个问题。新的行为和接口含义应在实现之前明确，并随成果接受检查；结算回填的是这次实际做到和验证到哪里，不能等到最后才按代码结果改写需求。它需要更新原权威规格中的实现状态、相关代码与测试入口，处理已完成的待办，留下真实的未覆盖项和证据引用。订单规格继续定义取消承诺，支付契约继续定义退款结果；索引只负责指向它们，不复制一份新规则。已经存在的文档没有受影响，就没有必要为了结算重新写一遍。

状态也必须精确。设计要求退款异步完成，只表示系统应该如此；从代码中看到处理逻辑，只表示存在相应实现；实际在某个环境中验证了受理、成功和重复通知，才支持这些路径的验证结论。付款与取消并发尚未运行，就应该保留这项未知，不能被“退款能力已完成”的概括掩盖。

有 Git 的项目还需要提交本次交付及相关记录，让下一次工作能定位一份实际保存的成果。无关的工作区改动应该保留，不能为了制造“干净”状态一并提交或删除。保存和提交并不提高业务正确率，但它们决定经过检查的成果能否被准确找回；缺少这一步，换一个会话或工作环境，就可能接在另一份代码上。

跨会话接续也不应依赖模型记住整个聊天。新的主管从 Task、Plan、当前规格和有效报告恢复已知进度，再核实实际成果，继续剩余工作。进程重启后，保存下来的记录并不等于原工具调用还能从断点继续。对于结果未知的操作，要先查清影响再决定是否重试，不能把重新执行当作恢复。这与订单案例里“支付请求超时不等于没有发生”是同一种事实边界。

结算的可观察结果应当很朴素：一个未参与前序开发的会话，能找到当前行为、实现位置、已验证范围和剩余问题，并据此开始下一项工作。仅有一份漂亮的完成报告，达不到这个要求。

## 这套机制值得付出多少成本

规格、隔离上下文、独立检查和保存证据都需要时间，也会消耗更多模型调用。它们只有在降低真实交付风险时才有价值。把所有工作都套进最大流程，会让重要检查淹没在重复劳动中。

开明按变化的影响选择验证强度。一个不改变事件、状态、请求或数据，也不涉及共享布局或设计令牌的文案、纯样式修改，可以走简短计划、独立 Review 和结算，不建立 Test 阶段；一个局部交互或接口行为，开发执行定向检查，页面交互再走一条聚焦浏览器路径，独立 Test 验证本次验收和相关回归；共享契约、权限、数据迁移或状态机变化，才有理由扩大到跨模块或全量验证。判断依据是影响，而不是改了几行代码。

同样，已有规格足够就直接实施，小目标明确可以在简短 Plan 中说明验收，没有必要重新设计整个项目。用户只要调查，就交付调查。并行能够缩短独立工作的时间，却不能消除接口依赖；如果多个 Agent 需要不停同步一个尚未确定的语义，先把那项决定说清楚通常更划算。

系统本身也应遵守这个尺度。开明复用 Pi 的 coding-agent SDK 承担模型循环、原生工具与会话历史，工作台保存 Task、角色关联、报告和交付事实。浏览器或外部 Agent 可以成为入口，项目事实不必随着入口变化重新建立。已有 SDK 能力够用，就没有必要重造一套；不能因为需要保存工作状态，就顺势设计一个囊括所有业务判断的工作流语言。

这也限定了开明目前能够声称的成果。按项目 [2026 年 11 月 9 日的验证记录](../docs/technicalnew/validation.md)，真实模型已经跑通创建 Task、开发、独立 Review、Test、结算和结束的程序路径，交付文件真实存在，测试实际运行，报告保存并关联了交付状态。其中一次调用因为 Plan 缺少验收被拒绝，补齐后才继续。这是一条具体的运行证据，说明相应机制并非只停留在设计文本里。

但这类实验不能证明开明已经稳定交付任意多模块业务系统。该记录仍列有未执行的人工产品验收，一些设计流程只得到单元或集成测试覆盖；真实模型能否在长期复杂工作中持续写出充分验收、有效负向控制并作出正确判断，也不能由一次流程通过推出。本文的订单案例用于推演机制，不是业绩证明。设计要求、已有实现和真实验证，需要像文章要求其他项目那样分开说明。

回到最初那张订单。值得交付的结果，是用户取消后不会再被发货，退款按约定推进，页面如实反映资金状态，失败有明确去向；同时，项目里能够找到支撑这些结论的依据和检查，尚未验证的部分仍然可见。下一位 Agent 接手时，也不需要重新猜测“成功”意味着什么。

强模型提供了完成这些工作的能力，交付系统则把这种能力组织成可质疑、可核对、可接续的项目成果。它不能消除错误，但应当让错误更有机会在成为用户损失之前暴露，并让每一次修正真正留在项目里。
