# 代码能写出来，系统怎样才算交付？

Claude Code、Codex 已经是很强的研发工具。[Claude Code](https://support.claude.com/en/articles/14554922-claude-code-user-faq) 能读仓库、修改多个文件、运行命令；[Codex](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan) 也把编写、审查和交付代码作为自己的工作。一个需求明确的简单系统，已经可以交给 Agent 推进实现。继续把它们看成补全代码的助手，会低估这类工具。

不过，能完成研发任务，和能交付一个多模块系统，中间还有不少工作。系统变大以后，难点常常出现在一段代码开始依赖另一段代码的地方。每部分单独看都说得通，合起来却未必符合用户原来的意思。

比如，要做一个支持付款和取消的订单系统。需求写着“未发货订单可以取消，已付款的原路退款”，看起来已经足够明确。负责订单的 Agent 把取消理解为改订单状态，负责支付的 Agent 认为退款需要单独申请，页面则在取消接口返回成功后显示“已退款”。这里甚至不需要谁写出明显的坏代码，用户就已经得到了一个错误结果。

这既有需求理解的问题，也有架构的问题。订单状态由谁负责，取消接口的成功是否就表示退款完成，都得有一致的约定。付款回调和取消请求同时到达时，也要明确由谁决定最终结果。如果这些事情没有先说清，模块会各自补上一个合理假设。等到联调时，才发现接口名字一样，背后的意思却不一样。再补几个判断，可能让眼前这条路径跑通，却把同一项业务判断留在了两个地方，以后改规则还得猜哪里也要跟着改。

我觉得，讨论 Agent 做系统，应该更多看这种地方。代码写得快，反而更需要尽早弄清哪些决定会影响别的模块。否则，方向一旦偏了，Agent 也能很快把这个方向实现得相当完整。

测试未必会把它拦下来。

还是这个例子。如果开发者认为取消只需要改状态，他很容易写出这样的测试：调用取消接口，检查返回成功，再检查订单状态为已取消。测试通过，说明实现符合他的理解。需求里本来需要处理的退款，没有进入实现，也没有进入测试。让同一个 Agent 再“全面检查一下”，它可能继续沿着这份理解补用例，最后得到一组越来越齐全的通过记录。

所以，测试的预期要另有来处：用户确认的要求、已经确定的接口约定，或者业务上必须成立的关系。若约定取消成功后必须退款，就得检查真实支付结果；若退款失败时只允许显示处理中，就不能用“取消接口返回成功”代替整个流程成功。还应故意放进一个会出错的情况，比如让付款后的取消漏掉退款，看看检查能不能真的失败。如果漏掉退款也能通过，这组测试就没有检查到原来的要求。

这也是开明想做“可交付 Agent”的原因。

面对一个大目标，先把用户要走的流程和关键异常说清，再决定模块职责及它们之间的约定。订单状态放在哪里、支付模块返回的成功究竟表示什么，这些决定要成为后续实现共同使用的依据。涉及产品取舍和模块边界，由用户确认；实现者不应在写代码时各自发明一套。目标小、依据清楚，就直接做，也没必要为了显得完整再写一轮架构。

这份共同依据也得经得起实现。假如支付渠道不支持原定的退款方式，就要把限制带回设计，重新确认用户会看到什么，再调整相关模块。不能只在支付代码里绕过去，继续让页面按原来的承诺显示结果。

分工随后才有意义。每项工作要能单独验收，依赖的接口先明确，完成后还得把组合起来的系统走一遍。订单模块和支付模块分别通过检查，不能推导出用户取消订单这条流程已经通过。真正的联调需要运行中的服务，需要看页面显示与实际保存的状态是否一致，也需要碰一碰约定里的失败情况。

文档在这里有很具体的用途。接手订单取消的 Agent，应该从项目索引找到订单模块，查到允许取消的状态和取消后的结果；再沿引用找到支付接口，弄清退款成功与退款受理的区别。共用的权限规则也要一起读，不能因为任务只写“订单模块”就忽略它。发现条件不足，可以继续补读或提出问题。

这比把整个项目的材料都塞进每次对话更容易核对：这次工作的判断依据究竟在哪里？订单规则只在一个地方定义，支付模块引用它，避免各写一份后慢慢变成两种说法。索引负责带人找到相关内容，模块文档保留完整语义。下一位 Agent 不需要重读设计时的全部聊天，也能知道接口该怎么用、哪些事还没有决定。

独立审核同样围绕成果展开。审核者拿到正式要求、这次工作的验收和实际变更，自己核对实现；测试者从真实入口验证用户结果。开发者写的总结可以说明改了什么，却不能成为“已经正确”的依据。检查若发现依据本身含糊，就把问题退回去决定，不能为了维持进度，替用户挑一个最方便实现的解释。

这些安排也不能保证系统从此没有问题。它们至少应该让“完成”有东西可查：交付对应哪份代码，检查实际跑过什么，哪些依赖被替代，哪里还没验证。修复后成果变了，相应的检查也要跟上，旧的通过记录不能继续证明新的代码。

项目留下的当前说明也要随之更新。新同事或新会话打开项目，应该能找到已经验证的行为和剩余缺口，而不是面对一份写着“全部完成”的过期概况。

回到订单系统，要交付的始终是用户从付款走到取消时，能得到约定的结果。假如真实退款环境还没有跑过，这件事就该留在项目的未验证项里，写清还需要怎样检查，等下一次继续，而不是随着一段完成总结从视野里消失。
