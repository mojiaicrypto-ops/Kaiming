# 需求体系外接远程系统的可行性调研

2026-10-26。范围：需求（提案 / 实施需求）是否可以从「项目本地 Markdown 文件」改为「可对接飞书等远程系统」。本轮只做可行性判断，不改代码、不改需求契约。

## 结论

**技术上可行，改动量中等（约 2～3 个工作日量级，不含飞书侧权限与字段搭建）；但对现有产品保证有四处不可回避的损失，必须先决定接受哪几条。**

- 代码耦合点很少：只有 `runtime/requirement-store.ts` 认识文件，上层（工具、任务、界面）只认 `<id, 文本/元数据, 版本>`，可以插入一层接口而不重写。
- 真正的难点不是 HTTP，而是**状态机与权威归属**：远程系统的状态是自由拖拽的，本地状态是主管显式写入的决定。
- 第一期（飞书）**建议做镜像，不做替换**：本地仍是权威，远程做发布与回填。理由见 §5。

## 1. 现状耦合面（实测，非估计）

| 位置 | 依赖 | 说明 |
|---|---|---|

结论：**只有一处实现认识 `.dev/requirements/`**。改成「接口 + 两个实现」不需要动任务、界面或提示词。

## 2. 需要抽出的接口

```ts
interface RequirementSource {
  readonly capabilities: {
    versioned: boolean;      // 能否做「读过才可覆盖」的内容级乐观锁
    offline: boolean;        // 断网时能否读取
    structured: boolean;     // 能否保存七节结构化正文
    statusAuthority: 'local' | 'remote';
  };
  list(projectId, filter): { items, invalid, cursor };
  get(projectId, id): { found, text, metadata, version };
  save(projectId, id, markdown, expectedVersion): { ok, version } | { conflict, current };
  promote(projectId, id): { ok } | { refused, reason };
}
```

`capabilities` 不是装饰：看板必须据此如实显示「远程不可达 —— 需求内容不可读」，而不是显示成「没有需求」（现行 R-02 的硬要求）；`save` 在 `versioned: false` 时只能退化为「最后写赢 + 冲突提示」。

## 3. 飞书侧的能力核对（第一手 API 文档）

| 需求字段 | 飞书任务 Task v2 | 判定 |
|---|---|---|
| 标题 | `summary`（≤3000 字符） | ✅ 直接映射 |
| 正文 | `description`（≤**3000** 字符） | ⚠️ 现有实施需求正文常超 3000（七节 + 验收）；只能存摘要，正文要另找地方 |
| 状态 | **无常驻状态字段**，只有 `completed_at`（完成 / 未完成） | ❌ 5 个本地状态（pending/in_progress/completed/cancelled/archived）无法直接映射；自定义单选字段可以，但**该字段必须关联到任务清单**才可写 |
| 状态设置 | `POST /task/v2/tasks` 支持 `custom_fields`（`single_select_value` 填选项 guid） | ✅ 可行，需先规划一个任务清单 + 一个单选字段 |
| 更新 | `PATCH /task/v2/tasks/:task_guid`，必须显式列 `update_fields`；**未列出的字段不动，列了却没给值会被清空** | ⚠️ 更新是「字段级指令」，没有内容版本；并发只能靠后写覆盖 |
| 幂等 | 创建支持 `client_token`（10～100 字符） | ✅ 与本地「先保存再提交」的回执模型天然契合，重复推送不会建出两条任务 |
| 来源标识 | 创建时可设 `origin`（平台名 + 链接），创建后不可改 | ✅ 可在飞书任务里标出「来自 AgentDev + 关联需求」 |
| 速率 | 10 次/秒 | ✅ 富余 |
| 除任务外的形态 | 云文档 docx：块级 API（创建 / 批量更新 / 删除块），可承载七节正文与真实 Markdown 结构 | ✅ 正文的正确去处 |
| 文档块限制 | 需要在 Task 与文档之间建立关联（`docx_source` 需 token + block_id，二者须为 27 位且 block 未绑定其他任务） | ⚠️ 关联成本不低；也可只在任务 `origin.href` 里放文档链接 |

**结论**：飞书能承载「标题 + 状态（走自定义单选）+ 链接」，**不能承载完整结构化正文**。正文要么放 docx（多一层创建/更新/绑定），要么放本地继续权威。

## 4. 语义差距与损失（必须先接受）

| 现有保证 | 远程权威后 | 影响 |
|---|---|---|
| R-06：项目复制 / 换环境仍能读需求 | ❌ 不再成立（权威在远程） | 需改产品契约，或保留只读快照（又违反「一份事实来源」K-03） |
| 离线可读（需求纯文件） | ❌ 需要缓存 + 过期标记 | 看板必须新增「远程不可达」状态 |
| 内容级并发（读过才可覆盖，sha256） | ⚠️ 退化为字段级最后写赢 | 「三个人同时改同一条需求」会静默丢失；本地可检测，远程不能 |
| 七节结构化模板 + 格式校验 | ⚠️ 正文进 docx 时格式校验只剩本地一半 | 验收条件是否还在，取决于文档内容，不再可机检 |
| R-05：状态不由 Task 数量推断，由主管显式写 | ⚠️ 远程任何有权限的人都能拖状态 | 必须新增「远程变更待确认」的事实，否则看板与真实决定脱节 |
| 需求 id 稳定（`req-xxx`） | ✅ 双向映射表可保 | 但映射表本身成为新的权威事实，要进 SQLite 并纳入恢复 |

## 5. 三种形态的成本与取舍

| | A. 镜像（本地权威） | B. 适配器（远程权威） | C. 双向同步（都权威） |
|---|---|---|---|
| 改动 | 新增 `RequirementMirror` 组件 + `requirement` 工具的发布动作 + 配置页一段；不动 store 与 Task 边缘 | 抽 `RequirementSource`、实现 `LocalFileSource` + `FeishuSource`，改 3 处调用点，加缓存/过期语义 | B + 冲突解决、变更拉取、映射表恢复 |
| 工期量级 | 1 天 | 2～3 天（含飞书侧建清单/字段） | 1～2 周，且长期维护成本高 |
| 保留的保证 | 全部（离线、版本检查、七节模板、R-06） | 丢失 R-06 / 离线 / 内容级并发 | 名义上全保留，实际靠冲突策略 |
| 团队可见性 | 飞书里能看到任务与状态（发布后） | 飞书里就是唯一事实 | 同 B |
| 风险 | 低：远程挂了不影响任何工作 | 中：远程不可达时需求看板与 Task 创建都要降级 | 高：两套写入者互相覆盖 |

## 6. 建议

1. **第一期做 A（镜像）**：本地权威不变，需求保存 / 状态变化时把「标题 + 状态 + 链接 + 摘要」推成飞书任务；飞书侧的状态变更拉回来只作为「有人改了，待主管确认」的提示，不自动改本地状态。这样 §4 的损失一条都不发生。
2. **先把接口抽出来**（`RequirementSource` + `capabilities`），本地实现先落地并保持现状行为；远程实现挂在同一接口后。这一步即使最终不做远程也有价值：它让「需求」不再等于「文件」。
3. **飞书侧需要用户先决定的准备工作**（不是代码）：
   - 用一个专属任务清单承载 AgentDev 的需求（自定义字段必须挂任务清单）；
   - 定义一个单选字段「需求状态」，选项与本地 5 个状态一一对应（guid 要配置到 AgentDev）；
   - 是否要为正文建 docx（若否，飞书里的描述只是摘要）。
4. **不要在第一期就做双向同步**：冲突策略需要真实的飞书使用数据才能定，现在定只能靠猜。

## 7. 未决问题（需要用户回答后才能进入设计）

- 远程的用途是「让团队看到进度」还是「让团队直接在飞书里管需求」？前者 = A，后者 = B。
- 需求正文是否必须在飞书里可读可改？若是，接受正文进 docx 或接受「飞书只有摘要」。
- 飞书侧状态被人工改动时，希望 AgentDev：忽略 / 提示待确认 / 直接采纳？
- 一个 AgentDev 项目对应飞书里一个任务清单，还是所有项目共用一个？
- 是否需要把「任务（Task）」也发布到飞书（那是另一条映射，且 Task 生命周期短、更新频繁，成本更高）。

## 8. 存档（2026-10-26）

用户决定：**存档，以后再讨论**。不排期、不进入设计、不改 R 系列契约。

存档时形成的定位（恢复讨论时的起点）：AgentDev 作为**执行端**，需求由飞书等远程系统管控（写入方可以是人或另一个有权限的 Agent）；问题因此从「读哪里」变成「谁有资格改需求 + 多台执行端如何不撞车」。

讨论中还形成一条应作为前提的判断：**执行端永不修改需求的目标与验收，只能回传事实（进度、阻塞、反向发现）**。写端可以换人、换 Agent，这条不变；它是 R-03「不能修改验收来掩盖实际缺陷」的跨机器版本。
