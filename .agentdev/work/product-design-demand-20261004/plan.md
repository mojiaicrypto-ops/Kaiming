# 产品需求转化与设计角色整合

## 目标与授权
用户已确认需求提案、实施需求、设计工作和实现流程的整体方向，并要求先修改产品文档。仅更新 docs/productnew 与文档入口状态；不修改业务代码、技术协议或提示词。

## 依据与上下文
读取 docs/INDEX.md、当前八份产品文档及 workflow skill 的设计、原则、结算规则。历史 docs/old、业务源码和开发聊天不作为当前产品依据；既有技术契约只用于标记后续待同步，不反向限制已确认的产品行为。

## 实施安排
1. 改需求管理：轻量提案、实施需求、设计转化、来源关系、实现关联与返回设计。
2. 改任务交付及项目知识：合并设计责任，保留产品/技术文档边界、独立审阅、结算和按需上下文。
3. 同步总览、用户流程、主管入口、工作区入口与可观察验收。
4. 独立审阅当前产品文档，检查一致性、链接、遗漏和不必要复杂度；修复后复查。
5. 保存本次实际证据与结算，只提交本轮文件，保留用户无关改动。

## 返回设计的衔接
同一交付目标补充设计时，停止实现写入，在原 Task 内委派设计 Session，审阅当前依据后继续。用户主动暂停的 Task 不自动启动设计。重新拆成不同交付目标时，确认并保存替代需求与成果关系，安全取消旧实现 Task；新需求按原有效授权或新决定另行启动，不创建父子 Task 树。

## 验证与限制
执行文档链接和格式检查，并由独立 Session 审阅。未运行产品、模型、SDK 或故障测试，不宣称功能已实现。技术文档与角色提示词须后续按产品变化同步，入口明确标记。
